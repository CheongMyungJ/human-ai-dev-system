## 실행 방법 (P3-03 기준)

**필요한 것:** Windows, Python 3.12(`py -3.12` 로 잡히는 것), Git, Node.js 22 이상.
런타임은 3.12로 고정돼 있다. `python` 과 `py` 의 기본 버전이 달라도 스크립트가 `.venv` 의
인터프리터를 직접 가리키므로 세션마다 달라지지 않는다.

```powershell
# 1) 한 번만: 저장소 로컬 가상환경 + Python 의존성 + 웹 UI 빌드
scripts\bootstrap.ps1

# 2) 제어부 (기본 http://127.0.0.1:8765, 빌드된 화면을 같은 주소에서 서빙)
scripts\run-controller.ps1

# 3) 다른 창에서 로컬 Runner
scripts\run-runner.ps1

# 4) 전체 시험 (제품 pytest 242건 + P1 OpenCode 문서 계약 unittest 18건)
scripts\run-tests.ps1
```

설치 대상은 저장소 안의 `.venv\` 와 `web\node_modules\` 뿐이다. 사용자 전역 Python·Node·CLI
설정은 바꾸지 않는다. 상태 DB·원문·로그는 `var\` 에 생기며 커밋하지 않는다. 지워도 다시 만들어진다.

**추가로 필요한 것(P2-03):** 설치·로그인된 Codex CLI 또는 Claude Code.
시스템은 이 CLI들의 **자격증명을 읽지도 주입하지도 않는다.** 로그인은 각 CLI 자신의 설정에 있다.
설치되지 않은 도구는 사용 가능으로 표시되지 않고, 그 도구를 쓰는 실행은 거부된다.

**지금 동작하는 범위:** 프로젝트·Case 생성, 원문 제출과 Runner 영속 저장,
여섯 항목 의도 초안(**AI 작성 또는 사람 작성**)·성공 기준·원문 열람·피드백·미정 질문·명시 동의,
QG-01 의도 품질 게이트(규칙 검사 + **작성과 별도 세션의 AI 의미 검토**),
**FR-29 진입 조건 검사**(서버 측, 화면을 우회한 직접 호출도 동일),
실제 코딩 CLI를 **읽기 권한으로** 실행하고 실행 ID·정규화 이벤트·결과 원문 저장,
**기준별 결과와 근거 열람, 사람 최종 인수·예외 수용·종료, 연결된 새 Case**,
**일곱 축 근거가 있는 작업 수준(간소·표준·심층)과 사람의 조정**,
**설계안·개발계획을 각각 조회·검토**(기본값 둘 다 사람 검토, 단계별 자동 진행 선택),
**준비가 갖춰졌을 때 기능 구현 배정이 열리는 FR-29 선행 조건 검사**,
**작성 실행에 고정되는 이전 버전·피드백 참조**(재작성이 산출물을 처음부터 다시 쓰지 않게),
강제 종료 후 복원, 같은 요청 재전송의 중복 실행 방지.
**작업 그래프와 Task 단위 의존·질문 차단**(P3-02),
**Case 전용 브랜치·worktree 와 기준 커밋, 실제 코드 수정과 빌드·테스트 실행의 증거**(P3-03).
**아직 아닌 것:** 합의한 작은 기능의 수직 시나리오(P3-04),
나머지 품질 게이트와 게이트 ON/OFF 설정(P4), GitHub(P5), 원격·인증(P6).

**쓰기 권한은 P3-03에서 열렸다 — 조건부로.** `workspace_write` 는 **준비된 Case 작업공간이
있는 구현·검증 실행에만** 배정된다. 작업공간이 없으면 `workspace_not_ready` 이고, 의도·설계·계획을
쓰는 실행에는 여전히 `permission_not_allowed_in_stage` 다. `explicit_escalated` 는 아직 열지
않았다. 그리고 **worktree 는 파일 배치의 분리이며 OS 격리가 아니다**(D-44) — 작업공간 밖의
변경은 감지해 드러낼 뿐 막지 못한다.

### 의도 흐름을 화면에서 확인하는 절차 (P2-02)

제어부와 Runner를 모두 띄운 뒤 http://127.0.0.1:8765 에서:

1. 프로젝트를 만들고 **기능 개발** 유형으로 Case를 만든다. 기능 개발 Case에만 의도 화면이 뜬다.
2. `의도` 화면에서 여섯 항목(목표·기대 결과·범위·제외사항·제약·미정 질문)을 쓴다.
   **비워 둔 항목은 미정으로 남는다.** 시스템이 값을 채우지 않는다.
   내용을 쓴 항목에는 내용의 성격(사용자 요구 / 프로젝트 규칙 / 관찰 사실 / AI 제안 / AI 가정)을 고른다.
3. 제출한다. 제어부는 본문을 저장하지 않고 Runner로 중계한다. Runner가 저장하고 항목 구조를
   보고하면 표에 나타난다(1~2초).
4. `원문 받아 보기` 를 누른다. 본문은 소유 Runner에서 와 이 화면에만 나타난다.
   **원문을 받아 보기 전에는 동의 버튼이 잠겨 있다.**
5. 피드백을 보내거나 미정 질문에 답한다. **둘 다 동의가 아니다.** 동의 상태는 그대로 `동의 없음`이다.
6. 동의 문구를 직접 쓰고 `이 버전에 명시적으로 동의` 를 누른다. 동의는 그 버전·그 원문에만 붙는다.
7. 새 버전을 제출하면 동의 상태가 `이전 버전에만 동의함`으로 바뀐다.
   과거 동의는 기록으로 남지만 최신 버전에 적용되지 않는다.

Runner를 멈추고 4를 해 보면 `PC 연결 필요` 로 표시된다. 원문이 사라진 것이 아니다.

실행 증거는 [P2-02 결과](p2/evidence/P2-02-results.md)에 있다.

### 진입 제어와 실제 CLI 실행 (P2-03)

P2-03부터 **기능 개발 Case의 실행은 서버가 조건을 검사한 뒤에만 열린다.** 순서는 이렇다.

1. `의도` 화면에서 `AI에게 초안 요청` 에 원하는 것을 쓰고 보낸다. 요청 원문이 Runner로
   가고 **설치된 코딩 CLI가 읽기 권한으로** 여섯 항목 초안을 써서 새 의도 버전이 된다.
   화면에 `작성 주체: AI가 작성해 제시한 초안` 으로 표시된다.
   사람이 직접 쓰는 폼도 그대로 있다.
2. `QG-01 의도 초안 품질 게이트` 패널을 본다. 구조가 보고되면 **규칙 검사**가 자동으로
   돌지만 종합 판정은 `검토 안 함` 이다. 규칙만 통과한 것은 통과가 아니다.
3. `실행` 에서 목적을 `QG-01 의미 검토` 로 골라 실행한다. **작성과 다른 세션**에서
   CLI가 초안을 검토하고, 찾은 것이 기준·필수/권고·차단 효과와 함께 표에 나타난다.
   두 세션의 식별자가 다르다는 것이 패널에 함께 표시된다.
4. 게이트가 `실패` 면 이유가 보인다. **이때도 열람·질문 답변·피드백은 막히지 않는다.**
   피드백을 보내고 새 버전을 만들면 이전 판정은 `재검토 필요` 가 되고 새 버전은
   `검토 안 함` 에서 다시 시작한다.
5. 원문을 받아 보고 그 버전에 명시적으로 동의한다.
6. `실행` 에서 목적을 `제한 작업` 으로 골라 실행한다. 동의와 게이트 통과가 **둘 다**
   있어야 열린다. 하나라도 없으면 `진입 조건 미충족` 과 사유가 표시되고 Run은
   만들어지지 않는다.

확인해 볼 만한 거부들:

- 목적을 `기능 구현` 으로 고르면 조건을 다 갖춰도 거부된다 — 선행 조건인 설계·계획
  검토가 아직 없기 때문이며, 임시 통과 처리를 넣지 않았다.
- 권한을 `workspace_write` 로 고르면 거부된다 — 코드를 바꾸는 실행은 P3에서 연결한다.
- 설치되지 않은 도구는 목록에 없고, API로 직접 지정해도 거부된다.

**이 검사는 화면이 아니라 서버에 있다.** 버튼을 거치지 않고 `POST /api/cases/{id}/runs`
를 직접 불러도 같은 409와 같은 사유 코드가 돌아온다. 진입 검사 기록은 허용·거부 모두
화면 아래 표와 `GET /api/cases/{id}/admission-checks` 에 남는다.

실행 증거는 [P2-03 결과](p2/evidence/P2-03-results.md)에 있다. 라이브 검증에서
**QG-01이 AI가 쓴 초안을 두 번 연속 실패시켰고**(모순·확인 불가능한 성공 기준·빠진 질문)
게이트를 느슨하게 고치는 대신 피드백 → 새 버전 → 재검토로 통과시켰다.

화면은 실제 브라우저로 1~2와 6의 거부 표시까지 확인했다
([캡처](p2/evidence/P2-03-ui-ai-draft.png), [기록](p2/evidence/P2-03-ui-check.log)).
3~6을 화면에서 누르는 경로는 P2-04의 시연에서 닫았다(아래).

### 처음부터 끝까지 화면으로 하는 시연 (P2-04)

`scriptsootstrap.ps1` → `scripts
un-controller.ps1` → 다른 창에서
`scripts
un-runner.ps1` 을 띄우고 http://127.0.0.1:8765 에서 아래를 그대로 따라간다.
**전부 화면의 버튼과 입력 칸이며 API를 직접 부르지 않는다.**

1. **프로젝트와 Case.** 프로젝트를 만들 때 `저장소 경로` 에 Runner 호스트에서 해석할
   실제 폴더를 적는다. 그 폴더가 CLI의 작업공간이 된다. Case 유형은 **기능 개발**.
2. **AI에게 초안 요청.** 만들고 싶은 것을 쓰고 코딩 CLI를 골라 보낸다. 실제 CLI가
   읽기 권한으로 여섯 항목 초안과 **성공 기준**을 써서 새 의도 버전이 된다.
   `작성 주체: AI가 작성해 제시한 초안` 으로 표시된다. 사람이 직접 쓰는 폼도 그대로 있다.
3. **QG-01 의미 검토.** `실행` 에서 목적을 `QG-01 의미 검토`, 도구를 코딩 CLI로 골라
   실행한다. **작성과 다른 세션**에서 검토가 돌고 두 세션 식별자가 함께 표시된다.
   실패하면 지적 사항이 기준·필수/권고·차단 효과와 함께 보인다.
4. **실패했으면 복구 경로를 탄다.** 피드백을 보내고 다시 초안을 요청한다. 새 버전이
   생기면 이전 판정은 `재검토 필요` 가 되고 새 버전은 `검토 안 함` 에서 다시 시작한다.
   **게이트를 느슨하게 고치지 않는다.**
5. **피드백을 닫는다.** `아직 닫지 않은 피드백` 에서 `의도 vN 이 반영함` 또는 이유를 적고
   `반영하지 않음` 을 누른다. **사람이 판단한다** — AI가 스스로 "반영했다"고 적지 않는다.
   닫지 않으면 마지막 인수가 `unresolved_feedback` 으로 거부된다.
6. **원문 열람과 동의.** `원문 받아 보기` 를 누른 뒤에만 동의 버튼이 열린다.
   동의하면 그 버전의 성공 기준이 `제안` 에서 `사람이 확인한 기준` 으로 바뀐다.
7. **제한 작업.** 지시 원문을 제출하고 `실행` 에서 목적을 `제한 작업` 으로 골라 실행한다.
   동의와 게이트 통과가 **둘 다** 있어야 열린다.
8. **기준별 판정.** `결과와 최종 확인` 에서 기준마다 판정과 근거를 고르고 기록한다.
   근거를 실행 결과로 고르면 **그 실행이 정상 완료했을 때만** `충족` 이 기록된다 —
   결과가 `unknown` 인 실행으로는 거부된다. `근거 원문 받아 보기` 로 결과 원문을 읽는다.
9. **최종 확인.** `결과 후보 만들기` 를 누르면 의도·동의·게이트·기준별 결과·미해결 항목·
   미정리 실행이 한 버전으로 묶인다. 인수 문구에 `이 결과를 인수` 같은 표현이 없으면
   거절된다. 남은 미충족은 예외로 수용할 수 있고, **원래 판정은 그대로 남는다.**
10. **종료 후.** 종료된 Case 는 새 의도 버전·새 실행·새 동의를 받지 않는다. 수정 요청은
    `연결된 새 Case 만들기` 로 만들며 이전 동의를 승계하지 않는다. 읽기와 설명은 그대로 된다.

확인해 볼 만한 거부가 더 있다.

- 성공 기준을 하나도 쓰지 않으면 QG-01에 권고로 표시되고 최종 인수가
  `no_success_criteria` 로 거부된다. 견줄 기준 없이 결과를 인수하지 않는다.
- 결과가 `unknown` 인 실행이 남아 있으면 **인수는 기록되고 종료는 확정되지 않는다.**
  화면에 `인수됨 · 실행 상태 확인 필요` 로 두 상태가 함께 보인다.
- 완료 정책을 `조건 충족 시 자동 완료` 로 바꿔도 사람 인수로 기록되지 않으며,
  자동 모드는 미충족·미검증을 스스로 예외 수용하지 않는다.

실행 증거는 [P2-04 결과](p2/evidence/P2-04-results.md)에 있다.

### 수준·설계·계획을 화면에서 확인하는 절차 (P3-01)

위 시연의 6단계(원문 열람과 동의)까지 마친 Case 에서 이어 간다. 새로 보이는 것은
`작업 수준과 준비 산출물` 패널이다.

1. **작업 수준.** AI 초안이 일곱 축의 `판단 / 미확인 / 영향`과 함께 수준을 제안한다.
   축을 **점수로 합산하지 않는다** — 권한 축 하나가 높으면 나머지가 모두 낮아도 심층이
   도출된다. 제안이 도출값보다 낮으면 화면이 그 사실을 알리고 **낮은 쪽을 쓰지 않는다.**
   수준을 바꾸려면 `조정 이유` 와 `남는 위험` 을 둘 다 적어야 한다. 조정은
   **의도 동의·성공 기준·검토 옵션을 해제하지 않는다.**
2. **설계안 작성.** `실행` 에서 목적을 `설계안 작성`, 도구를 코딩 CLI로 골라 실행한다.
   동의된 의도 원문이 **고정 컨텍스트로 실려** 간다. 수준이 요구하는 항목이 표로 보이고
   비어 있는 필수 항목은 `현재 수준이 요구하는 항목이 미정이다` 로 표시된다.
3. **원문 열람과 사람 검토.** `원문 열람 (일시 중계)` 로 설계 원문을 읽고
   `이 설계안을 검토했다` 를 누른다. **화면을 열어 본 것은 검토가 아니다** — 이 버튼이
   사람의 검토 결정을 `decision` 표에 남긴다.
4. **개발계획 작성.** 목적을 `개발계획 작성` 으로 골라 실행한다. **설계 검토 전에는
   거부된다**(`design_review_missing`). 계획에는 동의된 의도와 **현재 설계**가 고정
   컨텍스트로 실린다.
5. **기능 구현 배정.** 목적을 `기능 구현` 으로 골라 실행한다. 빠진 것이 있으면 사유가
   종류별로 보인다 — 수준 미결정, 설계·계획 없음/오래됨/항목 미정, 검토 미완, 이월 질문
   미해결. **모두 갖추면 이 목적이 처음으로 허용된다.**
6. **쓰기 권한은 따로다.** 같은 상태에서 권한을 `workspace_write` 로 바꾸면
   `permission_not_allowed_in_stage` 로 거부된다. **검토를 마쳤다는 사실이 쓰기 권한을
   만들지 않는다**(P3-03에서 작업공간과 함께 연다).

확인해 볼 만한 거부가 더 있다.

- 수준을 **심층으로 올리면** 같은 산출물의 필수 항목이 늘어나 `design_incomplete_for_level`
  로 막힌다. 준비가 업무에 비례한다는 것의 관측 가능한 형태다.
- 검토 방식을 `자동 진행` 으로 바꿔도 **산출물은 그대로 필요하다.** 상태는
  `자동 조건 충족 (사람 승인 아님)` 으로 표시되고 `decision` 표에 사람 검토 행이
  생기지 않는다. 설정만 바꾸고 조건 충족을 기록하지 않으면 여전히 막힌다.
- **새 의도 버전이 생기면** 두 산출물이 `의도가 바뀌어 재검토 필요` 가 되고 이전 검토를
  재사용하지 않는다. 수준 판단도 같은 규칙으로 대체된다.
- 설계를 다시 만들면 그 위에 세웠던 계획이 대체된다. 계획 목록에는 `superseded` 로
  남아 무엇이 있었는지 조회할 수 있다.

실행 증거는 [P3-01 결과](p3/evidence/P3-01-results.md)에 있다.

### 작업 그래프와 질문을 화면에서 확인하는 절차 (P3-02)

위 절차의 4단계(개발계획 작성)까지 마친 Case 에서 이어 간다. 새로 보이는 것은
`작업 그래프` 패널이다.

1. **계획이 작업을 낳는다.** 개발계획을 쓰면 그 안의 `tasks` 가 작업 그래프
   리비전이 된다. 목록에 작업마다 종류·목적·산출물·완료 조건·선행 작업·대응하는
   성공 기준이 보인다. **계획이 작업을 정의하지 않으면 그래프가 없고**, 기능 구현은
   `work_graph_missing` 으로 막힌다 — "Task 가 없다"를 "Task 가 필요 없다"로 읽지
   않는다.
2. **무엇이 왜 막혀 있는가.** 작업마다 `배정 가능` 또는 차단 사유가 보인다. 사유는
   서버가 계산한 것을 그대로 보이며, 화면이 따로 판단하지 않는다.
3. **좁히기.** 이월 질문이 특정 작업을 막는다고 적혀 있으면 **그 작업만** 막힌다.
   독립 작업은 계속 배정된다. P3-01에서는 질문 하나가 업무 전체를 멈췄다.
4. **좁히기가 느슨해지지 않는다.** 질문에 기다리는 작업이 적혀 있지 않거나, 적힌
   작업을 찾지 못하면 화면이 **모든 작업이 막혀 있다**고 알린다. 연결이 없다는 것은
   "아무 것도 막지 않는다"가 아니라 무엇을 막는지 모른다는 뜻이다. 그때는 질문에
   답하거나 기다리는 작업을 지정해 좁힌다. **연결을 고치는 것은 답하는 것이 아니다** —
   연결된 작업은 여전히 막힌다.
5. **순서.** 선행 작업이 끝나지 않으면 후속 작업은 `task_dependencies_unmet` 으로
   막힌다. **완료는 실행 결과다** — 사람이 누르는 완료 버튼은 없다. 조사 작업을
   `제한 작업` 으로 실제 실행해 끝내면 그 사유가 사라진다.
6. **성공 기준 대응.** 기준마다 구현 작업과 검증 작업이 보인다. **확인할 작업이 없는
   기준은 표시만 한다** — 배정을 막지 않는다. 연결이 적절한지는 사람 검토와 (P4의)
   게이트의 몫이다.
7. **사람의 재계획.** 작업을 더하거나 취소하면 **새 리비전**이 만들어지고 이유가
   남는다. 이유를 비우면 거부된다. 이전 리비전과 그 작업의 실행 이력은 보존되므로
   **재분할이 실패 이력을 초기화하지 않는다.** 분할은 추가 + 취소로 한다.

확인해 볼 만한 거부가 더 있다.

- 그래프에 없는 `task_id` 로 배정을 요청하면 `task_not_in_work_graph` 다.
  취소된 작업도 같다. 이 검사는 **제한 작업에도 적용된다** — 조사도 실행이다.
- 의존 관계에 **순환**이 있거나 없는 작업을 가리키면 그래프가 만들어지지 않는다.
  잘못된 그래프를 저장하면 그 뒤의 모든 차단 판정이 그 위에서 이루어진다.
- 없는 성공 기준을 가리키는 연결도 거부된다. 조용히 버리면 "연결했다"는 기록만
  남고 실제 연결은 없다.
- **새 의도 버전이 생기면** 그래프가 `work_graph_stale` 이 된다. 이전 리비전은
  조회로 보존된다.
- 그래프를 갖춰도 **작업공간이 없으면** `workspace_write` 는 `workspace_not_ready` 로
  거부된다(P3-03). 그래프는 "무엇을 어떤 순서로"이고 작업공간은 "어디에"다.

실행 증거는 [P3-02 결과](p3/evidence/P3-02-results.md)에 있다.

### 작업공간에서 코드를 바꾸는 절차 (P3-03)

위 절차까지 마친 Case 에서 이어 간다. 새로 보이는 것은 `작업공간` 패널이다.

1. **작업공간을 준비한다.** `작업공간 준비 요청` 을 누르면 제어부에 요청이 남고,
   저장소를 가진 Runner 가 **Case 전용 브랜치와 worktree** 를 기준 커밋 위에 만든다.
   **요청은 준비됨이 아니다** — `requested` 상태에서 쓰기는 계속 거부된다.
2. **사용자의 원래 작업 트리는 건드리지 않는다.** 저장소에 미커밋·미추적 파일이 있어도
   시스템은 커밋·stash·reset·삭제를 하지 않는다. 기준 커밋은 **커밋된 상태**이므로
   선택되지 않은 변경이 따라오지도 않는다. 화면이 "변경 N건이 있었고 건드리지 않았다"고
   적는다.
3. **덮어쓰지 않는다.** 같은 이름의 브랜치나 비어 있지 않은 경로가 이미 있으면 준비가
   `failed` 가 되고 사유가 남는다. 우리가 만든 것으로 확인되면 재사용하며, 그때도
   **기준 커밋은 처음 만든 그 커밋**이다.
4. **구현 실행.** 준비가 끝나면 구현 Task 에 `workspace_write` 배정이 열린다. 실행이
   끝나면 화면에 **파일 수·삽입·삭제 줄 수와 HEAD 전후**가 보인다. 변경 내용과 파일
   경로는 제어부에 없다 — 상세는 원문 조회로 본다.
5. **바뀌지 않았으면 완료가 아니다.** CLI 가 "고쳤다"고 보고해도 작업공간이 그대로면
   그 실행은 `failed` 이고 Task 는 끝나지 않는다. 이것이 없으면 아무 것도 바꾸지 않은
   실행 하나로 후속 Task 가 전부 열린다.
6. **검증 실행.** 빌드·테스트는 `검증 실행` 으로 돌린다. **실행한 명령과 종료 코드**가
   증거로 남고 출력 원문은 Runner 에 있다. **종료 코드가 0이 아니어도 실행은 완료다** —
   "테스트가 실패했다"와 "검증을 수행하지 못했다"는 다른 것이다. 명령이 하나도 없으면
   완료가 아니다.
7. **경합.** 같은 Case 의 쓰기는 하나씩만 배정된다(`case_write_in_progress`). 읽기 전용은
   그때도 배정된다. 같은 Runner 의 동시 쓰기도 기본 1개이며, 두 번째 쓰기는 **거부가
   아니라 대기**다 — 앞의 쓰기가 끝나면 그대로 배정된다.
8. **격리 한계.** 패널 아래에 "worktree 는 파일 배치의 분리이며 OS 격리가 아니다"가
   서버가 준 문장 그대로 보인다. 실행 중 작업공간 밖이 바뀌면 그 사실이 드러나지만
   **막은 것이 아니고 되돌리지도 않는다.** 사람이 직접 worktree 를 고친 것도 같다 —
   드러내되 보존한다.

실행 증거는 [P3-03 결과](p3/evidence/P3-03-results.md)에 있다.

## 먼저 읽을 문서

1. [전체 설계](design-draft.md): 첫 버전 범위, 업무 흐름, 구성도, 실행·저장 모델.
2. [주요 시나리오·기능 요구사항](scenarios-functional-requirements.md): SC-01~12, FR-01~30과 수용 기준.
3. [비기능 요구사항](nonfunctional-requirements.md): NFR-01~12와 장애·데이터·컨텍스트 검증.
4. [구현·운영 계획](implementation-baseline.md): 채택 기술, 설치, 백업, 동시성, 개발 순서와 기술 검증.

핵심 구조는 Python/FastAPI 제어부·Python Runner·SQLite·React/TypeScript 웹 UI다. 기능 개발은 의도 초안·사람 피드백·최신 동의를 필수로 거치고 필요한 설계·개발계획 후 구현한다. AI가 업무에 맞는 작업 그래프를 제안하며 시스템이 승인·버전·검증·진행 조건을 검사한다.

첫 버전은 Windows 네이티브·한 사용자·프로젝트당 Git 저장소 하나·업무별 브랜치와 worktree다. 로컬·서버 완결형과 서버 제어부 + 개인 PC Runner를 지원한다. PC 분리형에서는 상세 문서·대화·코드·diff·로그를 PC에 두고 서버는 상태·요약·참조와 일시중계만 맡는다. 상세 열람과 새 원문 저장에는 PC 연결이 필요하다.

## 검토 결과의 경계

주요 제품 정책에 대한 답변 수집은 끝났다. 실제 Windows/CLI의 도구 경계 제어, 원문이 서버 로그·캐시에 남지 않는지, 부분 장애 복구와 목표 규모의 성능은 구현 단계에서 시험해야 한다. OpenCode는 미설치 상태의 문서 기반 설계이며 실환경 검증 완료로 표시하지 않는다.

공동 사용·Linux/WSL·복수 저장소/프로젝트 업무·지식 자동 추출/채택·인터넷 직접 공개·병합/배포는 확장 범위로 분리했다. 확장 가능성을 준비하는 것과 첫 버전에서 구현하는 것을 구분한다.
