## 0. 제품 판단

**새로 내린 제품 판단: QG-02~07 의 길 하나 — 사용자 결정 (ⅱ) 진행기가 켠 게이트를 스스로 돌린다(2026-09-24, D-94, 3.4절).**
DEVELOPMENT 1.11절이 "UI-05a 시작 때 묻는다"고 정했다. 이 세션은 **답과 무관한 부분(전수 대조·작업 그래프·실행 상세)을 먼저
끝낸 뒤** 물었다(사용자가 실시간으로 답하기 어려운 조건). 답을 받기 전에는 3.4절을 구현하지 않았다. 같은 자리에서 P4-09 의
남은 질문 "실행 중 Case 의 취소 2단계" 는 **UI-05b 에 붙인다**로 답을 받았다.

그 밖에는 새 판단을 내리지 않는다. 상세 설계 선택(제품 정책이 아니다, 9절에도 적는다):

- **옮긴 화면은 기존 API·서버 판정을 그대로 부른다.** 작업 그래프는 `GET /cases/{id}` 의 `preparation.work_graph`(진입 검사와
  같은 값), 수정은 `POST …/work-graph/tasks`·`…/tasks/{key}/cancel`·`PUT …/questions/{id}/blocks`, 실행 상세는
  `GET /runs/{id}`(이벤트·잔류 관찰·명령·문맥)·`GET /runs/{id}/context-refs`. 화면이 막힘·배정 가능을 계산하지 않는다.
- **자리: 오른쪽 패널의 넷째 탭 `작업`.** 작업 그래프(작업·막힌 이유·기준 대응·기다리는 결정)와 실행(목록·상세)을 한 탭에
  둔다 — 둘 다 "지금 무엇이 왜 멈췄나"의 진단이고, 대화 흐름(카드)은 거기로 가는 버튼만 갖는다. 대화 머리에 `작업` 버튼,
  대기 카드·요청의 실행 세부·진행 이력의 실행 id·이월 질문 카드에서 이 탭(그 실행·그 질문)으로 간다.
- **그래프 수정 뒤 진행기가 다음 걸음을 본다(서버 보강).** 지금 세 끝점은 기록만 하고 진행기를 부르지 않아, 사람이 막힌
  Task 를 취소하거나 질문 연결을 고쳐도 다음 사건이나 `다시 시도` 전까지 아무 일도 없다. 다른 사람 결정(동의·확인 지점·
  delta·한도)과 같은 `_after_human_input` 을 붙인다 — 새 권한이 아니라 기존 진행 규칙의 호출 시점이다.
- **종료된 Case 의 그래프는 고치지 못한다(서버 보강).** 지금 `_replan`·`set_question_blocks` 는 종료·취소된 Case 도 새
  리비전을 만든다. 화면에서 감추는 것은 잠금이 아니므로 서버가 `guard_open_case` 로 거부한다(D-33 "종료 뒤 수정은 연결된 새
  Case", P4-09 (e) "취소 뒤 무반응"과 같은 방향).
- **실행 상세는 읽기 전용이다.** 요약·수·식별자·상태만 서버에서 오고 본문(출력·원문)은 기존 열람 경로(결과물 패널의 뷰어 —
  PC 에서 불러옴)로 연다. 새 저장·새 중계 없음.
- **질문 연결 고치기는 답이 아니다.** 화면이 그 말을 한다(API 계약 그대로 — 연결을 고쳐도 질문은 `open`, 연결된 Task 는 계속
  막힘).

## 3. 설계

### 3.1 전수 대조

관리 화면 파일(`App.tsx`·`*Panel.tsx`)의 버튼·폼·표시를 하나씩, 부르는 API·새 화면 대응·진행기 대응과 함께 적는다. 분류 기준:
`옮김` = 사람이 해야 하는데 새 화면·진행기 어디에도 없다, `대신함` = 새 화면 또는 진행기·요청 처리기가 같은 일을 한다(위치
명시), `개발자 전용` = 요청 처리기·진행기를 끈 운영(`HADS_AUTO_PROCESS_REQUESTS=0`)이나 진단에서만 필요, `버림` = 옛 흐름.
결과는 결과 문서 2절의 표다.

### 3.2 작업 그래프 — 제어부 (`controller/api.py`·`controller/repository.py`)

- `add_task`·`cancel_task`·`set_question_blocks` 끝점이 기록 뒤 `_after_human_input(request, repo, case_id, "replan:<rev>")`.
- `Repository._replan`·`set_question_blocks` 첫머리에 `guard_open_case`.

### 3.3 작업 그래프·실행 — 화면 (`web/src/shell/WorkPanel.tsx`(새)·`ReviewPanel.tsx`·`Shell.tsx`·`ConversationView.tsx`·`ProgressCards.tsx`·`events.ts`·`shell.css`)

- `PanelTab` 에 `work`. 탭 버튼 `작업`(`panel-tab-work`), 대화 머리 `작업` 버튼(`open-work`).
- `WorkPanel`: (가) 그래프 머리 — 리비전·출처·사유, 오래됨 경고, 연결 없는 질문 경고, 해석 못 한 참조. 그래프가 없으면 없다고
  적는다(준비됨으로 보이지 않는다). (나) 작업 목록 — 행마다 키·종류·상태·배정 가능/막힌 이유(서버 `readiness.blocked_by`)·
  저장소·산출물·완료 조건·선행·기준(관계)·그 작업의 실행(리비전을 가로지르는 `taskRuns`, 누르면 실행 상세), 취소(이유 입력
  필수). (다) 기준 대응 표(판정하지 않음). (라) 기다리는 결정 — 질문별 기다리는 작업(없으면 "모든 작업을 막는다"), `연결
  고치기` → 작업 체크 + 이유 → 저장, "답이 아니다" 문구. (마) 작업 추가 폼. (바) 실행 목록(최신순) → 실행 상세.
- 실행 상세: `api.getRun` + `preparationApi.contextRefs` 를 연 때 한 번(목록의 상태가 바뀌면 다시). 절 — 기본(목적·역할·도구·
  버전·모드·권한·상태·결과·종료 코드·배정 세대·Runner·세션·만든/끝난 시각·시작하지 않은 이유·사용량·잔류 + 잔류 관찰),
  고정 입력(참조 표 + 문맥 요약 — 상태·인라인 바이트/한도·생략·못 읽음·영수증 세대·최신성·지식 제공/생략/범위 미확정),
  진입 검사(이 run_id 의 기록), 이벤트(순번·시각·종류·원래 종류), 명령(요약·종료 코드·시간), 작업공간 효과(변경 여부·누적 수·
  관측 범위·외부 변경), 출력 열기(결과물 뷰어로 — `hads:open-ref`). 종료되지 않은 실행은 "진행 중" 을 적는다.
- 이동: `hads:open-panel` 의 탭에 `work`, 새 신호 `hads:open-run {caseId, runId}`(작업 탭을 열고 그 실행 상세). 대기 카드
  (`GenericWaitCard`·`LimitWaitCard`)에 `작업·실행 보기`, 요청 진행의 `실행 세부` 의 실행 id, 결정 사항 패널 진행 이력의 실행 id,
  이월 질문 카드에 `기다리는 작업 고치기`. **관리 화면 링크는 이번에 지우지 않는다**(UI-05b).
- 종료·취소된 대화: 보기만(폼 없음).

### 3.4 QG-02~07 — 진행기가 켠 게이트를 스스로 돌린다 (사용자 결정 2026-09-24, D-94)

**코드 대조로 확인한 사실(이슈 #7 의 1차 조사와 다르다):** 관리 화면도 QG-02~07 판정을 **기록하지 못한다**. 관리 화면의 실행
폼으로 `quality_gate_review` 실행을 만들 수는 있지만, Runner 가 올린 발견(`quality_gate_findings`)을 게이트 실행 기록
(`record_quality_gate_run`·`start/complete_quality_gate_run`)으로 옮기는 코드가 제어부 어디에도 없다 — 판정 기록은
`POST /api/cases/{id}/quality-gate-runs` 를 직접 부를 때만 생기고(시험이 그렇게 한다), 어느 화면도 그 끝점을 부르지 않는다.
**기본 적용(추천, 정책 리비전 0)된 게이트는 막지 않는다** — 그 목적은 기존 구조 검사(설계·계획 검토, 작업 그래프, 검증 실행과
기준 판정, 종료 후보 대조)가 강제한다. 막는 것은 **사람이 설정 탭에서 명시적으로 켠 게이트**뿐이고, 그때 판정을 만드는 경로가
없어 끄는 것 말고는 풀 수 없었다.

사용자에게 (ⅰ) 사람이 새 화면에서 돌림 / (ⅱ) 진행기가 스스로 돌림 / (ⅲ) 끄기로 풀고 미룸을 물었고, 게이트와 성공 기준의 차이를
설명한 뒤 **(ⅱ)** 를 골랐다(D-94). 사람은 한도가 다 된 뒤에만 부른다. 모양은 진행기의 QG-01 경로(검토 → 지적 반영 재작성 →
한도 뒤 사람 카드)와 같다.

**어디서 막는가(현재 연결 그대로):** 명시 ON 게이트가 실행 조건인 곳은 `quality_gate_blockers_for_run` 의 셋이다 — 계획 작성 전
QG-02, 구현 전 QG-02·QG-03(Task), 검증 전 QG-04(Task). QG-05·06·07 은 명시로 켜도 지금 어느 실행의 조건도 아니다(기록만 —
9절 한계). 진행기는 이 셋만 돌린다. **한 가지 고침:** Fast Lane(결합 기록)은 설계가 따로 없으므로 계획(결합 기록) 작성 전의
QG-02 는 "검토할 설계가 아직 없다" — 지금은 영원히 막는다. 설계 산출물이 없을 때 계획 작성에는 QG-02 를 요구하지 않고, 구현
전에는 결합 기록을 QG-02 의 대상으로 본다.

**대상(subject)** — `subject_key` 는 고치는 동안 바뀌지 않는 이름(repair 한도가 새 버전마다 초기화되지 않게), `input_hash` 는 그
버전(P4-01 모델 그대로):

| 게이트 | 막는 실행 | subject_key | input_hash·대상 | 고치는 실행(repair) |
|---|---|---|---|---|
| QG-02 설계 적합성 | 계획 작성(설계가 있을 때)·구현 | `design` | 현재 설계(없으면 결합 기록) 원문의 해시 | 설계 재작성(결합 기록이면 결합 기록 재작성) |
| QG-03 계획 실행 가능성 | 구현(그 Task) | `plan:<Task>` | 현재 계획(또는 결합 기록) 해시 + Task 키 | 계획(결합 기록) 재작성 |
| QG-04 구현 묶음 품질 | 검증(그 Task) | `impl:<Task>` | 그 검증 Task 가 기다리는 구현 Task 의 마지막 완료 실행과 트리 지문 | 그 구현 Task 다시 실행 |

**흐름(순수 규칙 `domain/work_flow.py` `quality_gate_step`, 진행기가 계획·구현·검증 걸음 직전에 부른다):** 켠 게이트가 막고
있으면 (1) 검토 중이면 기다림, (2) 대상이 없으면 사람 대기, (3) 그 대상 버전의 판정이 없거나 옛 버전 것이면 **독립 검토 실행**
(`quality_gate_review`, 검토자·읽기 전용, 대상 저장소의 작업공간 — 작업 id `qg:<게이트>:<Task>`), (4) 판정이 실패·보류면 게이트의
수정 한도(기본 2, 게이트 설정) 안에서 **repair 실행**(지적 목록을 지시문에 싣는다), 한도가 다 되면 사람 대기(`quality_gate` —
게이트·판정·지적·사용/한도), (5) 검토 자체가 실패(`blocked`)면 재시도 한도 안에서 다시 검토, 넘으면 사람 대기. 통과면 원래 걸음.

**제어부:** 검토 실행을 만들면 게이트 검증 1회를 연다(`start_quality_gate_run` — 시작 당시 정책 고정, P4-02 예약 규칙 그대로).
검토 실행의 결과 보고에 발견(`quality_gate_findings`)이 실려 오면 결과 기록 뒤·진행기 앞에서 그 검증을 닫는다
(`complete_quality_gate_run`, 검사 = 독립, 근거 `run:<id>`, 기준 참조 = 현재 기준 키 — 연결 없는 필수 의견은 권고로 내림, 기존 규칙).
실행이 실패하면 `blocked` 로 닫는다. repair 실행을 만들면 `start_remediation_attempt(product_repair)`, 그 실행이 끝나면
`complete_remediation_attempt`. 게이트 설정 변경(`PUT …/quality-gates/{gate}/policy`)도 사람의 결정이므로 기록 뒤 진행기를 부른다.

**Runner·지시문:** 결과 보고에 `quality_gate_findings`. 검토 실행의 배정에 게이트 정보(게이트·이름·목적·Task·대상 이름·기준 키)를
싣고 지시문 머리에 적는다. repair 실행(설계·계획 작성·구현)의 배정에 그 게이트의 지적 목록(요약)을 싣고 지시문에 "품질 게이트의
지적" 블록을 넣는다 — QG-01 지적 블록과 같은 모양.

**화면:** `quality_gate` 대기 카드(새) — 게이트·판정·지적 요약·수정 사용/한도, `수정 한도를 올리고 계속`(게이트 설정의 한도 +1,
사유 기록)·`이 게이트 끄기(사유)`·`작업·실행 보기`. 설정 탭 게이트 줄에 repair 사용 수. 대기 문구의 "관리 화면에서 진행" 을 고친다.

## 9. 알려진 한계·설계 선택

- QG-05·06·07 은 명시로 켜도 어느 실행의 조건도 아니다(P4-01 이 기록만 연결). 진행기는 막는 게이트만 돌린다 — 연결은 별도 plan.
- 통과한 게이트의 대상이 그 뒤 바뀌면(예: 사람 편집) 재검토는 P4-02 변경 사건(`needs_recheck`)의 몫이다. 진행기는 진입 검사가
  막을 때만 돈다(진입 검사와 다른 판단을 하지 않는다).
- 검토 실행은 프로젝트 기본 도구(같은 CLI·모델 허용, 별도 세션)로 돈다.

- 작업 탭의 데이터는 대화 상세 조회 주기(5초, 진행 중 1.5초)를 따른다. 실행 상세는 연 때 한 번 + 그 실행 상태가 바뀌면 다시.
- 작업 추가 폼은 기준 연결(`criteria`)을 받지 않는다 — 관리 화면도 받지 않았고, 기준 연결은 계획 원문의 자리다(필요하면 UI-05b 이후).
