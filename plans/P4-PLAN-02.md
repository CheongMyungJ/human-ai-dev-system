# P4-PLAN-02

변경·예약. 기준: 설계 v0.7 / D-01~67 / 2026-09-22.
선행: P4-01 완료(스키마 v13, pytest 430 + P1 계약 18 통과를 이 세션에서 재확인).
범위는 **P4-02 하나**이며 여섯 Profile 전수(P4-03)·컨텍스트 재개(P4-04)·완료 경로(P4-05)·
지식(P4-06·07)·외부 게시(P5)는 포함하지 않는다.

## 1. 현재 구현과 이 작업이 메울 차이

P4-01은 QG-01~07의 유효 정책, 명시 override, 조건부 독립 검토, 판정, 기본 2회 repair를
만들었다. 그러나 **시간축이 없다.** 지금 `set_quality_gate_policy`는 언제 호출되든
즉시 적용되고, `record_quality_gate_run`은 이미 끝난 평가 하나를 통째로 적는다.
그래서 다음이 구현되어 있지 않다.

1. **진행 중인 검증 1회**라는 상태. `quality_gate_run.status`에 `running` 값은 있지만
   그 상태를 만드는 경로가 없어 "지금 검사 중"을 표현할 수 없다.
2. 실행 중 설정 변경의 **예약**과 검증 1회 종료 시점의 반영(D-30). 지금은 진행 중
   검증이 있어도 정책이 즉시 바뀌고 그 실행의 `validity`가 바로 `needs_recheck`로
   내려간다 — 예약만으로 진행 중 검사를 무효화하지 않는다는 계약과 반대다.
3. **요청 설정 / 예약 설정 / 실제 적용 시각**의 구분. 지금은 `created_at` 하나뿐이다.
4. 요청·코드·권한 변경의 **부분 재검증**. 지금은 정책을 바꾸면 그 게이트의 현재 실행이
   전부 `needs_recheck`가 되고, 반대로 의도·코드가 바뀌어도 일반 게이트 실행은 아무
   영향을 받지 않는다. 영향 있는 것만 다시 보고 나머지는 이유·참조 버전과 함께
   재사용한다는 계약이 없다.
5. **배정 직전 재확인.** 저장과 배정 사이에 정책이 바뀌어도 옛 배정 요청이 그대로
   시작된다.
6. **늦은 결과.** 취소·정책 변경 뒤 도착한 결과를 원래 실행에 귀속시키고 그것만으로
   후속 수정·배정을 만들지 않는 경로가 없다.

또 현재 `set_quality_gate_policy`는 `setting`이 바뀌기만 하면 검사 강도가 같아도
기존 판정을 `needs_recheck`로 내린다. ON/OFF 토글만으로 같은 검사를 다시 돌릴 이유는
없다(gate-operations 5절)는 계약과 어긋나므로 P4-02에서 **강도·계약 변경**과
**단순 토글**을 나눈다.

## 3. 검증 1회 경계

`검증 1회`는 하나의 `quality_gate_run`이다. P4-02는 그 실행을 둘로 나눈다.

- **시작**(`start_quality_gate_run`): 현재 유효 정책의 `revision`·`fingerprint`·
  `inspection_required`를 그 실행에 **고정**하고 `status = 'running'`으로 연다.
  같은 `(case, gate, task_key, subject_key)`에 진행 중 실행이 둘 있을 수 없다.
- **종료**(`complete_quality_gate_run`): 발견에서 판정을 계산하고 `completed`/`blocked`
  로 닫는다. 판정은 **시작 당시 고정한 정책**으로 계산한다 — 중간에 바뀐 현재 정책으로
  다시 계산하지 않는다.

P4-01의 한 번에 적는 `record_quality_gate_run`은 남긴다. 검사가 즉시 끝나는 규칙
게이트는 여전히 그 경로를 쓰고, 그때는 시작·종료가 같은 순간이라 예약할 틈이 없다.

Runner 단절의 정지 경계(**현재 도구 호출 종료**)와 혼동하지 않는다. 진행 중 실행이
단절로 멈춰도 `running` 그대로이고, 그 사실만으로 검증이 끝났거나 예약이 적용됐다고
표시하지 않는다.

## 4. 설정 변경의 예약과 적용

`set_quality_gate_policy`의 판단을 둘로 나눈다.

| 상황 | 처리 |
|---|---|
| 그 범위에 진행 중 검증이 없다 | 즉시 적용. `state = 'current'`, `applied_at = now`, `apply_boundary = 'immediate'` |
| 그 범위에 진행 중 검증이 있다 | **예약.** `state = 'pending'`, `requested_at = now`, `applied_at = NULL`, `apply_after_run_id = 진행 중 실행` |

예약 행은 유효 정책 조회에 **반영되지 않는다.** 조회 응답에 `reserved` 블록으로 따로
붙어 요청 설정·요청 시각·요청자·이유·기다리는 실행을 보여 준다. 예약만으로는
`quality_gate_run.validity`를 건드리지 않고 진행 중 검사도 중단하지 않는다.

종료 시 `complete_quality_gate_run`이 한 트랜잭션에서 이 순서를 지킨다.

1. 현재 결과 보존 — 판정·발견·고정 정책을 먼저 쓴다.
2. 예약 정책 적용 — `apply_after_run_id`가 이 실행인 `pending` 행을 요청 순서대로
   `current`로 올리고 `applied_at`을 적는다. 이전 `current`는 `superseded`다.
3. 적용 효과 계산 — 검사 강도·repair 한도 변경의 효과를 그때 적용한다.
4. 판정이 실패여도 2·3을 수행한다. 게이트 통과만 기다리는 순환을 만들지 않는다.

예약 취소(`cancel_reserved_quality_gate_policy`)는 `state = 'cancelled'`로 남기고
주체·이유·시각을 보존한다. **이미 적용된 것은 롤백하지 않는다.**

적용된 OFF의 효과는 좁다.

- 그 게이트만을 위한 **새 repair 차수 시작이 거부**된다(`start_remediation_attempt`).
- `remediation_cycle` 행·`used_attempts`·발견·실패 판정은 **그대로 남는다.**
- 다시 ON 해도 누적은 초기화되지 않는다. OFF/ON 토글은 `used_attempts`를 건드리지
  않는다.
- 별도 성공 기준의 미충족은 OFF로 사라지지 않는다 — 기존 기준 판정은 이 경로가
  수정하지 않는다.

**needs_recheck를 만드는 것과 만들지 않는 것을 나눈다.** 판정을 내리는 것은
**검사 강도(`inspection`) 변경 하나**다 — 그것만이 "무엇을 보았는가"를 바꾼다.
ON/OFF 토글과 repair 한도 변경은 이미 본 것을 바꾸지 않으므로 기존 판정을 내리지
않는다. 다시 ON 했을 때 현재 입력에 유효한 통과가 남아 있으면 그대로 재사용된다.

> 범위 메모(구현 전 기록): 8절 초안의 AC-8은 repair 한도 변경도 `needs_recheck`로
> 적었으나, 한도는 다음 수정 차수의 허용량이고 이미 끝난 검사가 본 것을 바꾸지
> 않는다. 근거 없는 재실행을 만들지 않기 위해 강도 변경만 판정을 내리는 것으로
> 좁혔고 AC-8을 그에 맞게 고쳤다.

설정은 요청한 범위에만 쓴다. Task 설정이 다른 Task나 Case 전체로 전파되지 않는다.

## 5. 변경 영향과 부분 재검증

새 사건 기록 `quality_change_event`와 실행별 판정 `quality_revalidation`을 둔다.
판정 규칙은 `domain/quality.py`의 순수 함수 `change_impact`다.

| 변경 종류 | 재검증 대상 | 재사용 |
|---|---|---|
| `request` 요청·의도 | 바뀐 기준·의도 참조를 `criteria_refs`/`context_refs`에 가진 실행 | 그 참조가 없는 실행. 이유와 참조 버전을 남긴다 |
| `code` 코드 | 바뀐 저장소·스냅샷 참조를 입력에 가진 실행 | 다른 저장소만 본 실행 |
| `permission` 권한 | 바뀐 권한 범위를 기준·문맥으로 가진 실행 | 그 권한과 무관한 실행 |

**영향 범위를 확인할 수 없으면 재사용으로 추측하지 않는다.** 판정은
`revalidate | reuse | unknown` 셋이고 `unknown`은 재검증 대상이되 "확인 못 함"으로
따로 남는다. 재사용에도 이유·참조 버전을 적는다.

권한 변경은 게이트 예약과 **다른 제어**다. 검증 1회 종료를 기다리지 않고 새 관련
배정을 즉시 막으며, 이미 저장된 판정을 무효화하거나 이미 발생한 외부 효과를 되돌리지
않는다. P4-02는 이 경계를 기록·시험으로 고정하고 새 철회 기계를 만들지 않는다.

## 6. 배정 직전 재확인과 늦은 결과

배정 요청은 기대 정책 상태를 가지고 온다. 요청이 담은 `expected_policy_revision`이
현재 유효 정책과 다르면 새 사유 `quality_gate_policy_changed`로 거부한다 — 옛 배정
요청만으로 시작하지 않는다. 예약(`pending`)만 있는 상태는 **현재 정책을 바꾸지 않으므로
거부 사유가 아니다.**

늦은 결과는 `complete_quality_gate_run`이 다음을 확인해 처리한다.

- 고정한 정책 리비전이 현재와 다르거나, 그 사이 같은 대상의 새 실행이 `current`가
  됐거나, 게이트가 OFF로 바뀌었다 → 결과를 **원래 실행에 저장**하고
  `validity = 'historical'`, `late_result = 1`로 남긴다.
- 늦은 결과는 `remediation_cycle`을 만들거나 차수를 진행시키지 않고, 현재 정책의
  통과로도 쓰이지 않는다.

영향 없는 작업은 멈추지 않는다. 재검증 대상이 아닌 게이트·Task의 배정은 계속 열린다.

## 7. 저장·API·화면

스키마 **v14**.

- `quality_gate_policy` + `requested_at`·`applied_at`·`apply_after_run_id`·
  `apply_boundary`, `state`에 `pending`·`cancelled` 추가, 취소 주체·이유.
- `quality_gate_run` + `started_policy_revision`(v13 이전 행은 **NULL = 미기록**,
  0으로 적지 않는다)·`late_result`.
- 새 표 `quality_change_event`(종류·참조·범위 참조 목록·요약·주체·시각),
  `quality_revalidation`(사건·실행·판정·이유 요약·참조 버전).
- 본문 컬럼은 없다. 참조는 길이·줄·목록 크기를 제한하고 요약은 200자를 넘기지 않는다.

API.

- `POST /api/cases/{id}/quality-gate-runs`에 `open_only` — 진행 중 실행 시작.
- `POST /api/quality-gate-runs/{run_id}/complete` — 종료·예약 반영.
- `DELETE /api/cases/{id}/quality-gates/{gate}/policy/reserved` — 예약 취소.
- `POST /api/cases/{id}/quality-change-events` — 변경 기록과 실행별 판정 반환.
- `GET /api/cases/{id}/quality-gates` 응답에 `reserved`·`revalidation`·`late` 추가.

화면은 적용·예약·재검증 필요·늦은 결과를 **하나로 합치지 않고** 각각 보여 준다.
`요청 시각`과 `적용 시각`을 나란히 적는다.

이행 v13→v14는 기존 `current` 정책에 `applied_at = created_at`,
`apply_boundary = 'immediate'`를 채우고 예약·재검증·late 기록을 **만들지 않는다.**
반복 이행이 멱등이다.

## 8. 성공 기준

| 기준 | 내용 |
|---|---|
| AC-1 | 진행 중 검증이 없으면 설정 변경이 즉시 적용되고 적용 시각이 남는다 |
| AC-2 | 진행 중 검증이 있으면 변경이 예약되고 현재 유효 정책이 바뀌지 않는다 |
| AC-3 | 예약만으로 진행 중 검사가 중단되거나 그 결과가 무효화되지 않는다 |
| AC-4 | 요청 설정·예약 설정·실제 적용 시각이 각각 조회되고 합쳐지지 않는다 |
| AC-5 | 검증 종료 시 현재 결과 보존 → 예약 적용 → 재평가 순서가 지켜지고 실패 판정에서도 예약이 적용된다 |
| AC-6 | 예약 OFF 적용 뒤 그 게이트의 새 repair 시작이 거부되고 기존 실패·발견·누적은 남는다 |
| AC-7 | OFF→ON 토글이 repair 누적을 초기화하지 않고 유효한 기존 통과를 재실행 없이 재사용한다 |
| AC-8 | 검사 강도 변경은 관련 판정을 `needs_recheck`로 내리고, ON/OFF 토글·repair 한도 변경은 내리지 않는다 |
| AC-9 | 설정 변경이 다른 Task·Case 전체로 전파되지 않는다 |
| AC-10 | 예약 취소가 주체·이유와 함께 남고 이미 적용된 정책을 롤백하지 않는다 |
| AC-11 | 요청 변경은 연결된 기준을 가진 실행만 재검증 대상으로 만들고 나머지는 이유·참조 버전과 함께 재사용된다 |
| AC-12 | 코드 변경은 그 저장소를 입력으로 가진 실행만 대상으로 하고 무관한 저장소 증거는 유지된다 |
| AC-13 | 영향 범위 불명은 재사용으로 추측되지 않고 `unknown`으로 기록된 뒤 재검증 대상이 된다 |
| AC-14 | 권한 변경은 검증 종료를 기다리지 않고 새 배정을 막으며 기존 판정·외부 효과를 되돌리지 않는다 |
| AC-15 | 저장과 배정 사이 정책이 바뀌면 옛 배정 요청으로 실행을 시작하지 않는다 |
| AC-16 | 늦은 결과가 원래 실행에 저장되고 `historical`·`late_result`로 남으며 새 repair·배정을 만들지 않는다 |
| AC-17 | 게이트가 OFF인 상태로 늦게 온 통과가 현재 정책의 통과가 되지 않는다 |
| AC-18 | 영향 없는 게이트·Task의 배정은 계속 열린다 |
