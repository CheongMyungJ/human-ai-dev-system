## 1. 현재 구현과 이 작업이 메울 차이

코드를 대조해 확인한 사실이다([DEVELOPMENT.md](../DEVELOPMENT.md) 1.3절의 시작점).

1. **"무엇을 주려 했는가"만 있고 "무엇을 실제로 읽었는가"가 없다.** `run_context_ref` 는
   생성 시점의 계획이다. Runner 의 `load_context` 는 **해시를 대조하지 않고**, 읽음/못 읽음은
   의도·준비 작성 경로에서만 Runner 쪽 반환값과 산출물 본문에 남는다. 논의 응답·QG-01 검토·
   QG-02~07 검토·구현·검증 실행은 요청 원문을 못 읽어도 제어부 기록 어디에도 그 사실이 없다.
2. **필수 입력이 없어도 실행한다.** 제어부는 지시 원문의 가용성만 본다(`create_run`). 고정
   참조는 `pending`·`lost_before_persist` 여도 그대로 넣는다. Runner 는 "읽지 못했다"를 적고
   CLI 를 부른다 — 동의된 의도 없이 설계를, 이전 버전 없이 재작성을, 요청 원문 없이 QG-01
   검토를 한 결과가 성공 산출물로 남는다(P3-01 AC-12 시험이 "읽지 못함 표시 후 실행"을 고정).
   지시 원문이 Runner 에 없으면 원장을 잡은 뒤 예외가 나서 실행이 `assigned` 로 멈춘다.
3. **크기 한도가 없다.** 대화 두 역할은 전부 들어간다(UI-01 인계). 한 실행의 입력 크기를 보지
   않으므로 긴 대화는 CLI 문맥 한계를 넘거나 CLI 내부 압축에 맡겨지고, 그때 무엇이 빠졌는지
   시스템이 모른다(review-context-contract 4절 "압축에만 의존하지 않는다").
4. **stale 표시가 없다.** 실행이 입력을 고정한 뒤 새 피드백·답변·메시지·다른 주체의 새
   의도/준비 버전이 생겨도 실행·결과 어디에도 그 사실이 남지 않는다.
5. **Runner 재시작 시 사용량이 사라진다.** 착수만 기록된 실행은 `unknown` + `not_reported`
   로 보고된다. CLI 원시 출력(`raw/{run_id}.stdout.jsonl`)에 `turn.completed.usage`·
   `result.usage` 가 남아 있어도 읽지 않고, 토큰은 `unresolved(outcome_unknown)` 로 남는다.
   세션 식별자·이벤트도 버려진다.
6. **시작하지 않은 실행이 소비로 잡힌다.** Runner 가 CLI 호출 전에 거부한 실행(실행 경로 없음·
   작업공간 잠금)도 `run_count`·`context_bytes` 가 예약값 그대로 확정된다. `run_count` 의
   계약은 "시스템이 시작한 호출"이다.
7. **새 세션 복원은 구조상 초기화 경로가 없지만 확인한 시험이 없다.** 실행마다 새 CLI
   세션이고 참조는 영속 기록에서 다시 구성된다. 실패·불명 뒤 새 실행이 repair 차수·누적
   예산·미해결 질문·Profile 판·P4-03 완료 계약을 그대로 잇는지를 한 흐름으로 본 시험이 없다.

## 3. 설계

### 3.1 문맥 등급과 인라인 한도

- **등급은 역할에서 나온다**(순수 규칙, `domain/context.py`). 지시 원문은 언제나 핵심이다.
  - **핵심**: `original_request`·`agreed_intent`·`previous_intent`·`previous_design`·
    `current_design`·`previous_plan`·`current_plan`·`feedback`·`question_answer`·
    `conversation_user_message`. 요청·결정·명시 금지·동의 범위·사람의 답과 피드백, 그리고
    재작성의 이전 버전(없으면 처음부터 다시 쓴다 — P2-04 퇴화)이다.
  - **보조**: `conversation_assistant_message`. AI 의 이전 제안이며 사용자의 결정이 아니다
    (D-60·UI-01).
  - 모르는 역할은 **핵심으로 취급**한다 — 모르는 것을 생략 가능으로 읽지 않는다.
- **실행당 인라인 한도**(`context_inline_limit_bytes`, 제어부 설정, 기본 **256 KiB**). 이 값은
  상세 설계 제안값이며 사용자 확정 정책이 아니다. 환경 변수 `HADS_CONTEXT_INLINE_LIMIT_BYTES`
  로 바꾼다. **적용한 한도를 실행에 기록한다**(`run.context_inline_limit`).
- 크기는 `artifact_ref.byte_size` 로 잰다(제어부가 아는 값). 패키지 = 지시 원문 + 인라인 참조.
  1. 전부 한도 안이면 **전부 인라인** — 참조 목록·순서가 지금과 같다.
  2. 넘으면 **보조만, 오래된 것부터** 생략해 한도 안으로 맞춘다. 최근 제안이 지금 논의에 더
     가깝기 때문이다. 생략은 참조 행(`inclusion = omitted_size_limit`)·조회·지시문에 남는다.
  3. 지시 + 핵심만으로 넘으면 **진입 보류**(`context_over_inline_limit`). 핵심을 자르지 않는다
     (review-context-contract 4절 1항 "조용히 삭제하지 않고 분할하거나 의존 작업을 보류").
     거부 사유에 크기·한도와 "나누거나 한도를 조정해야 한다"를 적는다.
- 예약 `context_bytes` 는 **인라인 패키지 크기**다(생략분 제외). 이 지표의 계약이 "제어부가
  만들어 전달하는 입력 패키지"이기 때문이다. 진입 검사·생성·재배정이 같은 계산을 쓴다.

### 3.2 진입 검사 — 핵심 참조의 서버 가용성

- 인라인 핵심 참조의 `artifact_ref.availability` 가 `available` 이 아니면
  (`pending`·`runner_offline`·`lost_before_persist`) `required_context_unavailable` 로 거부한다.
  사유에 역할·참조·가용성을 적는다. 저장 대기(`pending`)는 곧 풀리는 보류이고, 유실은 다시
  보내거나 그 입력을 정리해야 풀린다 — **입력을 빼고 실행하지 않는다.**
- 보조 참조의 가용성은 진입을 막지 않는다(Runner 가 누락으로 보고하고 실행은 `partial`).
- 지시 원문 가용성 검사는 기존 그대로다.

### 3.3 실행 문맥 영수증 — 실제로 읽은 것

- 배정에 지시 원문의 해시(`instruction_content_hash`)와 참조별 등급·인라인 여부·해시를 싣는다.
- Runner 는 **원장을 잡은 뒤, CLI 를 부르기 전에** 지시·참조를 자기 저장소에서 읽고 해시를
  대조한다. 참조별 상태: `read`(해시 일치) · `missing`(없음) · `hash_mismatch`(다른 내용) ·
  `omitted`(제어부가 인라인하지 않기로 정함, 읽지 않음). 해시가 다른 본문은 **읽지 못한 것**
  으로 다루고 지시문에 넣지 않는다.
- `POST /api/runner/runs/{run_id}/context-receipt` 로 보고한다. **본문·경로가 없다** — 순번·
  역할·상태뿐이다. 같은 세대의 같은 영수증은 멱등(200), 다른 내용은 409, 옛 세대는 409,
  모르는 순번·제어부가 인라인으로 정한 참조의 `omitted` 는 409 다(Runner 가 핵심을 생략으로
  주장하지 못한다).
- **실행 문맥 상태**(도출, 저장하지 않음): `complete`(전부 읽음) · `partial`(핵심은 전부 읽음,
  보조 일부 생략·누락) · `blocked`(지시 또는 핵심 누락·불일치) · `not_reported`(영수증 없음 —
  P4-04 이전 실행). 계획(인라인 크기·생략 수·한도)과 함께 조회된다.

### 3.4 Runner 사전 중단과 시작하지 않은 실행

- 지시 원문 또는 **핵심** 참조가 `missing`·`hash_mismatch` 면 Runner 는 **CLI 를 부르지 않고**
  (부수효과 0) 실행을 `failed` + `residual_activity = none` +
  `not_started_reason = required_context_unavailable` 로 보고한다. 원장에 그 결과를 확정해
  재배정이 와도 같은 결과를 다시 보낸다. P3-01 AC-12 시험의 의미를 "핵심 누락 → 미실행,
  보조 누락 → 읽지 못함 표시로 실행"으로 바꾼다(검사를 지우지 않는다).
- **보조**만 누락이면 실행하고 지시문에 "읽지 못함"을 적는다(기존 표시). 생략분은 "크기 한도로
  이 실행에 넣지 않았다"로 적는다. 둘 다 "추측해 채우지 마라"가 붙는다.
- **시작하지 않은 실행의 정산.** `not_started_reason` 이 있는 결과는 `outcome = failed` 이고
  잔류 `none` 일 때만 받는다. 실행 수·검토 수·문맥 크기·실행 시간을 **0 으로 확정**
  (`settle_source = not_started`)하고 토큰·비용 행을 만들지 않는다. 기존 사전 거부 두 경로
  (`refused_no_execution_path`·`refused_workspace_busy`)도 같은 표시를 보낸다
  (`no_execution_path`·`workspace_busy`). 시작한 실행의 정산은 바뀌지 않는다.

### 3.5 문맥 최신성 — stale 표시

- **drift = (지금 구성하면 들어갈 참조) − (고정한 참조) − (그 실행 자신이 만든 산출물).**
  제거·해결은 보지 않는다 — 실행이 피드백을 반영해 해결하면 그 피드백이 빠지는 것이 정상이다.
  추가만 본다: 실행이 **보지 못한** 새 입력이다(새 피드백·새 답변·카드 답변 메시지·다른 주체의
  새 의도/준비 버전·저장 대기였다가 저장된 메시지).
- 자기 산출물: 실행 출력 원문, 그 실행이 쓴 의도 버전·준비 산출물(`author_run_id`).
- **결과 보고 시점에 한 번 계산해 저장**한다(`run.context_freshness_json`). 진행 중 실행은
  조회 시점으로 도출한다. 끝난 지 오래된 실행을 "지금과 다르다"로 표시하지 않는다.
- 최신성은 **표시**다. 결과·판정·게이트 유효성을 바꾸지 않는다 — 판정의 재검증은 P4-02 의
  변경 사건·참조 대조가 맡는다. 새 차단 조건을 만들지 않는다.

### 3.6 Runner 재시작의 사용량 복구

- 원장에 착수만 있는 실행을 다시 받으면(기존: `unknown` + `not_reported`) **CLI 를 다시 부르지
  않고** 원시 출력 `raw/{run_id}.stdout.jsonl` 을 배정의 도구로 정규화해 사용량·세션 식별자·
  이벤트를 복구한다. 결과는 **`unknown` 그대로**다 — 산출물 생성·작업공간 관측·결과 보고가
  끊겼기 때문이다. 잔류 활동도 `unknown`.
- 사용량에 `recovered_from = runner_raw_log` 를 붙여 보내고 토큰·비용은
  `settle_source = recovered_from_runner_log` 로 확정한다. 실행 시간은 여전히 `unresolved`.
  원시 출력에 사용량이 없으면(강제 종료 로그) 지금처럼 미제공이다. 원시 출력이 없으면 지금과
  같다. 복구 결과는 원장에 확정해 다음 재배정에도 같은 값을 보낸다.
- 실제 CLI 원시 출력(P1 증거로 커밋된 codex·claude `stdout.jsonl`, 강제 종료 로그 포함)을
  시험 입력으로 쓴다.

### 3.7 새 세션 복원

새 코드 경로를 만들지 않고 **보존을 시험으로 고정**한다. 불명·실패 뒤 같은 목적의 새 실행이
영속 기록에서 같은 핵심 참조를 받고, repair 차수·누적 예산(복구된 사용량 포함)·미해결 질문·
Profile 판·P4-03 완료 계약(목적 의무·결론 요구)이 초기화되지 않는다. 부분 복원(Runner
저장소에서 일부 원문이 사라지거나 다른 내용으로 돌아옴)은 그 원문에 기대는 실행만 멈추거나
`partial` 로 만들고 다른 실행은 영향이 없다.

### 3.8 조회·화면

- `GET /api/runs/{id}`·Case 조회의 실행 목록에 `context`(상태·계획·영수증 요약·최신성).
- `GET /api/runs/{id}/context-refs` 가 참조별 등급·인라인·크기·서버 가용성·영수증 상태를 보인다.
- 진입 거부는 기존 모양(`refusals`·`reasons`)이다.
- 관리 화면: 실행 표에 **문맥** 열(완전 / 부분(생략 n·누락 n) / 실행 전 중단 / 미보고, 입력 이후
  새 입력 표시). 문맥 역할 표지를 보강한다. 새 화면은 만들지 않는다.

### 3.9 넣지 않는 것 — 분할 검토·체크포인트·단계적 조회

- **분할 검토 실행**(같은 기준 버전의 하위 검토와 통합 검토)과 **검토 체크포인트**는 넣지 않는다.
  지금 제어부가 고정해 넣는 문맥(요청·의도·준비·피드백·대화)은 하나의 의도·준비 문서와 대화라
  나눌 대상이 아니고, 큰 대상(큰 diff)은 CLI 가 작업공간에서 직접 읽는다. 하위 검토를 게이트
  판정에 합치려면 P4-01/02 의 판정·repair·늦은 결과 모델을 함께 바꿔야 한다. 실제로 큰 대상
  검토가 필요한 작업에서 별도 plan 으로 다루고 인계에 남긴다. 이 작업은 그 전제(핵심을 자르지
  않고 보류, 읽지 않은 범위를 완료로 적지 않음)를 만든다.
- **단계적 조회**: 생략한 보조 자료를 CLI 가 필요할 때 읽게 하는 경로는 CLI·권한 모드별
  실증이 필요하다. 지금은 생략 사실과 참조 ID 만 지시문에 적는다.

스키마 **v17**. 새 표 하나와 컬럼 다섯.

표시). 예산·판정·Profile 판을 바꾸지 않는다. 반복 이행이 멱등이다.

## 10. 구현 중 plan 에서 바꾼 것

- **영수증 시점.** 3.3절은 "원장을 잡은 뒤, CLI 를 부르기 전에"로 적었다. 영수증 보고가
  유실되면 CLI 를 부르지 않은 실행이 원장의 착수 기록 때문에 다음 재배정에서 결과 불명으로
  보고된다. **원장을 잡기 전**으로 옮기고 원장에 이미 있는 실행은 다시 읽지 않게 했다(시험
  `test_a_lost_receipt_report_claims_nothing_and_the_run_is_not_reported_unknown`).
- **영수증을 보낸 Runner 확인.** 배정된 Runner 가 아닌 곳의 영수증을 409 로 거부한다(3.3절에
  없던 검사). 다른 Runner 의 저장소 상태를 이 실행의 읽음으로 적지 않기 위해서다.
- **한도 설정 검증.** 0 이하의 한도는 모든 실행을 보류시키므로 제어부 기동 시 거부한다.
- **실제 CLI 횟수.** 6절 7항은 논의 응답 1~2회로 적었다. 생략을 만들려면 앞선 AI 응답이
  있어야 하므로 A·B 두 번으로 문맥을 쌓았고, 재시작 복구를 실제 강제 종료로 보려고 D 를
  더했다 — codex 호출 4회(2회차), 1회차 포함 8회.
- **기존 이행 시험의 판 고정.** v15→v16 시험의 `SCHEMA_VERSION == 16` 을 `>= 16` 으로 바꿨다
  (6절 "기존 시험이 새 규칙과 충돌하면 의미를 검토해 고친다").
