# P3-PLAN-04

수직 통합. 기준: 설계 v0.7 / D-01~67 / 2026-09-22.
선행: P3-R4 완료(스키마 v11, pytest 395 + P1 계약 18 통과). 다음: [P4 품질·여섯 업무·지식](../DEVELOPMENT.md).

## 1. 이 작업이 답해야 하는 것

R1~R4는 네 축의 강제를 하나씩 붙였다. **각 축은 자기 시험과 자기 라이브로 확인됐지만,
한 업무가 처음부터 끝까지 그 넷을 모두 지나간 적은 없다.** R4의 라이브조차 축별로 잘린
Case 였다 — controlled 를 본 Case 와 Fast Lane 을 본 Case 와 자동 완료를 본 Case 가
서로 다르다. P3-04가 그 조각들을 한 줄로 잇는다.

아직 보지 않은 것이 셋이다.

1. **`deep + ask-on-decision`.** R1은 WorkDepth 와 Autonomy 가 다른 축이라고 했고 R4가
   그 조합을 실제로 가능하게 만들었다(깊이는 준비를 늘리고 Autonomy 는 확인 지점을
   정한다). **그렇게 도는 것은 아직 보지 않았다.** 지금까지의 라이브는 `simple`+Fast
   Lane 이거나 `controlled` 였다.
2. **같은 Runner 위 두 저장소를 *함께 바꾸는* 업무.** R2는 두 작업공간을 만들고 실제
   codex 가 지정한 쪽에서 도는 것까지 봤지만, 그것은 **읽기 실행 두 건**이었다. 두
   저장소를 모두 바꾸고 그 둘이 서로 맞아야 끝나는 기능은 아직 없었다.
3. **controlled 와 예산 도달이 *실제 기능 흐름 안에서* 사람을 기다리는 모습.** R3·R4는
   조건을 만든 직후에 그 조건 하나만 찔러 확인했다. 기능이 진행되는 도중에 걸리면
   무엇이 멈추고 무엇이 계속되는지는 다른 질문이다.

그리고 이 흐름을 실제로 돌리면 드러날 구멍 하나를 **이미 알고 있다.**

> **Task 는 자기 저장소를 모른다.** `task` 표에 `repository_id` 가 없다.
> 실행의 대상 저장소(`run.repository_id`)와 그 실행이 수행한다는 Task(`run.task_id`)가
> 서로를 검사하지 않으므로, 두 저장소 Case 에서 **UI 작업을 한다면서 API 저장소를
> 고치는 실행**이 조용히 통과한다. 진입 검사는 "대상이 기록됐는가"만 보고 "그 대상이
> 맞는가"는 보지 않는다.

설계는 이미 그것을 요구한다 — "**Task·Run이 사용하는 Repo와 작업공간을 명시한다**"
(execution-workspace-review 19행). 새 제품 판단이 아니라 미구현이다.

**이 작업의 방법은 순서가 중요하다.** 먼저 고치고 나서 돌려 보는 것이 아니라,
**먼저 끝까지 돌려 보고 막히는 자리를 입력으로 삼는다.** 수직 통합에서 값어치 있는
것은 코드가 아니라 "실제로 어디서 끊기는가"이며, 미리 고친 것은 그 관측을 지운다.
R4의 라이브가 결합 기록 지시문의 구멍을 찾은 것도 같은 순서에서였다.

## 3. 실제로 돌릴 세 경로 — 이 작업의 중심 표

한 Case 는 두 경로를 동시에 탈 수 없다(R4 결과 5절). Autonomy 가 다르면 다른 Case 다.

| 경로 | Autonomy | 무엇을 보는가 | 사람이 하는 일 |
|---|---|---|---|
| **A. 기본 자율** | `ask_on_decision` | `deep` 수준, 설계+계획 두 산출물, 독립 의미 검토, 두 저장소 구현·검증, 조합, 자동 완료 | **요청과 의도 동의 둘뿐** |
| **B. controlled** | `controlled` | 시작 확인 대기 → 진행 → 결과 후보 확인 → 종료 | 시작 확인·의도 동의·결과 확인 |
| **C. 예산 도달** | `ask_on_decision` | 진행 중 `run_count` hard 도달 → 새 배정 거부 → 한도 상향 → 재개 | 한도 변경 하나 |

### 3.1 경로 A 가 답하는 것

`deep` 은 **준비를 늘리고** `ask_on_decision` 은 **확인 지점을 정한다.** 두 축이
섞이지 않는다는 것이 실제로 이런 모습이어야 한다.

```
수준 deep          → 설계 산출물 + 계획 산출물 두 건이 필수 (Fast Lane 아님)
                   → 결합 기록으로는 통과하지 않는다
                   → QG-01 은 independent 필수 (level_above_simple)
ask_on_decision    → 설계·계획의 사람 검토는 없다 (stage_review = auto_proceed)
                   → 조건 충족 시 사람 인수 없이 완료
```

**여기서 깨질 수 있는 것이 정확히 무엇인지 적어 둔다.** 만약 `deep` 인데 사람 검토를
요구하면 Autonomy 가 깊이에 오염된 것이고, `ask_on_decision` 인데 결합 기록 하나로
통과하면 Fast Lane 판정이 Autonomy 에 오염된 것이다. 둘 다 R1의 분리가 말뿐이었다는
뜻이 된다.

## 4. 구현할 것

### 4.1 Task ↔ Repository (스키마 v12)

```
task.repository_id  TEXT NULL REFERENCES project_repository(id)   ← 새 컬럼
```

**NULL 은 미기록이다.** v12 이전에 만들어진 Task 와, 저장소가 하나뿐이어서 말할 필요가
없던 Task 가 그 값을 갖는다. 유도해 채우지 않는다 — 작업공간이 하나뿐이라는 이유로
그 저장소를 적으면, 나중에 저장소가 늘었을 때 "계획이 그렇게 정했다"는 기록이 된다
(D-62 "유도해 채우지 않는다", R2의 `implicit_single_repository` 와 같은 자리).

| 층 | 무엇을 더하는가 |
|---|---|
| 계획 산출물 | `tasks[].repository` — 저장소 **이름 또는 id**. 없으면 미기록 |
| 제어부 해석 | 그 Case 의 **선택된** 저장소 중에서만 해석한다. 선택 밖 이름은 허용 확대 요구이며 R2가 이미 거부하는 것과 같다 |
| 해석 실패 | 조용히 버리지 않는다. `task_repository_unresolved` 로 남기고 그 Task 를 **미기록으로 취급**한다(`task_block_unresolved` 와 같은 이유) |
| 진입 검사 | `run_task_repository_mismatch` — 실행의 대상 저장소가 Task 가 기록한 저장소와 다르면 거부 |
| 진입 검사 | `task_repository_not_recorded` — **저장소가 둘 이상인 Case 의 새 그래프에서만** 구현·검증을 막는다 |
| 화면 | 작업 그래프가 Task 별 저장소를, 미기록이면 미기록임을 보인다 |

**마지막 두 줄의 조건이 소급 금지의 자리다.** `task_repository_not_recorded` 를 모든
Case 에 걸면 R2 이전 Case 와 단일 저장소 Case 의 진행 중 업무가 멈춘다. 저장소가 둘
이상인 Case 는 R2 이후에만 있고, 그 Case 에서 Task 가 저장소를 말하지 않는 것은 계획이
덜 된 것이다 — 이 작업이 처음 만드는 상황이므로 소급이 아니다.

**왜 거부가 필요한가.** 기록만 하고 검사하지 않으면 R1이 Autonomy 에서 했던 실수를
반복하는 것이다 — 값은 있는데 아무 것도 막지 않으면, 두 저장소 Case 에서 "UI 작업을
한다면서 API 저장소를 고치는 실행"이 통과하고 그 변경은 **다른 Task 의 검증에** 섞여
들어간다. 실행 전후 대조가 우리가 가진 유일한 증거인데 그 대조가 엉뚱한 Task 에 붙는다.

### 4.2 이행(v11→v12)에서 소급하지 않는 것

| 대상 | v12 이후 | v12 이전에 만들어진 것 |
|---|---|---|
| 기존 `task` 행 | 계획이 말하면 기록 | `repository_id = NULL`(미기록). **작업공간에서 유도해 채우지 않는다** |
| 기존 작업 그래프 리비전 | 그대로 | 그대로. 재계산하지 않는다 |
| 진행 중 Case 의 실행 | 새 검사 | 저장소가 하나면 아무 것도 달라지지 않는다 |
| 기존 `run.repository_id` | 그대로 | 그대로. 옛 NULL 의 해석 규칙(§9 한계표)도 그대로 |

### 4.3 다중 Repo 통합은 **드러내되 강제하지 않는다**

R2가 이미 `code_composition.covers_all_code_repositories` 와 통합 미검증 표시를 만들었다.
P3-04는 실제 두 저장소 흐름에서 **그것이 맞게 나오는지 확인**하고 화면에 드러낸다.

**기준 판정의 전제로 강제하지 않는다.** "영향받는 회귀·권한·성능·다중 Repo 통합"은
case-profiles 4절의 **조건부 추가 증거**이며, 어떤 증거가 필요한지를 판정하는 것은
P4-01 게이트의 몫이다. 여기서 강제를 만들면 P3-04가 Profile 별 증거 규칙을 선점한다.

### 4.4 라이브가 드러내는 것

**새 지시문을 만들면 실제 CLI 로 한 번 돌려 본다**(R4가 남긴 교훈). 이 작업은 새
지시문을 거의 만들지 않지만, 구현·검증 지시문에 **대상 저장소와 계약 상대**가
들어가야 하는지는 실제로 돌려 봐야 안다 — 한 실행은 자기 작업공간만 보므로, 소비자
저장소를 고치는 실행은 생산자의 새 계약을 **직접 읽을 수 없다.**

그것을 지금 바꾸지 않는다(10절). 대신 계획 산출물이 계약을 문서로 고정하는 것으로
충분한지를 **관측하고 사실로 적는다.**

## 5. 작업 순서

1. **라이브 하네스부터 만든다.** 실제 git 저장소 두 개(사용자 미커밋 변경을 남긴 채),
   제어부·Runner 를 별도 프로세스로. 실행 id 에 시도마다 달라지는 값을 붙인다
   (R4 6.5의 멱등성 함정)
2. **경로 A 를 구현 전에 끝까지 돌려 본다.** 막히는 자리·어긋나는 자리를 전부 적는다.
   이것이 3~4번의 입력이다
3. Task ↔ Repository: 스키마 v12 + 이행 + 계획 문서 필드 + 해석 + 두 거부 사유 + 화면.
   **v11 DB 로 실제 이행 시험부터 만든다**(R2·R3·R4와 같은 방식)
4. 2번이 드러낸 결함 수정과 회귀 시험. 지시문을 고쳤으면 **실제 CLI 로 재실행**
5. 경로 A 재실행 — 자동 완료까지
6. 경로 B(controlled) 라이브
7. 경로 C(예산 도달) 라이브
8. 경계·회귀: 두 저장소 dirty 보존, 데이터 경계 바이트 검사, 제어부 강제 종료 후 복원,
   material delta 가 의존 Task 를 막는 경계
9. 전체 시험·`npm run build`·증거 정리(`p3/evidence/P3-04-*`)와 인계 갱신

## 6. 성공 기준 (AC)

| # | 기준 | 검증 |
|---|---|---|
| AC-1 | 두 저장소를 모두 쓰기 허용한 Case 에서 저장소별 worktree 가 따로 준비되고, **두 저장소의 사용자 미커밋 변경이 전 과정 뒤에도 시작 때와 같다** | 라이브 `git status --porcelain` 전후 |

- **자동 시험:** 기존 395 + P1 계약 18 을 유지하면서 위 AC 마다 시험을 더한다. 기존
  시험이 v12 이전 가정을 고정했다면 **지우지 않고** 의미를 검토해 바꾸고 짝이 되는
  보존 시험을 남긴다.
- **이행 시험:** 커밋 이력의 v11 스키마로 실제 DB 를 만들어 올린다(`_v11_schema()`).

  재실행해 확인한다(R3·R4가 같은 자리에서 확인했다).
- **라이브:** 실제 제어부·Runner 프로세스, 실제 git 저장소 둘, **실제 codex**. 세 경로.
  종료 코드가 아니라 실제 기록(조합·판정·인수·예약)을 본다.
- **재시작 복원:** 제어부를 실제로 강제 종료하고 본다.
- **화면:** `npm run build` 와 실제 패널 확인(작업 그래프의 저장소, 조합의 통합 상태).
- **경계·회귀:** 두 저장소 dirty 보존, 데이터 경계 바이트 검사, 예산·저장소 검사 우회
  없음.

**하지 않은 시험을 통과로 적지 않는다.** 외부 push·PR·CI 는 이 작업에 없고, 계약
시험과 미검증을 구분해 결과 문서에 남긴다.

## 8. 복구·인계

- 스키마 v12는 **컬럼 하나**다. 기존 컬럼을 바꾸지 않으며 이행 전 DB 사본을 남긴다.
- 이행이 실패하면 `task.repository_id` 가 없고 두 거부 사유는 동작하지 않는다.
  **반쯤 적용된 검사를 "검사한다"로 표시하지 않는다.**
- 라이브 데이터는 `%LOCALAPPDATA%\Temp\hads-p3-04-live` 에 두고 저장소 `var\` 를
  건드리지 않는다. **이 설계 저장소를 CLI 에 쓰기로 노출하지 않는다**(P3-03과 같다).
- 시험 대상 git 저장소는 임시 경로에 새로 만들고 원격을 붙이지 않는다 — 원격이 없으면
  실수로도 push 가 일어나지 않는다.
- 외부 쓰기(push·PR·이슈)는 이 작업에 없다. 커밋·push 는 사용자 확인 뒤에만 한다.
- **P4 는 READY 로 인계하고 착수하지 않는다.**

## 10. 남은 위험

- **한 실행이 한 작업공간만 본다는 것이 실제로 문제일 위험.** 소비자 저장소를 고치는
  실행은 생산자의 새 계약을 **직접 읽을 수 없고** 계획 산출물의 요약에 의존한다. 그
  요약이 부족하면 두 저장소가 어긋난 채 각자의 검증을 통과할 수 있다. 이것이 드러나면
  **결함이 아니라 관측 결과로 적고** 처리 위치를 정한다 — 여기서 실행 모델을 바꾸는
  것은 R2의 재설계다.
- **라이브가 찾는 것이 지시문 문제일 위험.** R4 6.1과 같은 자리다. 자동 시험은
  `FakeCliExecutor` 가 언제나 올바른 형식을 내므로 지시문의 구멍을 볼 수 없다.
- **Task↔Repo 검사가 옛 Case 를 막을 위험.** 조건을 "저장소 둘 이상 + 새 그래프"로
  좁히는 것이 그 방어다. 넓히면 소급이 된다.
- **경로 A 가 사람 없이 끝까지 가지 못할 위험.** 그러면 그 자리가 이 작업의 결과다 —
  "명확한 기능의 추가 사람 호출 없음"이 지켜지지 않는 지점을 **덮지 않고 적는다.**
- **실제 codex 가 계약 기능을 못 만들 위험.** 그 경우도 제품 결함과 CLI 능력의 한계를
  구분해 적는다. 실패한 실행을 성공으로 바꾸지 않는다.

## 11. 사람에게 물어야 할 것 — 실제 시험 기능

인계가 이 선택을 P3-04 plan 으로 지정했다(DEVELOPMENT.md 5절, S-014 인계).

**무엇을 고르든 공통인 것:** 임시 git 저장소 두 개(원격 없음), 같은 Runner, 사용자
미커밋 변경을 남긴 채 시작, 각 저장소에 실제로 도는 테스트. 세 경로(A·B·C)는 같은
요청을 서로 다른 Case 로 돌린다.

| 안 | 시험 기능 | 왜 이것인가 | 약한 곳 |
|---|---|---|---|
| **A. 생산자→소비자 계약 변경** (Profile `feature`) | 저장소 1의 요약 함수가 결과에 항목 하나를 더하고, 저장소 2가 그것을 읽어 표시한다 | **두 저장소가 서로 맞아야 끝난다.** 영향 축이 둘 이상이라 수준이 `deep` 으로 나오기 쉽고 `deep + ask-on-decision` 확인에 맞는다. "실제 작은 기능 개발"의 글자 그대로 | 계약이 단순해서 CLI 가 쉽게 맞출 수 있다 — 10절의 첫 위험이 안 드러날 수 있다 |
| **B. 두 저장소에 걸친 결함 수정** (Profile `defect_fix`) | 저장소 2에서 드러나는 증상의 원인이 저장소 1에 있다. 재현 → 수정 → 회귀 | `not_reproduced`·`already_satisfied` 구분과 Profile 별 완료 의미를 함께 본다 | 조사 성격이 커서 **설계·계획·구현**의 기능 경로를 덜 밟는다. 수준이 `simple` 로 나오면 `deep` 조합을 못 본다 |
| **C. 공용 유틸 추출** (Profile `refactoring`) | 두 저장소의 중복 함수를 한쪽으로 모으고 공개 동작을 보존한다 | 보존 조건 검증이 중심이라 회귀 증거가 선명하다 | 새 동작이 없어 "기능 개발"이 아니고, 성공 기준이 "테스트가 여전히 통과"로 쏠린다 |

## 12. 수정 기록

### 해석된 뒤에도 **계획이 적은 문자열을 남긴다** (4.1절)

계획 4.1절은 해석 실패만 `repository_ref` 에 남기는 것으로 적었다. 구현하면서
해석 성공에도 남기기로 바꿨다.

이유는 조회의 두 소비자가 다른 것을 묻기 때문이다. 진입 검사는 "무엇으로
해석됐는가"를 묻고 화면은 "계획이 무엇이라고 적었는가"를 묻는다. 해석 성공에
원문을 지우면 두 번째 물음에 답할 수 없고, 나중에 저장소 이름이 바뀌었을 때
"계획이 그때 무엇을 가리켰는가"가 사라진다. 지문·요약을 본문과 함께 남기는 규칙과
같은 자리다.

### 대조는 **실행이 밝힌 대상**으로 한다 (4.1절)

처음 구현은 대상 저장소를 `workspace_state` 에서 끌어냈다. 그러면 구멍이 하나
생긴다 — **준비되지 않은 저장소를 대상으로 적은 요청**은 작업공간이 없어
`repository_id` 가 비고, 그래서 대조가 조용히 건너뛰어진다.

그 경우에도 "이 Task 의 저장소가 아니다"는 사실이며, 사람이 고쳐야 하는 것도
다르다 — 작업공간을 준비하는 것이 아니라 대상을 바로잡는 것이다. `AdmissionRequest`
에 `run_repository_id` 를 두어 **요청이 밝힌 값**을 그대로 보게 했고, 짝이 되는
시험(`test_the_mismatch_is_caught_even_without_a_prepared_workspace`)이 두 사유가
함께 보이는 것을 고정한다.

### 계획이 저장소를 말하려면 **계획을 쓰는 실행이 그 목록을 알아야 한다** (4.4절)

계획 4.1절은 계획 산출물에 `tasks[].repository` 를 더한다고만 적었고, **그 이름을
누가 아는가**는 정하지 않았다. 라이브 준비 중에 그것이 실제 문제로 드러났다.

Project 를 만들면 등록 저장소가 `primary` 라는 이름으로 자동 생성된다. 사람이
부르는 이름(디렉터리 이름 `repo-core`)과 다르고, 요청 원문에도 후자가 적혀 있다.
계획을 쓰는 실행에게 목록을 주지 않으면 **요청 원문에 있는 이름을 그대로 적게**
되고, 그 이름은 이 Case 의 선택 안에서 해석되지 않아 그 Task 가 막힌다. 새 검사가
계획을 실수로 몰아가는 모양이다.

그래서 배정이 `case_repositories`(이름과 식별자뿐)를 싣고 계획·결합 기록 지시문이
그 목록만 보여 준다. **Runner 가 저장소를 찾아 나서지 않는다** — 찾아 나서면 이
Case 가 고르지 않은 저장소를 계획에 적게 되고 그것은 허용을 넓히는 요구가 된다
(D-38·D-63). 고를 것이 하나뿐이면 규칙을 아예 넣지 않는다 — 고를 것이 없는데
고르라고 하면 이름을 지어낸다.

### 두 저장소 Case 의 기존 시험이 **계획에 저장소를 적게** 바뀌었다 (7절)

`tests/{test_repositories,test_data_boundary}.py` 의 세 시험이 두 저장소를 고른 채
저장소를 말하지 않은 계획으로 구현을 요청하고 있었다. v12 에서 그것은 정확히
`task_repository_not_recorded` 이며, 시험이 고정하던 것은 "두 저장소 Case 에서
아무 Task 로나 구현이 열린다"였다.

**지우지 않고** `_prepare_both(task_repository=...)` 로 계획이 저장소를 말하게
바꿨고, 말하지 않았을 때의 거절은 `tests/test_task_repository.py` 가 짝으로
고정한다. 단일 저장소 Case 의 시험은 손대지 않았다 — 그 Case 에서는 아무 것도
달라지지 않는 것이 이 단계의 계약이다.
