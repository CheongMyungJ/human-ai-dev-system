## 0. 제품 판단 — 새로 내리지 않는다

이 plan 이 정하는 것은 **화면의 자리와 기술 선택**이며 D-80·D-67 안이다. 사용자에게 물을 것으로 인계에 남긴
두 항목의 답은 아직 없다 — (1) 참고 후보의 자동 활성화 조건: **그대로 없음**(가장 좁은 쪽, S-027 과 같다).
(2) UI-04 첫 하위 plan 의 범위: S-027 인계의 제안(결정 사항 패널·프로젝트 규칙 화면)을 **그대로** 잡는다 —
P4-06·07 이 남긴 후보·채택 확인의 새 화면 자리를 먼저 채우는 것이 지식 흐름을 끝까지 잇는 순서이고, 다른
하위 범위(검색·설정·알림)는 이것에 의존하지 않는다. 다른 범위를 먼저 원하면 다음 세션이 바꾼다.

화면 배치의 상세 선택(제품 정책이 아니다, 9절에도 적는다):

- **"프로젝트 규칙" 의 자리.** 설계는 "프로젝트 설정의 프로젝트 규칙" 이지만 새 화면에 프로젝트 설정 화면이
  아직 없다(상세 설정은 뒤 하위 plan). 왼쪽 목록의 프로젝트 자리에 `프로젝트 규칙` 진입을 두고 가운데를
  그 화면으로 바꾼다(`?project=…&screen=rules`). 프로젝트 설정 화면이 생기면 그 안으로 옮긴다.
- **수동 등록의 출처.** 지식 등록 API 는 출처 대화(`case_id`, 본문의 소유 Case)를 요구한다(P4-06b 서버 본문도
  `artifact_ref.case_id` 로 그 Case 에 속한다). 프로젝트 규칙 화면의 등록 폼은 **출처 대화를 고른다**(이
  프로젝트의 대화 목록, 기본값 = 마지막으로 연 대화). 대화 없이 등록하는 경로는 만들지 않는다 — 출처 없는
  규칙을 만들지 않는다는 등록부 계약(project-knowledge 1절 "출처가 있고") 그대로다.
- **변경은 프로젝트 규칙 화면에서만.** 결정 사항 패널은 이 대화의 것을 **보고 이동**하는 자리다(D-80 "대화의
  결정 사항에서 … 보고, 프로젝트 설정의 프로젝트 규칙에서 확인·변경"). 대화 카드의 무효화(P4-06)는 그대로
  둔다.

## 1. 현재 구현과 차이 (코드 대조)

1. **결정 사항 패널은 UI-03 의 목록이다.** `web/src/shell/ReviewPanel.tsx` 의 `Decisions` 가 업무화·`decision`
   행(종류 코드·대상 id 그대로)·답한 질문·AI 해석·진행 이력을 보이고 "프로젝트 공통 규칙·지식은 이후 작업
   (P4-06·UI-04)이다" 로 끝난다. 목표·기준(의도 최신 버전·기준 판정), 이 대화에서 정한 규칙·후보, 이 업무에
   **적용된** 규칙(Manifest)이 없다. 결정 행의 대상(의도 버전)을 여는 길·근거 메시지로 가는 길이 없다.
2. **프로젝트 규칙 화면이 없다.** 등록부는 관리 화면 `?view=admin` 의 `KnowledgePanel` 에만 있다(등록·채택
   확인·활성화·무효·충돌). 새 화면의 후보·제안·등록 카드는 전부 관리 화면으로 링크한다(`ProgressCards.tsx`).
   개정(`POST /api/knowledge/{id}/versions`)은 API 만 있고 화면이 없다.
3. **원래 대화·근거로 이동이 없다.** `knowledge_view` 의 버전에는 `source_case_id`·`source_message_id`·
   `source_run_id` 가 있지만 대화 제목·메시지 순번이 없고, 새 화면은 주소로 대화만 연다(`?project&case`) —
   특정 메시지로 가는 길이 없다. `knowledge_registrations_view` 에도 메시지 순번이 없다.
4. **이 업무에 적용된 지식을 Case 단위로 보는 조회가 없다.** `run_knowledge_view` 는 실행 하나의 Manifest 다.
5. **서버 본문 읽기(`readBody`)는 `KnowledgePanel.tsx` 안의 함수다.** 새 화면이 같은 것을 쓴다.
6. **화면 주소.** `Shell.tsx` 의 `readAddress`/`writeAddress` 는 `project`·`case` 만 안다. `main.tsx` 는
   `?view=admin` 만 관리 화면으로 보낸다.

## 3. 설계

### 3.1 서버 조회 (`controller/repository.py`, `controller/api.py`)

- `_knowledge_version_row` 뒤에 붙는 출처 표시: `source_case_title`(그 Case 제목), `source_message_seq`(권위
  메시지의 순번, 없으면 null). `knowledge_evidence_for` 의 행에 `source_case_title`. 제목·순번뿐 — 본문·요약을
  옮기지 않는다.
- `knowledge_registrations_view`: `source_message_seq`(사용자 말 등록의 권위 메시지), `reply_seq`(그 실행이
  붙인 AI 메시지의 순번 — 논의 응답만 메시지가 있다; 작업 실행은 null).
- `case_knowledge_use_view(case_id)` → `GET /api/cases/{case_id}/knowledge-use`:
  `{case_id, items: [{knowledge_id, knowledge_key, version, version_id, summary, kind, obligation, state,
  authority_kind, scope_kind, repository_name, provided_runs, skipped: {decision: n}, last_run_id,
  last_run_purpose, first_at}], runs_recorded, runs_unrecorded, note}`. `run_knowledge` 를 이 Case 의 실행으로
  묶어 버전별로 센다. `provided` 만 "적용(제공)" 이고 나머지는 사유별 수다. `runs_unrecorded` 는 v22 이전
  실행(Manifest 기록 전)의 수 — "지식 없음" 이 아니다. note = "주입은 제공 기록이며 준수의 증거가 아니다".
- 정책·진입·권위·본문 경계는 건드리지 않는다. 새 표·컬럼 없음.

### 3.2 화면 주소와 이동 (`Shell.tsx`, `Sidebar.tsx`, `ConversationView.tsx`)

- 주소: `?project=P[&case=C][&screen=rules][&item=K-001][&seq=N]`. `screen=rules` 면 가운데가 프로젝트 규칙
  화면이고 오른쪽 패널은 닫힌다. `item` 은 그 항목을 펼쳐 보인다. `seq` 는 대화를 연 뒤 **한 번** 소비한다
  (그 메시지로 스크롤·`sh-message-focus` 강조 3초, 주소에서 지운다). 읽던 위치 기억(D-68)보다 우선한다.
- 왼쪽 목록: 프로젝트 선택 아래 `프로젝트 규칙` 버튼(`data-testid="open-rules"`). 프로젝트 규칙 화면의 머리에
  `← 대화로`(마지막 대화로 복귀).
- 관리 화면 링크는 왼쪽 아래에 그대로.

### 3.3 결정 사항 패널 (`ReviewPanel.tsx` `Decisions`)

절 순서와 내용(전부 서버 값 그대로, 없으면 절을 만들지 않는다):

1. **업무** — 업무화·Profile·결정 주체·위임 근거(UI-03 그대로).
2. **목표·기준** — 의도 최신 버전(`intent_state.latest_intent_version`: 버전·상태·동의 상태·작성 방식)과
   `원문 열기`(결과물 패널의 그 버전, `hads:open-ref`). 기준(`result.criteria`): 요약·판정(`CRITERION_VERDICT_LABEL`).
   의도 본문의 항목(목표·범위·제약)은 PC 원문이라 여기 적지 않는다 — "원문은 결과물 패널에서".
3. **결정** — `detail.decisions`: 종류를 사람 말로(`DECISION_KIND_LABEL`: 의도 동의·설계 검토·계획 검토·최종
   인수·예외 종료·material delta 확인·시작 범위 확인·결과 후보 확인 …), 대상(`intent_version` 이면 `의도 vN`
   + 열기, 그 밖에는 종류·id 앞자리), 주체, 시각, `evidence_ref` 가 이 대화의 메시지 원문이면 `메시지 #n`
   으로 이동.
4. **이 대화에서 정한 규칙·후보** — `conv.knowledge_registrations` 를 출처별로: 사용자 말(활성 등록) / AI 제안
   (논의 응답) / 실행이 남긴 후보 / 근거로 이음 / 등록하지 않음. 행: 키 vN · 지금 상태(현재 버전) · 효력 ·
   종류 · 요약 · `메시지 #n`(권위 메시지 또는 응답 메시지) · `프로젝트 규칙에서 보기`(`screen=rules&item=`).
   "활성화·개정은 프로젝트 규칙에서, 무효화는 카드에서".
5. **이 업무에 적용된 프로젝트 규칙** — `knowledge-use`: 키 vN · 효력 · 상태 · 요약 · 제공 실행 n · 마지막
   실행 · 생략/비적용 수. 머리에 "주입은 제공 기록이며 준수의 증거가 아니다". `runs_unrecorded > 0` 이면
   "Manifest 기록 전 실행 n(지식 없음이 아니다)". 패널을 열 때 한 번 조회하고 진행 상태가 바뀌면 다시.
6. **답한 질문**, **AI 해석 기록**, **진행 이력** — UI-03·P4-05 그대로.
7. 꼬리: "프로젝트 공통 규칙은 프로젝트 규칙 화면에서" 링크.

### 3.4 프로젝트 규칙 화면 (`web/src/shell/ProjectRules.tsx`)

- 조회: `knowledgeApi.list(projectId)` + `shellApi.repositories(projectId)` + 대화 목록(등록 폼의 출처).
  5초 반복 조회는 하지 않는다 — 동작 뒤에 다시 읽는다(관리 패널과 같다).
- 절: **활성 필수** / **활성 참고** / **후보** / **대체·무효**(접힘). 각 행(`data-testid="rule-{key}"`):
  키 vN · 상태 · 효력 · 종류 · 요약 · 범위(프로젝트 전체 / 저장소·경로) · 활동 · 권위 · 내용 저장 위치
  (서버/PC 에만) · 관측(저장소@커밋 — Case 브랜치) · 관계(← K-001 반증 …) · 근거 n 건(출처 실행·대화로 이동)
  · 채택 기록 · 이력(v1 → v2 …) · **출처: 대화 제목 · 메시지 #n** → `?project&case&seq`(권위 메시지가 없으면
  대화만) · `내용 보기`(서버 본문, `lib/knowledgeBody.ts` 로 옮긴 `readBody`).
- 동작(행 안, 사유 칸은 행마다):
  - 후보: `채택 확인`(결과 항목 목록: 막음/경고, 근거 수, 독립 검토 없음) → 활성화 폼(효력 참고/필수, 활동
    좁히기, 저장소로 좁히기(프로젝트 범위 후보에만 — 저장소 선택), `K-00x 의 새 버전으로`) → `활성으로`.
    409 는 코드·항목을 그대로 보인다.
  - 활성·후보: `무효로`(사유 필수).
  - 활성: `개정`(폼: 새 내용(비우면 이전 원문 그대로)·제목·종류·효력·범위·활동·사유; 새 내용은 출처 대화 +
    출처 PC 필요 — 화면이 이 프로젝트의 마지막 대화와 등록된 PC 를 기본값으로 채운다).
  - 충돌: 두 항목 고르기 + 사유 → 기록; 열린 충돌 → 해소 기록.
  - 등록: 출처 대화 선택 · 내용 · 제목 · 종류 · 효력 · 저장소 범위(선택) · 활동 · `AI 제안(후보)` · 사유 →
    등록(바로 활성, 재승인 없음 / 후보). 안내 문구는 관리 패널과 같다(서버 저장 · 비밀값 금지 · 등록은 실행
    권한이 아니다 · 자동 활성화 없음).
- 문구: "등록·활성화·개정은 실행 권한·동의·인수가 아니다. 주입은 준수의 증거가 아니다. AI 제안은 후보로만
  들어가고 활성화는 사람의 결정이다(자동 활성화 없음)".

## 6. 경계

- 결정 사항 패널·프로젝트 규칙 화면은 **보고·이동·사람의 변경** 자리다. 등록·활성화·개정·무효·충돌 기록은
  기존 API 의 규칙 그대로이며 권한·동의·인수·준수가 아니다. 주입 집계도 "제공했다" 일 뿐이다.
- AI 제안은 어떤 경로로도 활성 필수가 되지 않는다(DB CHECK). 참고 후보의 자동 활성화는 없다(사용자 판단
  대기).
- 원문 경계 그대로 — 대화 본문·의도 본문은 PC 에 있고 화면은 열람 경로로만 본다. 지식 본문은 P4-06b 의 서버
  본문 경로다. 새 조회는 제목·순번·수를 더할 뿐 본문·요약을 서버에 새로 두지 않는다.
- 스키마 v24 그대로. 새 표·컬럼·이행 없음.

## 9. 알려진 한계·설계 선택

- **프로젝트 규칙의 자리는 임시다.** 프로젝트 설정 화면(뒤 하위 plan)이 생기면 그 안으로 옮긴다. 지금은 왼쪽
  목록의 프로젝트 자리에서 연다.
- **수동 등록은 출처 대화를 고른다.** API 계약(출처 Case)을 따른 것이며 대화 없는 등록 경로는 만들지 않았다.
- **목표·제약의 본문은 보이지 않는다.** 서버는 의도의 버전·동의·기준 요약·판정만 알고 본문은 PC 다. 항목별
  표시(목표·범위·제약)는 원문 열람과 함께 뒤 작업에서 본다.
- **적용된 규칙 집계는 Manifest 다.** 실행이 실제로 읽었는가(영수증)·지켰는가(판정)는 세지 않는다 — 실행별
  영수증은 관리 화면의 실행 문맥에 있다.
- **원래 메시지로 이동은 순번이다.** 본문은 여전히 열람 경로로 오며 PC 미연결이면 "연결 필요" 다. 검색(D-84)이
  아니다.
- **버전 이력은 항목 안에서만 잇는다.** `into` 로 다른 항목의 새 버전이 된 후보는 후보 항목의 이력에
  `superseded_by` 로 남고 대상 항목에는 채택 기록(`from_candidate`)으로 남는다 — 두 항목 사이의 관계선은
  그리지 않는다(값은 있다).
