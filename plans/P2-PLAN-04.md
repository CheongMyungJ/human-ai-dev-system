## 성공 기준 (AC)

| ID | 기준 | 검증 방법 |
|---|---|---|
| AC-1 | 성공 기준이 **의도 버전에 묶여** 기록된다. 초안의 기준은 `proposed` 이고, 사람이 그 버전에 명시 동의하면 그 버전의 기준만 `user_confirmed` 가 된다. 기준이 0건이면 0건으로 남고 시스템이 채우지 않는다 | 자동 시험: 구조 보고 → `proposed`, 동의 → `user_confirmed`, 기준 없는 초안의 0건 유지 |
| AC-2 | 기준별 결과의 기본값은 **`unverified`** 다. 실행이 끝났다는 사실만으로 판정이 생기지 않고, 판정을 기록하려면 근거 참조가 있어야 한다 | 자동 시험: Run 완료 후에도 결과가 `unverified`, 근거 없는 판정 기록 거부 |
| AC-3 | **실행 불명이 성공이 되지 않는다.** outcome 이 `unknown`·`failed`·`cancelled` 인 Run을 근거로 `met` 을 기록할 수 없다 | 자동 시험 3건(세 outcome 각각 거부) + 라이브 1건 |
| AC-4 | 기준별 **근거 원문을 화면에서 읽을 수 있다.** 근거는 기존 일시중계 경로로 한 번 지나가고 제어부는 본문을 보관하지 않는다 | 라이브(브라우저 열람) + 자동 시험(제어부 바이트에 본문 없음) |
| AC-5 | 최종 결과 후보가 **의도 버전·동의·게이트 판정·기준별 결과·미해결 항목·실행 정리 상태**를 한 버전으로 묶는다. 후보 내용이 바뀌면 새 후보가 생기고 이전 후보는 `superseded` 가 된다 | 자동 시험: 후보 생성 → 기준 판정 변경 → 새 후보, 이전 후보로의 인수 거부 |
| AC-6 | 기본 모드는 **사람의 명시적 인수**로만 완료된다. 거절 사유가 코드로 구별된다(미해결 기준, 후보 대체됨, 명시적이지 않음, 미정리 실행, 의도 미동의, 종료된 Case) | 자동 시험 6건, 각 사유 코드 확인 |
| AC-7 | 미충족·미검증이 남은 채 종료하려면 **예외 수용**이 필요하고, 예외를 수용해도 **원래 판정이 보존**된다. 기준 결과는 `met` 으로 바뀌지 않고 종료 종류는 `closed_with_exceptions` 다 | 자동 시험: 예외 수용 전후의 `criterion_result.verdict` 불변, `exception_decision.original_verdict` 보존 |
| AC-8 | **자동 완료는 사람 인수가 아니다.** 같은 후보를 기본·자동 두 모드로 평가하면 기준 충족 판정은 같고 사람 확인 필요 여부만 다르다. 자동 모드는 미충족·미검증을 **스스로 예외 수용하지 않는다** | 자동 시험: 같은 후보 두 모드 비교, 자동 모드의 예외 요청 거부, 기록의 `mode=auto_policy`·actor 가 사람이 아님 |
| AC-9 | 인수·예외 수용이 **다른 권한을 만들지 않는다.** 의도 동의·게이트 판정·진입 조건과 별개 기록이며, 인수 후에도 코드 변경 실행은 여전히 거부된다 | 자동 시험: 인수 후 `feature_implementation`·`workspace_write` 거부 유지, decision 표에 종류별 행이 따로 남음 |

| AC-11 | **재시작 복원.** 제어부와 Runner를 각각 `taskkill /F /T` 로 죽인 뒤 재기동해도 입력·동의·Run·원문 참조·기준별 결과·후보·인수·종료 기록이 그대로다 | 라이브: 강제 종료 후 재기동 대조 + 자동 시험(새 프로세스 대신 새 연결로 재현) |
| AC-12 | 중계 중이던 **원문 열람은 `expired` 가 되며 원문 삭제와 구분**된다. 재시작 후 다시 요청하면 소유 Runner에서 같은 해시로 다시 온다 | 라이브 + 자동 시험 |
| AC-13 | 데이터 경계 유지: 성공 기준 본문·근거 서술·인수/예외 문구가 제어부 DB·WAL·SHM·로그 **바이트에 없고** Runner 저장소에는 있다 | 자동 시험 확장 + 라이브 바이트 검사 |
| AC-14 | **화면만으로 처음부터 끝까지 한 바퀴.** AI 초안 → QG-01 의미 검토 실행 → 원문 열람 → 동의 → 제한 작업 → 기준별 결과·근거 → 최종 확인까지 브라우저로 재현하고 README 절차가 그대로 동작한다. P2-03이 남긴 화면 미확인 경로가 여기서 닫힌다 | 라이브: 브라우저 캡처·조작 기록 |

## 기준별 결과의 판정값과 승격 조건

| 판정 | 뜻 | 기록 조건 |
|---|---|---|
| `unverified` | 아직 확인하지 않음. **기본값** | 조건 없음. 기준이 생기면 이 값으로 시작한다 |
| `met` | 충족 | 근거 Run 의 outcome 이 `completed` 이고 근거 원문 참조가 있어야 한다 |
| `not_met` | 미충족 | 근거 참조 필요. 실패도 근거 없이 적지 않는다 |
| `blocked` | 확인할 수 없었음(환경·도구 문제) | 근거 참조 필요. **미충족과 구분**한다 |
| `needs_recheck` | 대상이 바뀌어 재검토 필요 | 시스템이 새 의도 버전 생성 시 전이시킨다 |

`unknown` 을 판정값으로 두지 않는다. 실행의 `unknown` 은 Run 쪽 값이고, 그 Run을
근거로 한 기준 판정은 **기록 자체가 거부**된다. 실행 불명을 기준 판정으로 옮기면
"불명"이 조용히 판정이 되어 버리기 때문이다.

## 인수 거절 사유 (AcceptanceRefusal)

| 코드 | 언제 |
|---|---|
| `not_explicit` | 대상이 분명한 인수 행동·문구가 아니다 |
| `candidate_superseded` | 그 사이 후보가 바뀌었다. 이전 후보의 확인을 새 후보에 쓰지 않는다 |
| `unresolved_criteria` | `met` 이 아닌 기준이 남아 있고 그 기준에 대한 예외 수용이 없다 |
| `unsettled_runs_present` | 진행 중이거나 결과가 `unknown` 인 Run이 남아 있다 |
| `intent_not_agreed` | 기능 개발 Case인데 최신 의도에 동의가 없다 |
| `case_already_closed` | 이미 종료된 Case다. 변경은 연결된 새 Case로 한다 |
| `auto_policy_cannot_accept_exception` | 자동 완료 모드가 예외를 수용하려 했다 |
| `exception_target_not_failing` | 충족된 기준에 예외를 걸려 했다 |

이 목록은 `AgreementRefusal`(P2-02)·`AdmissionRefusal`(P2-03)과 **합치지 않는다.**
세 검사는 서로 다른 질문에 답한다.

## 완료 정책과 종료 종류

| 정책 | 동작 |
|---|---|
| `human_acceptance` (기본) | 후보를 만들고 사람의 명시적 인수를 기다린다 |
| `auto_on_conditions` | 모든 기준이 `met` 이고 미정리 실행이 없고 게이트·동의 조건이 유효하면 자동 완료한다. 기록은 `mode=auto_policy` 이며 사람 인수로 표시하지 않는다 |

| 종료 종류 | 언제 |
|---|---|
| `completed` | 모든 기준이 `met` 이고 예외가 없다 |
| `closed_with_exceptions` | 사람이 표시된 미충족·미검증을 수용했다. 원래 판정은 보존된다 |
| `cancelled` | 수행 중단 결정. 성공도 예외 인수도 아니다 |

**인수했는데 미정리 실행이 남아 있으면** `final_acceptance` 는 기록하되
`closure_record` 를 만들지 않는다. 화면에는 `인수됨 · 실행 상태 확인 필요` 로 두
상태를 함께 표시한다(completion-lifecycle 5절).

## 완료 기록 (2026-09-21)

`P2-PLAN-04`는 **성공 기준 AC-1~14를 모두 통과해 완료로 종료**했다. 결과와 증거는
[P2-04 결과](../p2/evidence/P2-04-results.md)에 있다. **계획을 고치지 않고 끝냈다** —
범위·설계 선택·제외 범위를 바꾸지 않았다.

계획이 예상하지 못한 것이 둘 있었고, 둘 다 라이브 검증에서 드러났다.

1. **화면이 대체된 의도 버전을 검토하고 있었다.** 목록의 첫 intent 원문을 지시로 집는
   바람에, v2 가 있는데도 v1 을 검토했다. 검토는 정상 종료하는데 최신 버전의 게이트는
   `not_run` 그대로여서 아무 것도 진척되지 않았다. 이 계획이 "화면 미확인 경로를 닫는다"를
   범위에 넣지 않았다면 발견하지 못했을 결함이다. 화면과 **서버**를 함께 고쳤다.
2. **AI 재작성 경로가 이전 버전을 보지 못한다.** 초안 작성 실행에 들어가는 것은 요청
   원문 하나뿐이라 "이 지적을 고쳐 달라"만 보내면 AI가 처음부터 다시 쓴다. 라이브에서
   실제로 초안이 퇴화했다. **고치지 않고 P3·P4로 넘겼다** — 작성 실행의 컨텍스트 구성은
   P2-03이 만든 경로의 확장이고 review-context-contract.md·FR-15의 범위이기 때문이다.

계획에 없던 작은 구현 선택 하나를 더했다. **피드백의 처리 결과를 사람이 정하는 경로**
(`POST /api/cases/{id}/feedback/{fid}/disposition`)다. 위 2번 때문에 AI가 새 버전을 써도
피드백이 닫히지 않아 최종 인수가 막혔는데, AI가 스스로 "반영했다"고 선언하게 만드는 대신
사람이 판단하게 했다(intent-artifacts 3절). 미반영은 이유가 필수다.
