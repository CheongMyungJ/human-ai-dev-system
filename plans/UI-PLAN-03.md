# UI-PLAN-03

기본 대화 화면. 기준: 설계 v0.8 2차 / D-01~90 / 2026-09-23.
선행: UI-02 완료(스키마 v18), P4-04 완료(v17), UI-01 완료(v16). 이 세션에서 `scripts\run-tests.ps1` 로
pytest **575**, P1 계약 unittest **18** 통과를 다시 확인했다(5분 20초 — 이전부터 흔들리던 P4-02 시험도
이번에는 통과).
범위는 **UI-03 하나**다. P4-05~07, UI-04(대화 검색·알림·상세 설정·외부 편집·미커밋 포함 시작·활성 Case
목적 변경), P5·P6 은 포함하지 않는다.

## 1. 현재 구현과 이 작업이 메울 차이

코드를 대조해 확인한 사실이다([DEVELOPMENT.md](../DEVELOPMENT.md) 1.5절의 시작점).

1. **화면은 관리 화면 하나다.** `web/src/App.tsx` 가 프로젝트·Case·상세 패널을 열 단위로 늘어놓고
   (다크 테마, 수동 새로 고침), `ConversationPanel` 은 메시지의 **요약만** 보인다. 대화 본문을
   보이는 곳이 없다(의도 원문만 `IntentPanel` 이 열람 중계로 연다).
2. **사용자 요청을 처리하는 쪽이 제품에 없다.** 메시지가 저장돼도 사람이 관리 화면에서 "논의 응답
   실행"을 만들고 "처리 완료 기록"을 눌러야 한다(9절 UI-01 행). 라이브에서는 하네스가 그 역할을 했다.
3. **자연어 업무 요청의 AI 분류가 없다.** 업무화 기록 계약(`work-start`, `decided_by =
   ai_interpretation`)은 UI-01 에 있으나 그것을 쓰는 흐름이 없다(9절).
4. **초안이 브라우저에 남지 않는다.** `ConversationPanel` 은 입력을 React 상태로만 들고 있어 새로
   고침·대화 전환에 사라진다(D-83 미구현).
5. **결과물 목록·검토 버전 유지가 없다**(D-85). 산출물은 원문 참조 표로만 보인다.
6. **기본값 요약이 없다**(D-72). 정책 값은 관리 화면의 정책 패널에만 있다.
7. **원문 열람의 "연결 필요" 표시가 없다.** PC 가 미연결이어도 열람 요청은 대기한다(9절 UI-02 행).
8. **기존 접수 네 경로**(`/artifacts`·`/intent-drafts`·`/feedback`·`/questions/{id}/answer`)는
   접수를 커밋한 **뒤에** 본문을 중계 버퍼에 넣는다. 그 사이에 Runner 폴링이 끼면 본문 없는 접수가
   유실로 표시된다(9절 UI-01 행). 메시지 경로만 먼저 넣는다.
9. **업무 단계의 자동 진행은 제품에 없다.** 업무화 뒤 의도 초안→QG-01→repair→질문·동의→준비→
   작업 그래프→작업공간→구현·검증→완료를 이어 가는 것은 관리 화면의 버튼이나 라이브 하네스
   (`p3/live/path_a.py`)가 했다. 1.1절의 UI-03 정의(화면·초안·검토 버전)에는 들어 있지 않다 — 3.11절.

## 3. 설계

### 3.1 요청 처리기

`controller/request_processor.py`. 판정은 `domain/conversation.py` 에 둔다(순수 함수).

- **켜짐:** 제어부 설정 `auto_process_requests`(환경 변수 `HADS_AUTO_PROCESS_REQUESTS`, **기본 켜짐**).
  끄면 UI-01 의 명시 처리 계약 그대로다 — 기존 시험과 옛 라이브 하네스(`ui/live/ui01_*`·`ui02_*`)가
  그 경로를 쓴다. 제품 코드에 시험용 분기를 넣는 것이 아니라 운영 설정이다.
- **대상:** 일반·정정 메시지가 연 요청. 카드 답변은 요청을 열지 않으므로 대상이 아니다.
- **시작 시점:** 요청을 연 메시지 원문이 PC 에 **저장됐다는 보고**(intake `stored`)를 받은 직후.
  접수 대기(202)에서는 시작하지 않는다 — 받지 않은 말은 처리하지 않는다(진입 검사도 같다).
- **동작:** 논의 응답 실행 하나를 만든다. `run_id = reply-{request_id}`(멱등 — 같은 보고의 재전송·
  재시작 복구가 두 번 만들지 않는다), 목적 `discussion_reply`, 읽기 전용, 역할 author, 지시 = 여는
  메시지 원문(id·rev), `request_id`. 도구는 **프로젝트 기본 도구**(`project.default_tool_id`, D-72)이고
  그 원문을 가진 PC 가 그 도구를 코딩 CLI 로 `verified` 보고했을 때만 쓴다(mode 는 그 능력의 값).
  진입 검사·예산·중단·문맥 한도는 기존 `admit_and_create_run` 그대로다.
- **만들 수 없으면**(도구 없음·진입 거부) 요청을 `failed` 로 끝내고 사유 코드를 `note_summary` 에
  남긴다. 거부는 진입 검사 기록에도 남는다. 처리 중으로 두면 잠금이 영원히 남는다.
- **끝:** 연결 실행의 결과를 기록한 뒤, 요청이 처리 중이고 **중단 요청이 없고** 연결 실행이 전부
  끝났으면 — 먼저 AI 해석을 적용하고(3.2) 요청을 끝낸다. 처리기의 응답 실행이 `completed` 이고 AI
  메시지가 붙었으면 `completed`, 아니면 `failed` 를 요청한다. 결과를 모르는 실행은 `decide_settle` 이
  `unknown`·`interrupted` 로 판정한다(UI-02 그대로). 사람이 붙인 다른 실행이 남아 있으면 그것이 끝날
  때 다시 본다. 종료 주체는 `request-processor` 다.
- **중단된 요청은 건드리지 않는다** — UI-02 대로 확인한 제어부가 `interrupted` 로 끝낸다.
- **재시작 복구:** 제어부 기동 때 처리 중·중단 없음·여는 메시지 저장됨인 요청을 훑는다. 실행이
  없으면 응답 실행을 만들고, 연결 실행이 전부 끝났으면 (해석을 적용하고) 끝낸다.
- **경계:** 처리기는 **읽기 전용 응답 하나만** 만든다. 업무 단계에서도 같다 — 업무 단계의 다음
  작업을 시작하지 않는다(3.11). 응답 실행이 하나이므로 "실행 사이에 잠금을 푸는" 자리가 없다.

### 3.2 AI 해석과 최초 업무화 (D-69)

- **준비 단계 Case 의 응답에만.** 배정 내용에 `conversation_stage`(배정 시점의 유효 단계)를 싣고,
  Runner 는 준비 단계면 논의 지시문에 **해석 규칙**을 덧붙인다.
- **해석 규칙(지시문):** 답 글 끝에 기계용 블록 하나를 둔다 —
  ```` ```hads-interpretation ```` 안에 `{"kind": "discussion"}` 또는
  `{"kind": "work_request", "profile": "<여섯 중 하나>"}`. `work_request` 는 사용자의 **마지막
  메시지가** 구체적인 작업 수행(분석·조사 정리, 원인 규명, 주어진 범위의 구현·수정 등)을 **명시적으로**
  요청할 때만이다. 선택지 동의·생각 나누기·질문·금지 표명은 `discussion` 이다. 모호하면
  `discussion` 으로 두고 글로 묻는다. 업무 요청이면 글에 이해한 목표·범위·제약을 짧게 적는다
  (ui-conversation-design 5절 표).
- **Runner:** 최종 메시지에서 마지막 블록을 떼어 **글만** 응답 원문으로 저장하고, 해석을 결과 보고에
  싣는다(`interpretation: {status: reported | missing | invalid, kind?, profile?}`). 블록이 없거나 형식이
  틀리면 `missing`·`invalid` 이고 응답 글은 그대로 붙는다 — 해석 실패가 응답을 지우지 않는다. 블록을
  뗀 글이 비면 실행은 `failed` 다(글 없는 응답을 AI 의 말로 보이지 않는다).
- **제어부:** 해석을 새 표 `conversation_interpretation` 에 결과와 **같은 트랜잭션**으로 남긴다(본문
  없음). 처리기가 요청을 끝내기 전에 적용한다: `work_request` + 유효 Profile + 응답 `completed` 이면
  `start_work(decided_by = ai_interpretation, interpretation_run_id = 그 실행, request_message_id = 여는
  메시지, actor = ai:<도구>)`. **위임 근거는 UI-01 그대로 여는 메시지 원문**이다 — AI 의 해석 글이
  위임 근거가 되지 않는다. 적용이 거부되면(이미 업무 단계·종료 등) 사유를 해석 행에 남긴다.
- **요약은 본문에서 만들지 않는다.** 업무화 요약은 `AI 해석 · <Profile> 업무 요청 · 메시지 #n` 같은
  표시다 — 이해한 목표는 PC 에 있는 응답 글에 있다(D-51, 9절 "요약이 본문 발췌인지 판별 못함").
- **사람 확인 없이 업무화하는 것은 D-69 의 확정 동작이다**("일괄 시작 버튼을 요구하지 않고 명확한
  자연어 요청으로 업무화"). 업무화는 실행을 시작하지 않는다. Autonomy·예산·저장소 선택·금지는 그대로
  이어지고 조사 Profile 의 제품 쓰기 차단(D-66)은 사용자 결정이 없으므로 풀리지 않는다(UI-01 규칙).
  Case 제목은 바꾸지 않는다(본문에서 제목을 지으면 서버에 내용이 남는다).
- 업무 단계 Case 의 응답에는 해석 규칙을 붙이지 않는다. 목적·유형 변경(D-86)은 UI-04 다.

### 3.3 화면 구성 (D-68·D-71)

- 새 기본 화면이 `/` 다. 기존 관리 화면은 `/?view=admin` 으로 그대로 둔다(3.10).
- **왼쪽:** 프로젝트 선택(다른 프로젝트의 "답변 필요·실행 상태 확인 필요" 수를 선택기에 표시, 자동
  전환 없음), 새 대화, **답변 필요** 대화, 최근 대화(보관 제외, 마지막 활동 순), 보관된 대화(접힘,
  복원 가능). 아래에 PC 연결·테마·관리 화면 링크. 목록 행은 제목과 필요한 상태만 보인다(처리 중·
  중단 요청 중·실행 상태 확인 필요·답변 필요·업무 Profile·종료).
- **가운데:** 머리(제목·단계/Profile·종료 상태·보관/복원·`결과물`·`결정 사항`), 대화 흐름(메시지·
  업무화 표시·요청 진행·질문 카드), 입력창.
- **오른쪽:** `결과물`·`결정 사항`을 누를 때만 열린다. 닫혀 있으면 대화 폭을 넓게 쓴다.
- 왼쪽·오른쪽 패널 접기와 폭 조절(끌기), 폭·접힘을 브라우저에 기억. 프로젝트 전환 때 그 프로젝트의
  마지막 대화와 읽던 위치(스크롤)를 복원한다. 주소(`?project=&case=`)도 유지한다.
- **라이트가 기본**이고 다크·시스템 따르기를 고른다(브라우저에 기억). 낮은 채도, 읽기 폭 제한, 절제된
  구분선. 카드는 질문·업무화·결과에만 쓴다.
- 갱신은 조회 반복이다(처리 중 약 1.5초, 평소 5초). 푸시·알림은 UI-04.
- **판단 값은 서버가 준 그대로다:** 전송 가능(`send.general`·`card_answer`)과 사유, 요청 상태, 실행
  상태, PC 연결, 원문 가용성. 화면이 스스로 계산하지 않는다.

### 3.4 대화 본문과 원문 가용성 (D-75·D-43·D-51)

- 메시지 본문(사용자·AI)은 기존 **원문 열람 중계**(`read-requests`)로 소유 PC 에서 가져온다. 서버는
  저장하지 않는다.
- **브라우저 메모리에만 둔다**(탭 수명). 브라우저 저장소에 대화 본문 사본을 만들지 않는다 — 초안
  (D-83)은 사용자가 아직 보내지 않은 자기 입력이고, 보낸 뒤의 원문 소유자는 PC 다. 한 번 불러온
  본문은 PC 가 끊겨도 보인다(D-75).
- 상태별 표시: 저장 대기(`pending`), 저장 전 유실, **소유 PC 미연결 → "연결 필요"**(새 열람 요청을
  만들지 않는다, 연결되면 불러온다), 열람 만료 → 다시 불러오기.
- AI 응답(실행 출력)은 머리(실행 정보)와 최종 메시지를 나눠 최종 메시지를 본문으로, 실행 정보는
  접어서 보인다.
- **의도 원문은 사람이 결과물 패널에서 열 때만 불러온다.** 의도 원문 전달은 "사람이 원문을 확인했다"
  기록(`intent_view`)을 남기므로 화면이 스스로 불러오지 않는다.
- PC 연결은 서버가 도출한다 — `GET /api/runners` 가 행마다 연결 상태를 싣는다(4절).

### 3.5 진행·질문 카드 (D-70·D-71·D-76)

- **요청 진행:** 현재 요청과 실행별 실제 상태(서버 `execution_state`)를 문장으로 보인다(예: AI 가 답을
  쓰는 중·배정 대기·실행 상태 확인 끊김). 근거 없는 진행률·예상 시간은 없다. 중단 버튼, 중단 요청 중,
  `unknown` 이면 "실행 상태 확인 필요"와 상태 다시 확인. 중단·불명 요약(서버 `interruption_summary`)과
  실행 세부(목적·도구·세션·사용량·잔류 근거·이벤트)는 접어서 보인다.
- **업무화 표시:** `work_start` 가 있으면 근거 메시지 뒤에 "업무로 전환됨 · Profile · 결정 주체(사람 /
  AI 해석) · 근거 메시지 #n".
- **질문 카드:** 최신 의도 버전의 열린 질문(서버 `intent_state`)마다 카드 — 질문 요약·결정 시점·대상
  의도 버전을 보이고 직접 입력으로 답한다(`card_answer`, 카드가 보인 의도 버전 포함). 질문 모델에
  선택지가 없으므로 선택지를 지어내지 않는다. 답한 질문은 "답함 · 시각". 답변이 동의·권한이 아님을
  카드에 적는다. 처리 중에도 답할 수 있고 PC 미연결이면 못 한다(서버 `card_answer`).
- **업무 단계 안내:** 업무 단계면 머리 아래 한 줄로 서버 상태(의도 동의 상태·QG-01 판정·완료 상태)와
  "업무 단계의 다음 작업은 아직 이 화면이 자동으로 진행하지 않는다 — 관리 화면에서 진행" 링크.
  미지원을 성공처럼 보이지 않는다.

### 3.6 결과물·결정 사항 패널과 검토 버전 유지 (D-71·D-85·D-89)

- **있는 것만 나열한다:** 의도(버전들), 설계·개발계획(개정들), 실행 출력(논의 응답 제외), 코드
  변경(실행별 작업공간 변화 요약), 검증(명령 기록·기준 결과). 없는 종류는 나타나지 않는다.
- 문서 단위: 의도 = Case 의 의도 버전 전체, 설계·계획 = 준비 단계별 개정, 실행 출력 = 실행 하나.
  목록에서 열면 최신 버전이다.
- **열람기는 본문을 특정 버전에 고정한다.** 더 새 버전이 생기면 본문을 바꾸지 않고 "새 버전 vN ·
  변경 내용 보기 · 최신으로 전환"을 보인다. 변경 내용 보기는 두 버전 본문을 불러 줄 단위로 비교한다
  (브라우저 계산, 원문은 메모리). 전환은 사용자가 고른다.
- 과거 메시지의 참조는 **그 메시지가 가리킨 버전**을 연다. 최신이 아니면 "최신 아님"을 표시하고 새
  버전으로 옮기지 않는다.
- **`대화에 참조`:** 열람 중인 문서의 id·버전(+선택 위치 표시)을 입력창 초안에 붙인다. 보낼 때 서버가
  버전·해시를 고정한다(UI-01 참조 계약).
- **코드 변경:** 서버에 있는 것은 변경 파일 수·지문뿐이고 diff 본문은 작업 PC 에 있다. 작업 PC 이름·
  작업공간 경로·경로 복사를 보이고 "변경 내용(diff) 열람은 아직 지원하지 않는다"를 표시한다. 폴더·
  편집기 열기는 제공하지 않는다(작업 PC 대상 열기는 UI-04).
- **결정 사항:** 업무화 기록, 기록된 결정(동의 등 — 주체·시각·대상 버전), 답한 질문, AI 해석 기록.
  읽기 전용. 프로젝트 공통 규칙·지식은 P4-06·UI-04.

### 3.7 입력창과 초안 복구 (D-70·D-81·D-83)

- 전송 가능은 서버 판정 그대로(`send.general`)이고 걸리는 사유를 전부 보인다. 버튼이 꺼져도 입력·
  참조 편집은 된다.
- **초안 저장:** 대화별로 현재 브라우저 `localStorage` 에 텍스트·참조·정정 대상을 자동 저장한다
  (편집 뒤 짧은 지연). "초안 저장됨(이 브라우저)"과 **저장 실패**를 구분해 보인다. 다른 기기로
  동기화하지 않고 서버에 대기열이 없다.
- **전송분 식별:** 보낼 때 초안 스냅샷과 전송 식별자(`client_message_id`)를 **보냄 기록**으로 초안에
  함께 저장한다. 같은 내용을 다시 보내면 같은 식별자를 쓴다(내용이 바뀌면 새 식별자).
- **비우기 규칙:** `by-client-id` 로 `stored` 가 확인되면 **지금 초안이 보낸 스냅샷과 같을 때만**
  비운다. 보낸 뒤 사용자가 고쳤으면 고친 초안을 남기고 보냄 기록만 지운다. 거부(409)·유실은 초안을
  남긴다. 응답을 못 받은 전송은 보냄 기록을 남기고 다음 확인(새로 고침·대화 전환 포함)에서 대조한다
  — 404 면 받지 않은 것이므로 보냄 기록만 지운다. **자동 전송하지 않는다.** "메시지 접수됨"은
  `stored` 일 때만이다.
- **정정("수정해서 다시 요청"):** 보낸 사용자 메시지에서 누르면 불러온 본문을 입력창에 가져와 정정
  모드가 된다. 보내면 `correction` 새 메시지이고 원본·실행·효과는 남는다.
- **참조:** 산출물 참조(결과물 패널), 파일 참조(등록 저장소 선택 + 경로 + 위치 표시). 이미지·외부 파일
  업로드는 없다(D-81).
- **카드 답변 초안**도 질문별로 같은 규칙으로 저장·복구한다.
- 처리 중: 초안 편집 가능·일반 전송 비활성·카드 답변 가능. PC 미연결: 편집 가능·둘 다 비활성.

### 3.8 기본값 요약 (D-72)

입력창 위 한 줄에 서버 정책 값 그대로: 응답 도구(프로젝트 기본 도구와 PC 보고 상태), Autonomy(적용
값·출처), 작업 깊이(있으면), 예산(한도 없음 / 설정된 한도), 대상 저장소 수. 펼치면 출처를 보인다.
변경은 관리 화면 링크다(상세 설정은 UI-04).

### 3.9 기존 접수 네 경로의 중계 순서

`/artifacts`·`/intent-drafts`·`/feedback`·`/questions/{id}/answer` 도 메시지 경로처럼 **접수 식별자를
먼저 정해 본문을 중계 버퍼에 넣고** 기록한다. 기록되지 않으면(거부·예외) 버퍼에서 뺀다. 멱등 키는
더하지 않는다 — 9절에 남긴다.

### 3.10 관리 화면

기존 `App` 을 `/?view=admin` 으로 유지하고 새 화면에서 링크한다. 동작은 바꾸지 않는다. 처리기가 켜져
있으면 관리 화면의 "논의 응답 실행"·"처리 완료 기록"은 이미 처리된 요청에 서버가 거부로 답할 수
있다 — 서버 판정 그대로 보인다. 관리 화면의 대화 패널에 처리기 상태 한 줄을 더한다.

### 3.11 넣지 않은 이유

- **업무 단계 자동 진행.** 업무화 뒤의 흐름을 제품이 스스로 이어 가려면 여러 실행을 한 요청에 묶는
  잠금·종료 시점, 사람 대기(질문·동의) 동안의 전송, repair·설정 예약·변경 사건과의 상호작용, Profile
  별 다음 작업 선택을 새로 정해야 한다. 라이브 하네스가 약 1,000줄로 한 역할이며 1.1절 UI-03 의
  정의에 없다. UI-03 은 이를 **미지원으로 표시**하고 관리 화면으로 연결한다(1.1절 "지원하지 않으면
  미지원으로 표시하며 임시 성공 동작을 만들지 않는다"). 어느 작업에 배정할지는 인계에서 사람에게 묻는다.
- **확인 카드.** 의도 동의·controlled 시작/결과·권한 확대·예외 수용은 대상·범위·버전을 보이는 확인
  동작이고 업무 단계 흐름과 함께 움직인다. 그 흐름이 관리 화면에 있으므로 확인도 거기 둔다.
- **서버 측 대화 요약문.** AI 요약을 서버에 두면 본문이 복제된다. 진행 요약은 상태에서 도출한다.

## 4. 저장·API

스키마 **v19**.

- 새 표 `conversation_interpretation`: `run_id`(PK, 실행), `case_id`, `request_id`, `opening_message_id`,
  `report_status`(`reported`/`missing`/`invalid`), `kind`(`discussion`/`work_request`, NULL 가능),
  `profile`(NULL 가능), `applied`(0/1), `refusal`(거부 코드, NULL 가능), `recorded_at`, `applied_at`.
  **본문·요약 없음.**
- 이행은 표만 만든다. 옛 요청·실행에 해석을 지어내지 않는다. 반복 이행이 멱등이다.

API:

| 경로 | 내용 |
|---|---|
| `POST /api/runner/runs/{id}/result` | 선택 필드 `interpretation`(논의 응답 실행만 받는다) |
| 배정 내용 | 논의 응답 실행에 `conversation_stage` |
| `GET /api/cases/{id}/conversation` | `processing`(처리기 켜짐 여부), `interpretations` |
| `GET /api/projects/{id}/conversations` | 행마다 `last_activity_at` |
| `GET /api/projects` | 행마다 `attention`(답변 필요·실행 상태 확인 필요·처리 중 수) |
| `GET /api/runners` | 행마다 `connection`(서버 도출 — 대화 조회와 같은 함수) |

설정: `HADS_AUTO_PROCESS_REQUESTS`(기본 `1`). 새 사용자 입력 경로는 없다.

의존성: 브라우저 시험용 `playwright`(Python)를 `requirements.txt` 에 더한다(pytest 와 같은 개발 의존성
자리). **브라우저는 내려받지 않고 설치된 Edge(`msedge` 채널)를 쓴다.** 웹 단위 시험은 Node 22 의
내장 시험 실행기(`node --test --experimental-strip-types`)로 돌려 새 npm 의존성을 더하지 않는다.
`scripts\run-tests.ps1` 에 웹 빌드·웹 단위 시험 단계를 더한다(`-SkipWeb` 으로 뺄 수 있다).

## 5. 성공 기준

| 기준 | 내용 |
|---|---|
| AC-1 | 여는 메시지의 저장 보고 뒤 논의 응답 실행이 **하나** 생긴다(목적·읽기 전용·프로젝트 기본 도구·지시 = 여는 메시지·요청). 저장 보고 재전송·재시작 복구에 중복이 없고, 저장 전에는 만들지 않으며, 카드 답변은 실행을 만들지 않는다 |
| AC-2 | 응답 완료 → AI 메시지 → 요청 `completed` → 전송 열림. 실패 → `failed` → 열림. 결과 불명은 UI-02 판정(`unknown` 잠금·`interrupted`). 사람이 붙인 다른 실행이 끝나지 않았으면 그것이 끝날 때 끝낸다 |
| AC-3 | 응답 실행을 만들 수 없으면(도구 없음·진입 거부) 요청이 `failed` 와 사유 코드로 끝나 잠금이 남지 않는다. 진입 거부는 진입 검사 기록에 남는다 |
| AC-4 | 중단이 요청된 요청은 처리기가 끝내지 않는다(UI-02 경로). 기동 복구가 빠진 응답 실행을 만들고 끝난 요청을 끝낸다. 설정으로 끄면 UI-01 명시 계약 그대로다 |
| AC-5 | 준비 단계 응답에만 해석 규칙이 붙는다. Runner 가 블록을 떼어 글만 저장하고 해석을 결과에 싣는다. 블록 없음·형식 오류는 `missing`·`invalid` 이고 응답은 붙는다. 글이 비면 `failed` |
| AC-6 | `work_request` + 유효 Profile + 완료 → 같은 Case 업무화(`ai_interpretation`·해석 실행·여는 메시지 위임 근거·현재 정의판), 이어서 요청 `completed`. `discussion` → 준비 단계 유지. 업무 단계·종료 Case 에는 적용하지 않고 사유를 남긴다. 업무화가 실행을 시작하지 않고 조사 Profile 의 제품 쓰기 차단이 유지된다 |
| AC-7 | 해석 기록에 본문·요약이 없고 대화 조회에 보인다 |
| AC-8 | 기존 네 접수 경로가 기록 전에 중계하고, 거부되면 버퍼에서 뺀다(커밋-중계 사이 폴링에도 유실 없음, 거부에 고아 본문 없음) |
| AC-9 | 조회 보강: 목록 마지막 활동, 프로젝트 주의 수, Runner 연결 도출(대화 조회와 같은 값), 대화 조회의 처리기 여부·해석 |
| AC-10 | v18→v19 이행이 새 표만 만들고 옛 데이터를 바꾸지 않으며 멱등이다 |
| AC-11 | 새 기본 화면(왼쪽·가운데·오른쪽), 관리 화면 유지, 라이트 기본·다크·시스템 선택 기억, 패널 접기·폭 기억, 프로젝트 전환 시 마지막 대화 복원 |
| AC-12 | 전송 버튼·사유·요청 상태·실행 상태·PC 연결이 서버 값 그대로다. 처리 중 일반 전송 비활성·초안 편집 가능·카드 답변 가능, PC 미연결 시 둘 다 비활성이고 같은 요청을 직접 보내도 서버가 같은 사유로 거부한다 |
| AC-13 | 본문은 열람 중계로 불러와 브라우저 메모리에만 있다(브라우저 저장소에 대화 본문 없음). 가용성 상태를 보이고, 소유 PC 미연결이면 "연결 필요"이며 새 열람 요청을 만들지 않는다. 불러온 본문은 단절 뒤에도 보인다. 의도 원문은 사람이 열 때만 불러온다 |

| AC-20 | 경계: 강제 축 넷·게시 미강제, 처리기·해석이 권한·동의를 만들지 않음(위임 근거 = 사용자 메시지), 제어부에 본문 없음(데이터 경계 시험), 기존 시험 통과 |

## 10. 구현 중 plan 에서 바꾼 것

- **목록 행에 `current_request_stopping`.** 중단 요청 중인 요청은 상태가 `processing` 그대로라
  목록이 "처리 중"과 "중단 요청 중"을 구별하려면 값이 하나 더 필요했다(4절 목록 보강에 더함).
- **처리기가 끝내지 못한 요청의 사유는 `note_summary` 에 남긴다.** 요청 이유 코드
  (`outcome_reason`)의 CHECK 목록을 넓히면 `conversation_request` 를 다시 만들어야 한다(UI-02 처럼).
  응답 실행을 만들 수 없거나 응답이 완료되지 않은 요청은 `failed`·`settled` 로 끝내고 사유 코드
  (`reply_tool_unavailable`·`reply_refused: …`·`reply_not_completed`)를 짧은 요약 칸에 둔다. 스키마
  v19 는 표 하나만 더한다.
- **처리기의 실패가 Runner 보고를 실패시키지 않는다.** 저장·결과 보고는 이미 기록된 뒤라, 처리기
  예외를 API 오류로 올리면 Runner 가 같은 보고를 되풀이한다. 실패는 로그(본문 없음)에 남기고 요청은
  처리 중으로 남으며, 다음 보고나 기동 복구가 다시 본다(3.1절 보강).
- **브라우저 시험은 실제 Runner 프로세스를 쓴다.** 6절 6항 그대로이며, 가짜 `codex` 에 해석
  블록을 내는 표지(`HADS_FAKE_WORK=<Profile>`)와 UTF-8 출력을 더했다(가짜가 콘솔 코드 페이지로
  한글을 내 화면에 깨진 글자가 보였다 — 실제 codex 는 UTF-8 이다).
- **v18→v19 이행 시험의 v18 DB.** v19 가 표 하나만 더하므로 "지금 이행 코드로 만든 DB 에서 그
  표와 v19 표식을 뺀 것"을 v18 DB 로 쓰고, 커밋된 v18 스키마에 그 표가 없고 나머지 표가 모두
  있다는 것을 먼저 단언해 그 동등성을 시험의 전제로 고정했다(6절 4항의 방법을 바꿈).
- **제어부 공유 연결을 문장 단위로 직렬화했다(범위에 없던 결함 수정).** 브라우저 시험이 가끔
  "방금 만든 열람 요청이 없다(404)"로 실패했고, 부하로 재현하니 25초에 367건이 틀리고 1,663건이
  오류였다(`InterfaceError: bad parameter or other API misuse`). 요청 스레드들이 연결 하나를 쓰는데
  쓰기 트랜잭션만 잠겨 있어, 같은 SQL 을 두 스레드가 동시에 실행하면 파이썬 sqlite3 의 준비된 문장
  캐시를 함께 써서 매개변수가 섞였다. P2 부터 있던 구조이며 새 화면이 조회를 겹쳐 보내면서
  드러났다. 기본 화면이 쓸 수 있으려면 고쳐야 하므로 이 작업에서 고쳤다: 앱의 연결을
  `SerializedConnection` 으로 감싸 **문장 하나(실행과 결과 읽기)를 쓰기 트랜잭션과 같은 잠금 안에서**
  끝낸다(`controller/db.py`). 같은 부하에서 0건·0 오류다. 회귀 시험 `tests/test_shared_connection.py`
  는 고치기 전 코드에서 실패하고 고친 뒤 통과함을 확인했다. 잠금은 이 프로세스 안에서만이다(P6-03).
- **관리 화면 스타일을 따로 불러온다.** 관리 화면의 다크 스타일(`styles.css`)이 전역이라 새
  화면에 새지 않도록, 진입점이 두 화면을 나눠 동적으로 불러오게 했다(`main.tsx`·`AdminEntry.tsx`).
