## 1. 현재 구현과 이 작업이 메울 차이

코드를 대조해 확인한 사실이다(DEVELOPMENT.md 1.6절의 시작점).

1. **업무화 뒤의 흐름을 제품이 잇지 않는다.** `controller/request_processor.py` 는 저장된 요청마다
   읽기 전용 논의 응답 하나를 만들고 요청을 끝낸다. 준비 단계 응답의 해석이 업무 요청이면
   `start_work` 로 같은 Case 를 업무 단계로 옮기지만 **거기서 멈춘다.** 의도 초안 작성·QG-01 검토·
   repair·질문·동의·수준·설계·계획·작업 그래프·작업공간·구현·검증·완료 판정은 관리 화면의 버튼과
   라이브 하네스(`p3/live/path_a.py`, 약 1,000줄)가 해 왔다. 새 화면은 "아직 자동으로 진행하지
   않는다 — 관리 화면에서 진행"을 보인다(`web/src/shell/ConversationView.tsx` `StageBanner`).
2. **진입 검사·판정은 전부 있다.** `admit_and_create_run` 이 Run 을 만드는 유일한 경로이고 목적별
   조건표(`controller/admission.py`)가 의도 동의·QG-01·수준·설계·계획·검토·작업 그래프·작업공간·
   Task×저장소·controlled 시작·목적·material delta·명시 게이트·정책 변경·예산·문맥을 본다. 자동
   완료(`maybe_auto_complete`)는 기준 판정·실행 종료마다 스스로 시도한다. **없는 것은 "다음에 무엇을
   시작하는가"를 정하고 그 실행을 만드는 쪽**이다.
3. **기준 판정을 제품이 적지 않는다.** `record_criterion_result` 는 API 로만 불리고(관리 화면·
   하네스), 검증 실행의 결과(명령·종료 코드)는 기록되지만 어느 기준이 충족됐는지는 사람·하네스가
   적었다(P3-04 하네스: 종료 코드 0 인 명령이 있는 검증 실행만 근거로 전부 `met`).
4. **요청 잠금은 실행 하나짜리 요청만 안다.** 처리기는 응답 실행 하나를 만들고 끝내므로 "실행
   사이에 잠금을 풀지 않는다"(D-70)를 시험할 자리가 없었다. 사람의 결정(동의·확인)으로 다시
   시작하는 진행에는 요청을 열 메시지가 없다 — `conversation_request.opened_by_message_id` 가
   `NOT NULL` 이다.
5. **확인 카드가 새 화면에 없다.** 의도 동의·controlled 시작/결과 확인·material delta 확인·이월 질문·
   단계 검토·피드백 처리·예외 수용은 관리 화면(`IntentPanel`·`PolicyPanel`·`ResultPanel`)에만 있다.
   질문 카드(카드 답변)만 새 화면에 있다.
6. **종료 Case 는 모든 입력을 막는다.** `general_send_state(case_closed=True)` 와 `submit_message` 가
   `case_already_closed` 로 거부하고 진입 검사도 `case_already_closed` 다. D-87 의 설명 전용 진입,
   종료 시점 소비 snapshot, 종료 후 예산 변경 이력, D-33·D-78 의 "새 Case 로 옮김"이 없다.
   `create_successor_case` 는 관리 API 로만 있고 대화와 이어지지 않는다.
7. **Runner 는 "어느 Task 인가"를 지시 원문에서만 안다.** 하네스가 Task 요약을 지시 본문에 적었다.
   배정 내용에는 `task_id` 뿐이고 Task 의 요약·완료 조건·연결 기준은 가지 않는다. 검증·분석 실행의
   보고 형식에 기준별 판정 자리가 없다.

## 3. 설계

### 3.1 진행기 — `controller/work_progressor.py`, 판정은 `domain/work_flow.py`

- **이벤트로 돈다**(처리기와 같다). 부르는 곳: 업무화 직후(처리기의 해석 적용·사람의 `work-start`),
  실행 결과 보고 뒤(`on_run_finished`), 사람 입력 뒤(카드 답변 저장·의도 동의·확인 지점·material
  delta 확인·단계 검토·피드백 처리·예외 수용·예산 변경·`resume`), 작업공간 준비/실패 보고 뒤,
  제어부 기동(복구). 별도 스레드 없음.
- **한 번에 한 걸음.** `advance(case_id)` 는 DB 에서 상태를 읽어(`domain/work_flow.next_step`)
  다음 한 걸음을 정하고 실행 하나(또는 작업공간 요청 하나)를 만든 뒤 돌아온다. 이미 끝나지 않은
  실행이 있으면 아무 것도 하지 않는다(멱등·재진입 안전). 판정은 순수 함수에 두고 진입 검사는 그대로
  `admit_and_create_run` 이 한다 — **진행기는 진입 검사를 우회하지 않는다.** 거부되면 그 사유로
  멈춘다(사람 사유 → 사람 대기, 환경 사유 → 막힘).
- **다음 걸음의 규칙**(`next_step`, 순서가 판정이다):
  1. 종료됐거나 준비 단계면 `idle`. 진행이 사람에 의해 멈춰 있으면(`paused`) `idle`.
  2. 의도 버전이 없다 → `intent_authoring`(지시 = 업무 요청 메시지 원문, 대화·이전 초안·답변·피드백은
     고정 문맥).
  3. 최신 의도 버전의 구조 보고가 아직 없다(실행 중) → 기다림.
  4. 열린 의도 단계 질문 → **사람 대기**(`intent_questions`, 기존 질문 카드).
  5. 최신 버전에 답한 질문이 있고 그 답이 버전보다 뒤에 왔다 → `intent_authoring`(답 반영 재작성).
  6. QG-01: 규칙 판정 실패 → 재작성(repair 상한 안, 지적은 배정 내용의 구조 목록으로 전달) / 상한
     초과 → 사람 대기(`gate_repair_exhausted`). 요구 방식이 `light` 이고 AI 검토 없음 → 가벼운 확인
     기록(`record_light_conformance_check`, 실행 없음). 요구가 `independent` 이고 `not_run` →
     `intent_gate_review`(reviewer·새 세션·지시 = 의도 원문). 검토 뒤 `hold`/`fail` → 재작성(상한) /
     사람 대기.
  7. 미확인 material delta → 사람 대기(`material_delta`).
  8. 최신 의도가 동의되지 않음 → **사람 대기**(`intent_agreement`). 자동 모드에서도 의도 동의는
     사람이 한다 — 기존 진입 조건(`intent_not_agreed`)과 1.6절의 "사람이 필요한 곳(…의도 동의…)"
     그대로다. 동의는 원문을 읽은 사람만 할 수 있다(FR-23, 카드가 원문을 연 뒤 연다).
  9. 수준 미결정 → 사람 대기(`sizing_not_decided`, 관리 화면).
  10. controlled 시작 확인 없음 → 사람 대기(`controlled_start`, 대상 = 최신 의도 버전·해시).
  11. 조사 Profile(RCA·research)이고 작업 그래프가 없다 → `limited_analysis`(읽기 전용, 배정에 현재
      기준 목록을 실어 기준별 결론을 보고하게 한다). 그 실행이 끝났고 기준이 남으면 → 후보(13).
  12. 제품 변경 Profile: Fast Lane 이고 설계 없음 → `plan_authoring`(결합 기록). 아니면 설계 없음/낡음
      → `design_authoring`; 설계 검토 없음: 사람 검토 모드 → 사람 대기(`stage_review`), 자동 모드인데
      필수 항목 미정 → 재작성(상한 2) / 사람 대기. 계획도 같다. 이월 질문은 작업 그래프의 준비도가
      막는 Task 만 막는다 — 배정 가능한 Task 가 없고 이월 질문이 있으면 사람 대기
      (`deferred_questions`). 작업 그래프 없음/낡음(Task 0건) → 사람 대기(`work_graph_missing`).
      배정 가능한 첫 Task: 종류 → 목적·권한(`investigation`→`limited_analysis`/읽기,
      `implementation`→`feature_implementation`/쓰기, `verification`·`integration`→`verification_run`/
      쓰기, `experiment`→`local_experiment`/쓰기). 쓰기 Task 의 저장소: Task 의 저장소 또는 유일한
      코드 저장소; 선택이 없으면 Project 의 대표 저장소를 `auto_select_repository` 로 시도하고
      거부되면 사람 대기(`repository_selection`, 관리 화면). 작업공간이 없으면 `request_workspace`
      뒤 준비 보고를 기다린다(`failed` → 막힘). Task 실행이 실패하면 한 번 다시 시도하고(D-79 의
      제한 재시도) 두 번째 실패는 사람 대기(`task_failed`, 다시 시도 카드).
  13. Task 가 전부 끝났다(또는 조사 실행이 끝났다): 미해결 기준·실행이 없으면 자동 완료는 이미 일어났다
      (`maybe_auto_complete`). controlled 면 후보를 만들고 사람 대기(`controlled_result`). 미해결
      기준이 남으면 후보를 만들고 사람 대기(`criteria_unresolved` — 예외 수용 카드). 목적 의무에
      기준이 없으면 사람 대기(`objective_without_criteria`). 종료 뒤 `done`.
- **repair 상한.** QG-01 재작성과 준비 산출물 재작성은 각 대상(의도 버전 계열·단계)마다 **2회**
  (D-29 기본값, P4-01 과 같은 수)다. 상한은 `case_progress.attempts_json` 에 누적하며 새 의도 버전·
  세션 교체로 초기화하지 않는다.
- **사람 대기·완료·막힘에서 요청을 끝낸다.** 진행 중이던 요청을 `completed`(사람 대기·완료) 또는
  `failed`(막힘)로 끝내고 사유 코드를 `note_summary` 에 남긴다 — 전송이 열린다(D-70).
- **다시 시작.** 사람 입력 뒤 활성 요청이 없으면 **진행 요청**을 열고(3.2) 다음 걸음을 만든다.
  사람 입력 뒤에도 조건이 그대로면 요청을 열지 않는다(빈 요청을 만들지 않는다).
- **중단.** 요청 중단(UI-02)이 진행 요청에도 그대로 적용된다. `interrupted`/`unknown` 으로 끝난
  진행은 `paused` 가 되고 사람이 `resume` 을 누를 때까지 새 실행을 만들지 않는다(D-76 "중단 요청을
  성공·취소로 표시하지 않고 사람이 다시 확인해 진행").
- **기동 복구.** `running` 인데 요청이 처리 중이 아니면 `paused`, 요청이 처리 중이고 끝나지 않은
  실행이 없으면 `advance`.
- **진행 상태·이력**은 새 표 `case_progress`(Case 당 한 행: 상태·걸음·대기 사유·요청·시도 수)와
  `case_progress_event`(걸음마다 한 줄: 행동·실행·요청·사유 코드·짧은 설명, **본문 없음**)다.
  대화 조회에 `progress` 로 실린다.

### 3.2 진행 요청 — 스키마 v20

- `conversation_request.opened_by_message_id` 를 NULL 허용으로 바꾸고 `origin`(`user_message`·
  `human_decision`·`system_resume`)·`origin_ref`(결정 id·메시지 id·걸음 코드, ≤120자)를 더한다.
  표를 다시 만든다(UI-02 의 v18 방식 `_widen_check` 와 같은 재구성). 옛 행은 전부 `user_message`.
- 진행 요청은 여는 메시지가 없다. `request_view.opening_receipt` 는 `stored` 로 답하고(저장할 원문이
  없다), `settle_request`·진입 검사의 "여는 메시지 저장됨" 조건도 같다. 논의 응답은 진행 요청에 붙지
  않는다(요청 처리기는 `user_message` 요청에만 응답 실행을 만든다).
- 잠금·중단·`unknown`·`interrupted`·재확인은 요청 기계 그대로다.

### 3.3 요청 처리기와의 접점

- 처리기 `finish()`: 해석을 적용한 뒤 Case 가 업무 단계면 **진행기에 넘긴다.** 진행기가 다음 실행을
  만들면 요청은 처리 중으로 남고, 만들지 않으면(사람 대기·완료·막힘·조건 그대로) 처리기가 종료를
  적는다. 진행 요청(`origin != user_message`)은 처리기가 응답을 만들지 않고 진행기가 끝낸다.
- 업무 단계의 사용자 메시지: 처리기가 읽기 전용 논의 응답을 만든다(UI-03 그대로, 해석 규칙 없음 —
  D-86 은 UI-04). 응답 뒤 진행기가 다시 본다(사람 입력으로 조건이 풀렸으면 이어 가고, 아니면 끝낸다).
- 설정: 진행기는 처리기와 같은 설정(`HADS_AUTO_PROCESS_REQUESTS`)으로 켜진다. 끄면 UI-01·UI-03 이전
  명시 계약 그대로(관리 화면·하네스가 진행). 기존 시험 하네스는 처리기를 끄므로 그대로 통과한다.

### 3.4 기준 판정의 제품 기록

- 검증 실행(`verification_run`)의 응답에 `criteria: [{key, verdict: met|not_met|unverified,
  summary}]` 를 더한다. 조사 Profile 의 분석 실행(`limited_analysis`, 배정에 기준 목록이 실린 경우)은
  `criteria: [{key, verdict, conclusion: determined|inconclusive, summary}]` 를 낸다. Runner 는 결과에
  `criteria_report` 로 싣고(본문 없음, 요약 ≤200), 제어부는 결과와 같은 트랜잭션에 `run.criteria_report_json`
  으로 남긴다.
- 진행기가 그 보고를 **한 번** 적용한다(`record_criterion_result`, `recorded_by = policy:work_progressor`,
  근거 = 그 실행·`run_output`·현재 코드 조합). 구조 검사: 실행 `completed`; 검증 실행은 종료 코드 0 인
  명령이 하나 이상(P3-04 하네스 규칙); 기준은 **그 Task 에 `verifies` 로 연결된 것만**(조사 Profile 의
  분석 실행은 그래프가 없으므로 현재 기준 전부); 충족 방식은 의무별 대응(제품 의무 → 이 Case 에 변경이
  있는 구현 실행이 있으면 `changed_and_verified`, 없으면 `already_satisfied`; 원인·조사 → `investigated`
  + 보고한 결론; 보존 → `preserved`). P4-03 의 규칙(`domain/completion_meaning.check_result`)이 거부하면
  그 기준은 적지 않고 사유를 진행 이력에 남긴다. 연결되지 않은 기준의 판정은 기록하지 않는다(진행
  이력에 `unlinked`). 미충족·미검증 보고는 그대로 적는다(`not_met`·`unverified`, 근거 = 실행).
- **AI 의 판정을 시스템이 검증하지 않는다.** 9절의 "명령·종료 코드가 AI 자기보고" 그대로이며, 이
  작업이 더한 것은 "판정을 누가 적는가"(제품)와 그 구조 검사다. 이것은 plan 이 정한 세부 규칙이며
  인계에서 사용자에게 확인을 요청한다(5절 물음 1).

### 3.5 Runner·배정 내용

- 배정 내용에 `task`(Task 키·종류·요약·산출물 요약·완료 조건 요약·저장소 이름·연결 기준의 키·요약·
  의무)를 싣는다 — 전부 제어부가 이미 가진 짧은 요약이다. 조사 Profile 의 분석 실행에는 `criteria`
  (현재 기준 전부)를 싣는다. QG-01 재작성 실행에는 `gate_findings`(기준·심각도·대상·요약)를 싣는다.
  종료 Case 의 논의 응답에는 `closed_case = true` 를 싣는다.
- 지시문(Runner): 구현·검증·분석 지시문 끝에 "--- 이 실행의 작업 ---" 블록(Task 요약·완료 조건·기준
  목록), 검증·분석 응답 형식에 `criteria`, 의도 재작성 지시문에 "--- 독립 검토의 지적 ---" 블록, 종료
  Case 응답에 설명 규칙(기존 결과·근거만 설명, 수정 요청이면 `work_request` 해석 — 3.7).
- 구현·검증·분석의 지시 원문은 **업무 요청 메시지 원문**이다(하네스가 쓰던 시스템 작성 지시문을
  만들지 않는다 — 제어부가 본문을 만들지 않는다). 동의된 의도·계획은 고정 문맥으로 간다(P3-04).
  가짜 CLI(`tests/conftest.FakeCliExecutor`·`tests/fake_cli/fake_codex.py`)는 목적별 응답을 낸다.

### 3.6 완료·예외·후속 — 종료 후 설명(D-87)

- 종료 Case 의 일반 메시지를 받는다(`general_send_state` 의 `case_already_closed` 거부를 "설명 전용"
  허용으로 바꾼다 — `send.general.note = explanation_only`). 처리기가 읽기 전용 논의 응답을 만들며
  진입 검사는 **논의 응답에 한해** `case_already_closed` 를 묻지 않는다. 다른 모든 목적·정책 변경은
  그대로 거부된다(`guard_open_case` 불변).
- `closure_record.snapshot_json`(v20 새 컬럼): 종료 시점의 사용량·한도. `budget_state` 가
  `at_closure`(snapshot)와 `after_closure`(총 − snapshot)를 나눠 보인다. 종료 후 설명 실행의 예약·정산은
  같은 Case 예산에 누적된다(기존 경로 그대로).
- 종료 후 예산 한도 변경을 받는다(`set_budget_limit`·`clear_budget_limit` 의 종료 guard 를 예산에
  한해 푼다). 이력은 `budget_setting` 개정으로 남고 종료 기록·판정은 바뀌지 않는다. 다른 정책 변경
  (Autonomy·저장소·확인 지점)은 그대로 거부된다.

### 3.7 후속 Case(D-33·D-78)

- 종료 Case 의 응답에 해석 규칙(종료 판)을 붙인다: `{"kind": "explanation"}` 또는
  `{"kind": "work_request", "profile": …}`. 처리기가 `work_request` 를 받으면 **연결된 새 대화**를
  만든다(`create_successor_conversation`): 준비 단계 Case, `case_relation(follow_up_change)`, 그
  사용자 메시지를 새 Case 의 첫 메시지로 **옮겨 적는다**(같은 원문 참조·같은 접수, 새 요청). 처리기가
  새 Case 의 요청에 논의 응답을 만들고 기존 규칙대로 해석·업무화한다 — 이전 동의·권한은 승계되지
  않는다. 원래 Case 에는 응답과 해석 기록·연결이 남는다.
- 대화 조회에 `relations`(이전/다음 Case)를 싣고 화면이 이동 카드를 보인다.

### 3.8 화면(새 기본 화면, D-72)

- `StageBanner` 를 **진행 카드**로 바꾼다: 진행 중(걸음·실행 상태), 사람 대기(사유별 확인 카드),
  막힘(사유·다시 시도), 멈춤(계속 진행), 완료(종료 종류·예외 수). 서버 `progress` 값 그대로다.
- 확인 카드: 의도 동의(결과물 패널에서 그 버전 원문을 연 뒤 "이 의도에 동의 — 이 범위의 실행을 위임"
  버튼, 서버가 열람 기록·해시를 검사한다), controlled 시작("이 범위로 시작", 대상 의도 버전·해시),
  controlled 결과("이 결과 확인", 후보·해시), material delta(건마다 확인), 단계 검토("설계/계획 검토함",
  원문을 연 뒤), 피드백 처리(반영됨/미반영 사유), 예외 수용(미충족·미검증 기준 선택 + 범위·영향 입력
  + "선택한 예외를 수용하고 종료" — 내부는 예외 결정 + 사람 최종 인수 두 기록), 막힘/실패(다시 시도),
  멈춤(계속 진행). 카드는 대상·버전·해시를 보이고 행위자·시각을 서버가 남긴다. 의례 문구 타이핑을
  요구하지 않는다(최종 인수 문구는 버튼이 정해진 문구를 보낸다 — 서버 계약 그대로).
- 종료 Case: 입력창이 열리고 "종료된 업무 — 기존 결과·근거의 설명만 답한다. 실제 수정 요청은 연결된
  새 대화로 옮겨진다"를 보인다. 후속 Case 가 생기면 이동 카드, 후속 Case 머리에 이전 업무 링크.
- 목록 행에 진행 상태(진행 중·확인 필요·막힘·멈춤), 결정 사항 패널에 진행 이력.
- 관리 화면은 그대로다.

### 3.9 넣지 않은 이유

- **QG-02~07 자동 실행.** P4-01 의 검증 1회 모델(주제 키·입력 해시·독립 세션·repair 예약)을 진행기에
  잇는 것은 게이트 운영 규칙 전체를 다루는 별도 plan 이다. 명시 ON 게이트가 막으면 사람 대기로
  보이고 관리 화면에서 진행한다.
- **활성 Case 의 목적·Profile 변경(D-86).** UI-04. 업무 단계 메시지는 읽기 전용 응답만 받는다.
- **AI 판정의 진위.** 제어부는 본문을 읽지 않는다. 기준 판정은 검증·분석 실행의 보고이고 구조 검사만
  더한다(3.4).
- **자동 게시.** 강제 축은 넷 그대로다. 완료 지점은 로컬 구현·검증(D-78)이다.

## 4. 저장·API

스키마 **v20**.

- `conversation_request` 재구성: `opened_by_message_id` NULL 허용, `origin`, `origin_ref`.

## 5. 성공 기준

| 기준 | 내용 |
|---|---|
| AC-1 | 업무화 뒤 제품이 `intent_authoring` 을 스스로 만든다(지시 = 업무 요청 원문, 같은 요청, 잠금 유지). 사람의 `work-start` 도 같다 |
| AC-2 | 열린 의도 질문에서 멈추고 요청을 끝내 전송이 열린다. 카드 답변 뒤 진행 요청을 열어 답을 반영한 재작성을 만든다 |
| AC-3 | QG-01: 가벼운 확인은 실행 없이 기록, 독립 검토는 reviewer·새 세션 실행. 지적이 있으면 배정에 지적을 실어 재작성하고 상한(2회)을 넘으면 사람 대기 |
| AC-4 | 게이트 통과·질문 없음이면 의도 동의에서 멈춘다. 동의는 원문을 읽은 사람만(서버 검사). 동의 뒤 이어 간다 |
| AC-5 | material delta 미확인이면 멈추고 확인 뒤 이어 간다 |
| AC-6 | controlled: 시작 확인에서 멈추고(대상 = 의도 버전·해시) 확인 뒤 준비를 시작한다. 결과 후보에서 멈추고 확인 뒤 시스템이 종료를 확정한다 |
| AC-7 | 준비: Fast Lane 이면 결합 기록 하나, 아니면 설계·계획 두 건. 자동 검토 모드는 실행 없이 조건 기록, 사람 검토 모드는 멈춘다. 필수 항목 미정이면 재작성(상한) |
| AC-8 | 작업 그래프 순서대로 Task 를 실행한다(의존·이월 질문·저장소·작업공간 조건은 진입 검사 그대로). 저장소 선택이 없으면 허용 안의 자동 선택을 시도하고 새 권한이 필요하면 멈춘다. 작업공간을 요청하고 준비 뒤 구현한다 |
| AC-9 | 검증 실행의 기준 보고를 구조 검사 뒤 기록한다(연결된 기준만, 종료 코드 0 명령 필요, 의무별 방식, 코드 조합 고정). 거부된 보고는 적지 않고 이력에 남는다. 미충족·미검증은 그대로 적힌다 |
| AC-10 | 기준이 전부 충족되면 사람 인수 없이 자동 완료된다(`auto_policy`). 미충족·미검증이 남으면 후보를 만들고 예외 수용에서 멈춘다. 자동 정책은 예외를 수용하지 않는다 |
| AC-11 | 조사 Profile: 분석 실행이 기준별 결론을 보고하고 `investigated` 로 기록된다. 판단 불가는 확정 필수 기준에서 `not_met` 이다 |
| AC-12 | Task 실행 실패는 한 번 재시도하고 두 번째는 사람 대기. 진입 거부의 환경 사유(도구·작업공간·예산·문맥)는 막힘이며 다시 시도로 재개한다 |
| AC-13 | 요청 중단 뒤 진행은 멈춤이고 스스로 재개하지 않는다. `resume` 이 진행 요청을 연다. 재시작 복구가 빠진 걸음을 잇고 중복 실행을 만들지 않는다 |
| AC-14 | 업무 단계 사용자 메시지는 읽기 전용 응답만 받고(해석 없음), 응답 뒤 진행이 조건에 따라 이어지거나 끝난다 |
| AC-15 | 종료 Case: 일반 메시지가 설명 응답을 받고 다른 실행·정책 변경은 여전히 거부된다. 종료 snapshot 과 종료 후 소비가 나뉜다. 종료 후 예산 변경이 이력으로 남고 판정은 불변이다 |

## 10. 구현 중 plan 에서 바꾼 것

- **설정 하나를 더했다** — `HADS_AUTO_PROGRESS_WORK`(기본 켜짐, `ControllerConfig.auto_progress_work`,
  `progress_enabled = 처리기 켜짐 and 이 값`). 4절 "의존성 추가 없음" 은 그대로이고, 새 라이브러리가
  아니라 운영 설정이다. 옛 라이브 `ui/live/ui03_shell.py` 가 이 값을 끄고 UI-03 계약을 그대로 본다.
- **독립 검토의 보고 순서.** 3.2절은 결과 보고 시점에 QG-01 판정이 있다고 가정했다. 실제 Runner 는
  결과 뒤에 검토 보고를 보내므로, 완료된 검토 실행에 판정이 없으면 진행기는 `gate_review_pending` 으로
  기다리고(`FlowState.review_pending`) 검토 보고 경로(`on_gate_reviewed`)가 다시 부른다. 이 대기 동안
  요청은 열린 채다(`keep_request`).
- **처리기와 진행기의 요청 종료.** 3.3절은 "처리기가 사용자 요청을 끝낸다" 였다. 사람 대기·완료·막힘에
  이른 사용자 요청은 **진행기가 사유 코드와 함께 끝내고**, 처리기의 뒤이은 종료 기록은 같은 결과의
  재전송으로 흡수된다. 조건이 그대로인 같은 대기(업무 단계의 대화 응답 뒤)는 이력을 다시 적지 않는다.
- **대화 조회의 현재 요청.** `conversation_view` 가 요청 목록과 현재 요청을 두 번 읽던 것을 한 번 읽은
  행에서 고르게 했다(라이브에서 저장 순간의 조회가 현재 요청 없이 처리 중 요청을 싣고 왔다). 판정 규칙은
  같다.
- **가짜 codex(시험 도구).** 업무 단계 목적별 응답을 `tests.conftest` 의 응답으로 내고, 표지는 고정
  문맥 뒤의 마지막 메시지에서만 읽는다. 검증 응답 fixture 에 기준 C-01·C-02 와 종료 코드 0·1 명령 둘을
  넣었다(구조 검사의 "성공 명령 하나" 를 지나기 위해).
- **기존 시험 다섯의 의미 수정**(결과 3절). AC 는 바꾸지 않았다.
