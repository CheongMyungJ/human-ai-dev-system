## 0. 제품 판단 — 새로 내리지 않는다

이 plan 이 정하는 것은 **무엇을 무엇과 대조하는가**와 **"구현·검증됨 / 남은 것 / 빠진 것"의 판정 규칙**이다. 판정 규칙은 다음
셋이며 상세 설계 선택이 아니라 이 저장소의 검증 규칙(DEVELOPMENT 3·10절)의 적용이다.

- **구현·검증됨**: 그 기대 동작을 완료된 plan 의 AC 가 이름 붙인 시험(자동·브라우저·이행) 또는 실제 CLI 라이브의 제품 규칙이
  고정하고 있고, 그 시험이 이번 세션의 기준선 실행에서 통과했다. 코드가 있다는 것·문서가 목표를 적었다는 것은 근거가 아니다.
- **남은 것**: 설계 문서가 적었지만 완료된 plan 들이 **범위 밖으로 명시**하고 넘긴 것(각 결과 문서의 "경계·남은 것"·DEVELOPMENT
  1.11절의 "넘긴 것"). 새 plan 을 강제하지 않는다 — 필요할 때 사용자가 정한다. P5·P6 의 몫으로 이미 배정된 것도 여기 적는다.
- **빠진 것**: 완료 조건(6절 "P4 완료 조건")이 요구하는데 어느 결과 문서의 AC 도 고정하지 않은 것. **새 plan 으로 기록**한다
  (착수하지 않는다).

"당시 사실" 규칙 그대로다 — 이전 결과의 수치·라이브는 그때의 사실이며 새 통과로 재명명하지 않는다. 실제 CLI 라이브가 선택 사항이던
작업(P4-07b·UI-04b·04c·04d)의 미수행은 빠진 것이 아니라 그 plan 의 AC 가 정한 대로 "미수행"이다.

## 2. 범위

- **UI-04 완료 확인**: D-90 표 4행의 네 항목이 전부 구현·검증됐는지(각 하위 plan 의 AC 전수), UI 설계 13절 1~19 를 결과 문서의
  AC 로 대조해 "구현·검증됨 / 남은 것(어느 작업의 몫)" 을 적는다. 실제 codex·Edge 라이브가 있는 작업과 없는 작업을 나눈다.
- **P4 수용 확인**: 완료 조건의 네 축(여섯 Profile 대표 / 혼합 목적 / 실패·복구·변경 재현 / Case 간 지식 관리·추출·주입)을
  P4-01~07b(+UI-04c 의 D-86)의 AC·시험·라이브로 대조하고, case-profiles 6절 시나리오 1~10 과 수용 점검표의 P4 관련 행(AC-01~20·
  30~36·39)에 근거를 연결한다. **빠진 것만 새 plan(`P4-PLAN-08`)으로 기록**한다.
- **문서 갱신**: DEVELOPMENT.md(1절 현재 표·1.11절·3절 plan 표·4절 진행표·6절·9절·10절 인계), README, 보존본(S-030 인계 옮김),
  수용 점검표·UI 설계 13절·case-profiles 6절에 대조 결과의 위치를 한 줄씩.
- **넣지 않는 것**: 코드·시험·스키마 변경, 새 라이브, P4-PLAN-08 의 착수, P5·P6 의 어떤 작업, 완료된 plan 재개.

## 3. 방법

1. 결과 문서 전부의 2절(성공 기준 근거)·3절(검증)·4/5절(경계·남은 것)을 읽고 AC 마다 근거의 종류(순수/서버/이행/브라우저/라이브)를
   적는다. 시험 이름은 파일에서 존재를 확인한다(`grep`).
2. UI 설계 13절 항목마다 "어느 결과 문서의 어느 AC" 로 대응표를 만든다. 대응이 없으면 그 항목이 어느 작업(P5·P6·별도 plan)의 몫인지
   결과 문서의 "남은 것"·DEVELOPMENT 1.11·9절에서 찾아 적는다 — 찾지 못하면 빠진 것이다.
3. P4 완료 조건의 네 축마다 (a) 계약·판정 수준(API·순수 시험), (b) 제품 흐름 수준(진행기 경유 — P4-05 이후의 실제 경로), (c) 실제
   CLI 라이브의 셋으로 나눠 무엇이 있는지 적는다. Profile 은 여섯을 각각 센다.
4. 빠진 것을 `plans/P4-PLAN-08.md` 에 성공 기준·검증 방법과 함께 기록한다(상태 READY, 착수하지 않음).
5. 기준선(`scripts\run-tests.ps1`)의 수치를 결과 문서에 적는다 — 이 세션은 코드를 바꾸지 않으므로 기준선이 곧 최종이다. 문서
   링크·시험 이름의 존재를 스크립트로 확인한다.

## 5. 검증

- 시험 실행: 시작 시 `pwsh -NoProfile -ExecutionPolicy Bypass -File scripts\run-tests.ps1`(웹 빌드·웹 단위·pytest·P1 계약) 한 번.
  코드 변경이 없으므로 다시 돌리지 않는다.
- 문서 확인: 결과 문서에 적은 시험 이름을 `tests/` 에서 `grep` 으로 확인, 상대 링크의 존재를 스크립트로 확인, `git ls-files --eol`
  로 줄 끝(LF) 확인, `git status --short` 로 변경 파일이 문서뿐임을 확인.
- 실제 CLI: 하지 않는다(새 기능이 없다).

기준선(S-033 시작, 변경 전, `scripts\run-tests.ps1`): 결과 문서 3절과 DEVELOPMENT 1절에 적는다.

## 9. 알려진 한계·선택

- 대조는 결과 문서와 시험 이름을 원천으로 한다. 시험의 **내용**이 AC 를 정말 고정하는지는 대표 몇 건(진행기 경유 Profile 흐름·의무별
  판정)만 코드로 확인했고 전수 재검토는 아니다 — 각 결과 문서가 그 세션에서 한 검토를 신뢰한다.
- 완료 조건의 문장("여섯 Profile 대표 … 재현")은 수준을 명시하지 않는다. 이 plan 은 **제품 흐름 수준(진행기 경유)** 을 기준으로 삼아
  빠진 것을 가른다 — P4-05 부터 업무 단계의 실제 경로가 진행기이기 때문이다. 계약 수준만으로 충분하다고 사용자가 정하면
  P4-PLAN-08 은 하지 않아도 된다(인계의 "사람에게 물어야 할 것").
