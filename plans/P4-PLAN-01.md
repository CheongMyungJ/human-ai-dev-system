# P4-PLAN-01

게이트·repair. 기준: 설계 v0.7 / D-01~67 / 2026-09-22.
선행: P3-04 완료(제한 있음, 스키마 v12, pytest 418 + P1 계약 18 통과 기록).
범위는 P4-01 하나이며 P4-02 이후의 설정 변경 예약·여섯 Profile 전수·지식·외부 게시는
포함하지 않는다.

## 1. 현재 구현과 이 작업이 메울 차이

현재 제품에는 기능 의도용 QG-01 한 종류와 그 규칙/독립 의미 검토가 있다. P3-R4가
QG-01의 정합성 방식을 `light | independent`로 조건부 선택하고, 가벼운 확인이 보지 않은
범위를 기록하게 했다. 그러나 다음은 아직 구현되어 있지 않다.

1. QG-02~07을 Case의 Profile·작업 수준·위험과 실제 Task에 맞춰 선택하는 모델.
2. Case 설정과 Task 명시 설정의 우선순위, 명시 OFF·자동 미적용·통과의 구분.
3. QG-01의 조건부 검사 강도와 QG-02~07의 조건부 별도 의미 검토를 같은 정책 조회에서
   설명하는 계약.
4. 최초 실패와 그 뒤 기본 최대 2회의 자동 수정·재검증을 분리해 누적하는 repair 모델.
5. 새 세션·Task 재분할·게이트 OFF/ON으로 repair 사용량을 초기화하지 않는 강제.

기존 `gate_result`는 의도 버전 하나에 묶인 QG-01의 과거 기록이므로 일반 게이트 표로
억지로 바꾸지 않는다. P4-01은 그 기록을 보존하고, 논리적 채택 경계와 정책·실행·repair를
표현하는 일반 모델을 그 위에 추가한다.

## 3. 정책과 상태 모델

### 3.1 게이트 적용안

`QG-01`은 기능 개발에서 필수이며 OFF를 거부한다. QG-02~07은 현재 Profile과
WorkDepth/작업 그래프를 바탕으로 추천하되, Case·Task 명시 설정으로 ON/OFF할 수 있다.
우선순위는 설계 기준대로 `Task 명시 → Case 명시 → Profile/시스템 추천`이다.

최소 초기 적용안은 다음과 같다.

| 게이트 | 기본 적용 |
|---|---|
| QG-01 요청·의도 | 기능 개발 필수. 다른 Profile도 요청 정합성은 유지하되 기존 기능용 문서 게이트를 강제하지 않음 |
| QG-02 설계 | 설계 산출물이 요구되는 수준/Case에 ON, 아니면 자동 미적용 |
| QG-03 계획 | 실행 작업 그래프를 만드는 Case에 ON |
| QG-04 구현 묶음 | 구현·refactoring·maintenance·defect 변경 Task에 ON |
| QG-05 통합 행동 | 통합 Task, 복수 저장소, deep/중요 위험에서 ON; 그 외 자동 조건부 |
| QG-06 종료 근거 | 모든 Case에 ON |
| QG-07 연구·원인 | root-cause-analysis/research 또는 investigation Task에 ON |

QG-01의 실제 요구 방식은 P3-R4의 `required_conformance_method()`를 계속 사용한다. 다른
게이트의 `independent` 요구도 위험·deep·Case/Task의 명시 상향에서만 선택한다. 규칙이나
실제 도구 증거로 충분한 게이트에 AI 실행을 의무로 추가하지 않는다.

### 3.2 네 축을 합치지 않는다

각 유효 게이트는 다음을 별도 값으로 반환한다.

- 적용: `required | on | off | not_applicable`
- 요구 검사: `rule | light | independent`
- 실행: `not_run | running | completed | blocked`
- 품질 판정: `pass | fail | hold | blocked | needs_recheck | not_applicable`
- 유효성: `current | needs_recheck | historical`

따라서 `off + 마지막 fail`, `on + not_run`, `not_applicable`, `pass`가 서로 다른 상태로
보인다. OFF는 성공 기준·권한·예산·controlled 확인을 지우지 않는다.

### 3.3 입력과 별도 의미 검토

일반 게이트 실행은 Case·Task·게이트·논리적 `subject_key`와 입력 해시, 정책 리비전,
검사 방식, 원문 artifact 참조를 고정한다. 제어부에는 본문을 저장하지 않는다.

`independent`가 요구되면 reviewer 역할의 전용 품질 검토 Run이어야 하고, 작성 Run과
세션이 같으면 통과로 채택하지 않는다. 작성자의 완료 주장만으로 실행을 만들 수 없도록
원 요청/기준/대상/증거 참조의 존재를 검사한다. AI가 올린 발견은 기존 성공 기준에 연결된
확정 필수 위반만 차단하며, 임의의 새 필수 요구를 만들지 않는다.

## 4. repair 누적 계약

repair는 예산과 별도인 `RemediationCycle`로 저장한다.

- 최초 `fail`은 주기를 만들지만 repair 사용량은 0이다.
- 수정 작업을 시작할 때 차수를 예약하고, 관련 재검증 결과가 붙을 때 한 차수로 확정한다.
- 기본 한도는 2이며 Case 명시 한도로 조정할 수 있다.
- 키는 `case_id + gate + subject_key`다. `task_id`·그래프 리비전·session은 보조 참조일 뿐
  누적 키가 아니므로 Task 분할·재계획·세션 교체로 초기화되지 않는다.
- 새 발견은 같은 주기에 추가하고, 같은 발견은 안정적인 `finding_key`로 이어 간다.
- 환경 장애는 제품 repair 차수와 분리하되 실행/예산 기록은 그대로 남는다.
- 한도 소진 뒤 새 repair 시작을 거부한다. 사람의 추가 허용은 한도를 늘리는 새 정책
  리비전이며 사용량과 실패를 0으로 만들지 않는다.
- 게이트 OFF/ON은 주기를 지우지 않는다.

## 5. 저장·API·화면

스키마 v13에 다음 최소 레코드를 둔다. 이름은 구현 중 SQL 제약에 맞게 다듬을 수 있으나
뜻은 바꾸지 않는다.

- `quality_gate_policy`: Case/Task override, 적용/검사 강도/repair 한도, 출처·주체·리비전.
- `quality_gate_run`: 논리적 채택 경계, 입력·정책 스냅샷, 실행 방식·상태·판정·유효성,
  reviewer/author Run·session 참조.
- `quality_gate_finding`: 안정 ID, 기준·대상·근거 참조·필수성·차단·상태·짧은 요약.
- `remediation_cycle`: Case+gate+subject 누적, 최초 실패·사용/예약 차수·한도·상태.
- `remediation_attempt`: 차수와 수정/재검증 Run, 환경 복구 여부, 시작·종료 결과.

API는 유효 정책 목록, Case/Task override, 게이트 실행 시작/결과 기록, repair 시작/종료를
제공한다. 화면은 게이트별 적용·검사 요구·현재 판정·repair `사용/한도`와 출처를 보이며
QG-01의 기존 발견 상세는 보존한다.

## 6. 소급·데이터 경계

- v12의 QG-01 `gate_result`·`conformance_check`를 고쳐 쓰거나 일반 게이트 통과로 복제하지
  않는다. 새 조회가 QG-01 현재 상태를 연결해 보여 줄 뿐이다.
- 기존 Case에 QG-02~07 통과를 만들지 않는다. 현재 추천은 도출값이며 실행은 `not_run`이다.
- 기존 실패/실행을 repair 차수라고 추정해 채우지 않는다. v13 이전에는 repair 모델이
  없었으므로 주기 행을 만들지 않는다.
- 제어부에는 원문·코드·diff·로그 본문을 두지 않고 해시·artifact/Run 참조·200자 이하 요약만
  둔다.

4. 웹: `Push-Location web; npm run build; Pop-Location`.
5. 재시작: 파일 DB에 정책·게이트 실패·repair 1회를 만든 뒤 제어부를 다시 열어 같은 조회와
