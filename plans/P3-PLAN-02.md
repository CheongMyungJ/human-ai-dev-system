포함 범위:
  (1) **작업 그래프 리비전(WorkGraphRevision)**. 현재 유효한 계획은 항상 하나이고
      이전 리비전은 보존된다(FR-07 "변경 이유와 현재 유효한 계획을 남긴다").

  (2) **Task**. 종류(구현·검증·조사·실험·통합), 목적·산출물·완료 조건의 짧은 요약,
      순서, 출처. **본문은 계획 원문 안에** 있고 제어부에는 요약·상태·참조만 온다
  (3) **의존 관계(TaskDependency)**. 순환은 거부한다. 선행 Task 가 끝나지 않으면
      후속 Task 는 배정되지 않는다(`task_dependencies_unmet`)
  (4) **요구·성공 기준과 Task 의 연결(TaskCriterion)**. 구현 Task 와 검증 Task 를
      `relation` 으로 구별한다(FR-06·FR-07). 검증 Task 가 없는 기준은 **화면에
      드러낸다** — 판정하지 않고 보이기만 한다(아래 제외 범위 (바))
  (5) **이월 질문 → Task 연결(TaskQuestionBlock)**. 산출물 원문의 자유 문자열

      `unresolved_block_refs` 로 남기며, 그 질문은 연결 없는 질문으로 취급한다
  (6) **진입 조건의 좁히기**. `deferred_questions_unresolved` 가 Case 전체가 아니라
      요청한 Task 를 막는다. **연결이 없는 열린 이월 질문은 전부 막는다.**
      그래프가 아예 없으면 지금처럼 Case 수준으로 막는다
  (7) **단계 자동 진행이 질문을 대신 해결하지 않는다.** 설계·계획 둘 다 자동 진행인
      Case 에서도 열린 이월 질문은 그대로 막는다(FR-13, intent-artifacts 2절)
  (8) **이미 유효한 승인을 다시 요구하지 않는다.** 답변한 질문은 같은 의도 버전
      안에서 유지되고, 그래프 리비전이 늘어도 다시 묻지 않는다. 계획만 다시 써도
      설계 검토를 다시 요구하지 않는다(FR-13 "막연한 진행 확인을 반복하지 않는다")
  (9) **사람의 재계획**. Task 추가·취소와 질문 연결 조정. 각각 **새 리비전**을

## 성공 기준 (AC)

| ID | 기준 | 검증 방법 |
|---|---|---|
| AC-1 | **검토를 마친 개발계획이 Task 를 정의하면 작업 그래프 리비전이 만들어진다.** 그래프는 그 계획·의도 버전에 묶이고, Task 가 0건인 계획(v1 문서 포함)은 그래프를 만들지 않는다 | 자동 시험: 구조 보고 → 리비전 1 생성·`plan_preparation_id` 일치, Task 0건 → 그래프 없음 |
| AC-2 | **Task 의 본문이 제어부에 오지 않는다.** 목적·산출물·완료 조건의 짧은 요약·종류·순서·출처만 저장되고 본문은 계획 원문에 있다 | 자동 시험(바이트 검사 확장) + 라이브 바이트 검사 |
| AC-3 | **의존 관계가 기록되고 순환은 거부된다.** 없는 Task 를 가리키는 의존도 거부된다 | 자동 시험 3건: 정상 의존, 순환 거부(409), 미지의 키 거부 |
| AC-4 | **성공 기준과 구현/검증 Task 가 연결된다.** `implements` 와 `verifies` 를 구별하고, 검증 Task 가 없는 기준이 조회 결과에 드러난다. 대체된 의도 버전의 기준을 가리키는 연결은 거부된다 | 자동 시험 3건: 연결 조회, 미연결 기준 표시, 옛 기준 연결 거부 |
| AC-5 | **이월 질문이 Task 에 연결된다.** 원문의 `blocks` 자유 문자열이 Task 키로 해석되고, **해석되지 않은 참조는 버려지지 않고** 기록에 남는다 | 자동 시험 2건: 정상 해석, 미해석 참조가 `unresolved_block_refs` 에 남고 그 질문은 연결 없음으로 취급 |
| AC-6 | **좁히기: 연결된 질문이 열려 있으면 그 Task 만 막힌다.** 같은 Case 의 독립 Task 는 배정된다 | 자동 시험: 질문이 T2 를 막는 상태에서 T1 은 `admitted`, T2 는 `deferred_questions_unresolved` |
| AC-7 | **좁히기가 느슨해지지 않는다.** (가) 그래프 없음 (나) Task 0건 (다) 연결 없는 열린 이월 질문 — 세 경우 모두 **전부 막는다** | 자동 시험 3건. (다)는 `blocks` 가 비었을 때와 해석 실패했을 때 각각 |
| AC-8 | **선행 Task 가 끝나지 않으면 후속 Task 가 배정되지 않는다.** 선행이 실제 실행으로 완료되면 그 사유가 사라진다. 실패·불명으로 끝난 실행은 완료로 치지 않는다 | 자동 시험 3건 + **라이브 1건**(실제 CLI 조사 Task 완료 → 후속 차단 해제) |
| AC-9 | **단계 자동 진행이 질문을 해결하지 않는다.** 설계·계획 둘 다 자동 진행인 Case 에서도 열린 이월 질문은 그대로 막고, 자동 진행 기록이 질문 상태를 바꾸지 않는다 | 자동 시험 2건: 자동 진행 후 질문 `open` 유지, 해당 Task 여전히 거부 |
| AC-10 | **이미 유효한 승인을 다시 요구하지 않는다.** 답변한 질문은 같은 의도 버전에서 유지되고 그래프 리비전이 늘어도 다시 묻지 않는다. 계획만 다시 써도 설계 검토를 다시 요구하지 않는다 | 자동 시험 2건: 리비전 2 이후 질문 `answered` 유지·배정 허용, 계획 재작성 후 `design_review_missing` 없음 |
| AC-11 | **그래프에 없는 `task_id` 로는 배정되지 않는다.** 취소된 Task 도 마찬가지다. 이 검사는 `feature_implementation` 과 `limited_analysis` 에 같이 적용된다 | 자동 시험 3건: `task_not_in_work_graph`·`task_cancelled`·`limited_analysis` 에도 적용 |
| AC-12 | **새 의도 버전이 생기면 그래프가 `stale` 이 되고 재사용되지 않는다** | 자동 시험: `work_graph_stale` 발급, 이전 리비전은 조회로 보존 |
| AC-13 | **사람이 Task 를 추가·취소하면 새 리비전이 만들어지고 이유가 남는다.** 이유 없는 재계획은 거부된다. **이전 리비전과 그 `task_key` 의 실행 이력은 보존된다** | 자동 시험 4건: 추가·취소·이유 없음 거부(422)·리비전을 가로지른 실행 이력 조회 |
| AC-14 | **그래프를 갖춰도 쓰기 권한은 생기지 않는다.** 모든 조건을 만족한 Task 에 `workspace_write` 를 요청하면 거부된다 | 자동 시험: 허용 1건 + 같은 상태에서 `permission_not_allowed_in_stage` 1건 |
| AC-15 | **데이터 경계 유지와 재시작 복원.** Task 본문·완료 조건 원문이 제어부 DB·WAL·SHM·로그 바이트에 없고, 강제 종료 후 그래프·리비전·연결·차단 사유가 그대로다. v5 DB에 v6 을 적용해도 기존 행이 보존된다 | 자동 시험(경계·마이그레이션) + 라이브 강제 종료 대조 |
| AC-16 | **화면으로 한 바퀴.** 실제 CLI가 Task 를 정의한 계획을 쓰고, 화면에서 Task·의존·막는 질문·기준 연결이 보이고, 질문에 답하자 해당 Task 의 차단이 풀리는 것까지 브라우저로 재현한다 | 라이브: 브라우저 캡처·조작 기록, README 절차 |

## 새 표 (스키마 v6)

**전부 본문 컬럼이 없다.** Task 의 목적·산출물·완료 조건 서술은 개발계획 원문 안에
있고 여기에는 짧은 요약(≤200)·상태·참조만 온다. P3-01까지의 규칙 그대로다.

| 표 | 답하는 질문 |
|---|---|
| `work_graph_revision` | **지금 유효한 계획은 무엇이고** 왜 바뀌었는가 |
| `task` | 무엇을 만들고 확인하는가. 어떤 순서인가 |
| `task_dependency` | 무엇이 무엇보다 먼저인가 |
| `task_criterion` | 어떤 Task 가 어떤 성공 기준을 구현·검증하는가 |
| `task_question_block` | 어떤 사람 결정이 어떤 Task 를 막는가 |
| `task_block_unresolved` | 원문이 가리킨 Task 를 **찾지 못한** 참조. 버리지 않는다 |
| `question_block_ref` | 원문이 적은 `blocks` 를 해석 전에 보관한다 — 설계 질문이 계획의 Task 를 가리킬 수 있어야 하기 때문 |

`task` 의 완료 상태는 **컬럼이 아니다.** 그 `task_key` 의 실행 결과에서 도출한다 —
실행 증거 없이 의존을 푸는 문을 만들지 않기 위해서다.

## 진입 조건의 새 사유 코드

`AdmissionRefusal` 에 더한다. `feature_implementation` 과 `limited_analysis` 에서
발급된다.

| 코드 | 언제 |
|---|---|
| `work_graph_missing` | 계획 검토는 끝났는데 Task 를 정의한 계획이 없다 |
| `work_graph_stale` | 그래프가 대체된 의도 버전 위에 세워졌다 |
| `task_not_in_work_graph` | 요청한 `task_id` 가 현재 리비전의 Task 가 아니다(취소 포함) |
| `task_dependencies_unmet` | 선행 Task 가 아직 완료되지 않았다 |

`deferred_questions_unresolved` 는 **기존 코드를 그대로 쓰되 범위가 좁아진다.**
새 코드를 만들지 않는 이유는 사람이 해야 할 일("그 질문에 답하라")이 같기 때문이다.
메시지에 어떤 질문이 이 Task 를 막는지와, 연결이 없어 전부 막는 경우인지를 적는다.

## 차단 판정 (요청한 Task 하나에 대해)

```text
그래프가 없다                      → (P3-01 그대로) 열린 이월 질문이 있으면 전부 막는다
그래프가 있다
  ├ stale                          → work_graph_stale
  ├ Task 0건                       → work_graph_missing
  ├ 요청 키가 없다/취소됐다        → task_not_in_work_graph
  ├ 연결 없는 열린 이월 질문이 있다 → deferred_questions_unresolved (전부 막음)
  ├ 이 Task 를 막는 열린 질문      → deferred_questions_unresolved (이 Task 만)
  └ 완료되지 않은 선행 Task        → task_dependencies_unmet
```

설계·계획·수준·의도의 조건은 P3-01 그대로 **먼저** 본다. 그래프는 그 위에 얹히는
조건이지 대체하는 조건이 아니다.
