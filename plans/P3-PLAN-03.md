설계 선택과 근거:
  (가) **작업공간 요청은 제어부가 만들고 실제 git 작업은 Runner 가 한다.**
      저장소와 파일은 Runner 호스트에 있다(D-43). 제어부가 직접 git 을 부르면

      **SHA** 같은 식별자만 올라온다
  (나) **기준 커밋은 커밋된 상태다.** 사용자의 미커밋 변경을 기준에 포함할지는
      별도 입력이며(execution-workspace-review 2절) 이번에는 포함하지 않는다.
      기본값을 "포함"으로 두면 선택되지 않은 변경을 조용히 복사하게 된다
  (다) **브랜치 이름은 Case id 에서 도출한다**(`hads/<case_id>`). 사람이 고른
      이름과 충돌하지 않게 접두사를 두고, 이름만으로 시스템이 만든 것임을 안다.
      **이름이 같다고 우리 것으로 간주하지 않는다** — 기록된 worktree 경로와
      대조해 소유를 확인한다
  (라) **쓰기 권한은 목적별로 연다.** 전역 `STAGE_ALLOWED_PERMISSIONS` 하나를
      넓히면 의도 초안 작성에도 쓰기가 열린다. 목적별 표로 바꾸고 구현·검증에만
      더한다. 그리고 **작업공간이 준비돼야** 한다 — 권한과 작업공간은 함께 열리는
      것이며 이것이 P3-02가 쓰기를 미룬 이유 그대로다(FR-08·FR-26)
  (마) **`verification_run` 을 별도 목적으로 둔다.** 완료 판정이 다르기 때문이다.
      구현은 **변경이 있어야** 완료이고 검증은 **명령 결과가 있어야** 완료다.
      한 목적에 합치면 둘 중 하나의 판정을 포기하게 된다. 작업 그래프의
      `TaskKind.VERIFICATION` 과도 맞는다
  (바) **완료는 계속 실행에서 도출한다.** P3-02의 `derive_task_state` 를 바꾸지
      않는다. 이번에 더하는 것은 "무엇을 completed 로 인정하는가"의 엄격함이다 —
      CLI 의 자기 보고가 아니라 작업공간의 실제 변화와 명령 결과를 본다
      (FR-09 "실제 실행 증거를 작성자의 완료 주장으로 대체하지 않는다")
  (사) **제어부에는 diff·파일 경로·명령 원문·빌드 로그를 두지 않는다.** 변경은
      **수와 SHA** 로, 명령은 짧은 요약(≤200)과 종료 코드로 남기고 원문은
      Runner 의 산출물로 참조한다(D-43·NFR-12). 화면의 상세 열람은 P2-02가 만든
      일시중계 경로를 그대로 쓴다
  (아) **쓰기 직렬화는 제어부의 진입 검사에서 한다.** Runner 쪽 잠금만으로는 다른
      Runner 를 막지 못하고, 제어부만으로는 같은 호스트의 두 Runner 프로세스를
      막지 못한다. 둘 다 둔다 — 제어부가 배정을 막고, Runner 는 worktree 에
      권고 잠금 파일을 둔다. **둘 다 OS 격리가 아니다**
  (자) **경계 밖 변경은 감지·표시만 한다.** 실행 전후로 원래 저장소 트리를
      관측해 바뀌었으면 드러낸다. 이것을 "격리했다"로 적으면 사실과 달라진다

  (차) **새 사유 코드는 `AdmissionRefusal` 에만 더한다.** P3-01·02와 같은 이유다

## 성공 기준 (AC)

| ID | 기준 | 검증 방법 |
|---|---|---|
| AC-1 | **Case 작업공간이 기록된다.** 저장소 경로·전용 브랜치·worktree 경로·**기준 커밋 SHA**가 남고 상태가 `requested → ready` 로 간다. 저장소가 이 호스트에 없으면 `failed` 와 사유가 남고 **빈 디렉터리를 만들지 않는다** | 자동 시험 3건(요청·준비 완료·없는 저장소) + 라이브 1건 |
| AC-2 | **사용자의 원래 작업 트리를 건드리지 않는다.** 미커밋·미추적 파일이 있어도 자동 커밋·stash·reset·삭제가 없고, 기준 커밋에 그 변경이 들어가지 않는다 | 자동 시험(실제 임시 git 저장소에 dirty 파일을 두고 생성 전후 `status` 비교) + **라이브 1건** |
| AC-3 | **충돌하면 덮어쓰지 않는다.** 같은 이름의 브랜치나 비어 있지 않은 경로가 이미 있으면 거부하고 사유를 남긴다. 우리가 만든 것으로 확인되면 재사용한다 | 자동 시험 3건(브랜치 충돌·경로 충돌·재사용) |
| AC-4 | **`workspace_write` 가 열린다 — 조건부로.** 준비된 작업공간이 있는 구현·검증 목적만 허용되고, 작업공간이 없으면 `workspace_not_ready`, 의도·설계·계획 목적은 계속 `permission_not_allowed_in_stage`, `explicit_escalated` 는 계속 거부된다 | 자동 시험 5건 |
| AC-5 | **실제 CLI 가 코드를 바꾼다.** 구현 실행 경로가 생기고, 실행 전후 HEAD·작업 트리 대조가 `workspace_effect` 로 남는다 | 자동 시험(가짜 CLI가 파일을 바꾸는 경로) + **라이브 1건(실제 diff)** |
| AC-6 | **바뀌지 않았으면 완료가 아니다.** 구현 실행이 CLI 기준으로 정상 종료해도 작업공간 변화가 없으면 `failed` 이고 그 Task 는 `done` 이 되지 않는다 | 자동 시험 2건(변경 있음 → completed, 변경 없음 → failed) |
| AC-7 | **빌드·테스트 실행이 증거를 남긴다.** 명령 요약·종료 코드·소요 시간이 기록되고 출력 원문은 Runner 에 있다. **명령 결과가 하나도 없으면 완료가 아니다** | 자동 시험 3건(성공·실패 종료 코드 보존·명령 없음 → failed) |

## 새 표 (스키마 v7)

**본문 컬럼이 없다.** 변경 내용·명령 원문·빌드 로그는 Runner 의 산출물에 있고
여기에는 식별자(SHA·경로·브랜치)와 수, 짧은 요약(≤200)만 온다.

| 표 | 답하는 질문 |
|---|---|
| `case_workspace` | 이 업무는 **어떤 코드 위에서** 어디에 만들어지는가. 준비됐는가 |
| `run_command` | 그 실행이 **무엇을 실제로 실행했고** 어떻게 끝났는가 |

`run.workspace_effect_json` 은 이미 있는 컬럼이며 이번에 처음 채운다 —
실행 전후 HEAD SHA, 변경 여부, 변경 파일 수·삽입·삭제 줄 수, 경계 밖 변경 표시.

## 진입 조건의 새 사유 코드

| 코드 | 언제 |
|---|---|
| `workspace_not_ready` | 쓰기를 요청했는데 준비된 Case 작업공간이 없다 |
| `workspace_failed` | 작업공간 준비가 실패한 상태로 남아 있다 |
| `case_write_in_progress` | 같은 Case 에 아직 끝나지 않은 쓰기 실행이 있다 |
| `runner_write_slot_busy` | 그 Runner 가 이미 쓰기를 하고 있다(기본 1개) |

`permission_not_allowed_in_stage` 는 **없어지지 않는다.** 의도·설계·계획 목적의
쓰기 요청과 `explicit_escalated` 는 계속 이 사유로 거부된다.

## 쓰기 권한 판정

```text
목적이 구현·검증이 아니다            → permission_not_allowed_in_stage
권한이 explicit_escalated 다         → permission_not_allowed_in_stage
Case 작업공간이 없다/requested 다    → workspace_not_ready
Case 작업공간이 failed 다            → workspace_failed
같은 Case 에 미완료 쓰기 실행이 있다 → case_write_in_progress
그 Runner 가 이미 쓰기 중이다        → runner_write_slot_busy
그 밖에는 P3-01·02의 조건을 먼저 본다(수준·설계·계획·검토·그래프·질문·의존)
```

작업공간 조건은 P3-01·02의 조건을 **대체하지 않고 그 위에 얹힌다.**

## 완료 판정

```text
feature_implementation
  CLI 가 completed 로 끝났다          그리고
  workspace_effect.changed == true    → completed
  변경이 없다                          → failed (reason: no_workspace_change)

verification_run
  CLI 가 completed 로 끝났다          그리고
  run_command 가 1건 이상 있다        → completed
  명령 기록이 없다                     → failed (reason: no_command_executed)
```

`unknown` 은 그대로 `unknown` 이며 어느 쪽으로도 바꾸지 않는다.
검증 실행의 **명령 종료 코드가 0이 아니어도 실행 자체는 `completed`** 다 —
"테스트가 실패했다"와 "검증을 수행하지 못했다"는 다른 것이고, 전자는 기준 판정의
입력이지 실행 실패가 아니다.
