포함 범위:
  (1) **작업 수준 판단(SizingAssessment)**. [작업 수준·UX](../sizing-and-review-ux.md)
      1절의 일곱 축마다 `현재 판단 / 아직 확인할 것 / 준비·검증에 주는 영향`을 남긴다.
      **점수로 합산하지 않는다.** AI 제안은 의도 버전에 묶이고(의도 문서 v3), 사람의
      조정은 별개 행으로 이유·남는 위험과 함께 남는다
  (2) **AI가 수준을 조용히 낮추지 못하게 하는 규칙**. 제어부가 축에서 수준을 도출하고
      (`controller/sizing.py`), AI가 그보다 낮은 수준을 제안하면 **낮은 쪽을 쓰지 않는다.**
      낮추는 것은 사람만 할 수 있고 이유·남는 위험이 필수다(sizing-and-review-ux 1·3절)
  (3) **설계안·개발계획 산출물(PreparationArtifact)**. 두 산출물은 **각각의 버전·검토
      상태·조회 경로**를 갖는다(intent-artifacts 2절 "두 산출물은 각각 조회할 수 있어야
      한다"). 정규 문서 형식은 `domain/prep_doc.py` 에 두고 **본문은 소유 Runner에만**
      있다. 제어부에는 참조·항목 상태·짧은 요약만 올라간다
  (4) **수준별 필수 항목**. 간소는 짧은 변경안·계획, 표준은 요구별 대응·인터페이스·
      데이터·의존·통합 순서, 심층은 대안·실패 복구까지. 요구하지 않는 항목은 삭제하지
      않고 `undecided` 로 남는다(intent-artifacts 1절의 규칙을 그대로 적용)
  (5) **단계별 검토 설정(StageReviewSetting)과 검토 기록(StageReview)**.
      기본값은 두 단계 모두 `human_review` 이며 **설정 행이 없는 상태를 자동 진행으로
      해석하지 않는다.** 자동 진행의 결과는 `auto_conditions_met` 이고 사람 검토
      (`human_reviewed`)와 표기·기록이 다르다. 사람 검토만 `decision` 표에
      `design_review`/`plan_review` 행을 만든다(FR-05 검토, FR-23)
  (6) **FR-29 진입 조건의 실제 구현**. `prerequisite_not_implemented` 한 줄 거부를
      실제 선행 조건 검사로 바꾼다 — 수준 미결정, 설계·계획 없음/대체됨/수준이 요구하는
      항목 미정, 사람 검토 미완, 이월 질문 미해결. 조건을 모두 갖추면 **허용한다**
  (7) **오래된 승인의 차단**. 새 의도 버전이 생기면 그 위에 세운 설계·계획이 `stale` 이
      되고 이전 검토를 재사용하지 않는다. 계획이 대체된 설계 위에 있으면 거부한다
  (8) **작성 실행의 고정 컨텍스트(RunContextRef)** — P2-04가 넘긴 위험 1의 해소.
      작성 실행에 이전 버전·미해결 피드백·동의된 의도·현재 설계의 **참조를 고정해**
      배정에 싣고 그 목록을 기록으로 남긴다(review-context-contract 2절 "전체 대화
      복사본 대신 버전이 고정된 참조 목록"). 참조 원문이 Runner에 없으면 "비교하지
      않음"으로 남기고 지어내지 않는다
  (9) Runner: `design_authoring` · `plan_authoring` 목적과 지시문, 산출물 저장·등록·
      항목 구조 보고. 의도 작성 지시문에도 고정 컨텍스트와 수준 제안 항목을 넣는다
  (10) 화면: 준비 패널(축별 판단·수준 조정·설계·계획 각각의 버전·항목 상태·원문 열람·
      검토 모드·검토 기록)과 기능 구현 배정 시도의 거부 사유 표시
  (11) 자동 시험과 **라이브 검증**(실제 CLI로 설계·계획 초안 작성, 브라우저로 한 바퀴)
  (12) README 시연 절차와 DEVELOPMENT.md 갱신

설계 선택과 근거:
  (가) **수준 제안은 의도 문서 안에 넣는다(의도 문서 v3).** 성공 기준을 v2에서 문서
      안으로 넣은 것과 같은 이유다 — 축별 근거를 별도 본문 API 로 받으면 데이터 경계가
      뚫리고, 의도 버전이 바뀌었을 때 옛 근거가 새 의도에 그대로 붙는다.
      v1·v2 문서도 계속 읽으며 그 문서의 축은 **0건**이고 `sizing_not_decided` 다
  (나) **사람의 조정은 새 의도 버전을 만들지 않는다.** 수준은 의도의 내용이 아니라
      준비 깊이의 결정이다. 그래서 `sizing_assessment` 를 별개 표로 두고 AI 제안과
      사람 조정을 `source` 로 구별한다. 조정이 의도 동의를 무효로 만들지 않는다
  (다) **효과 수준 = max(AI 제안, 축에서 도출한 수준)** 이다. "낮은 항목들의 평균으로
      중요한 영향을 상쇄하지 않는다"와 "AI가 진행을 위해 수행 수준을 묵시적으로 낮추는
      것은 허용하지 않는다"(sizing-and-review-ux 1·3절)의 구체적 구현이다.
      **사람은 낮출 수 있다** — 그때 이유와 남는 위험이 필수이고 기록에 남는다
  (라) **설계와 계획을 한 표(`preparation_artifact`)의 `stage` 로 구분한다.** 두 표로
      나누면 버전·검토·조회·대체 규칙을 두 벌 쓰게 되고 한쪽만 고치는 실수가 생긴다.
      **조회 경로는 단계별로 따로** 두어 "각각 조회할 수 있다"를 지킨다
  (마) **간소 수준에서도 두 산출물이 모두 존재한다.** intent-artifacts 2절은 간소에서
      "한 화면 또는 하나의 파일 안에 함께 표현할 수 있다"고 하지만 그것은 **표현**의
      허용이다. 논리적으로 구분해 조회해야 하므로 기록은 둘로 남기고 화면이 함께 보인다
  (바) **자동 진행은 `stage_review` 행을 만들지만 `decision` 행을 만들지 않는다.**
      한 표에 두 가지를 섞으면 "사람 승인 기록 생성"이 되어 버린다(sizing-and-review-ux
      2절 "자동 진행이 사람 승인 기록 생성으로 이어지면 안 된다").
      `actor` 도 사람 이름이 아니라 정책 식별자다
  (사) **계획은 검토된 설계 위에만 만든다.** 의존 관계가 `의도 → 설계 → 개발계획 →
      구현`(intent-artifacts 2절)이므로 설계 검토가 끝나기 전의 계획 작성은 거부한다.
      설계가 대체되면 그 위의 계획도 `plan_not_for_current_design` 으로 막힌다
  (아) **고정 컨텍스트는 참조 목록이며 본문이 아니다.** 제어부는 `run_context_ref` 에
      `(role, artifact_id, revision)` 만 남기고, 그 참조로 원문을 읽어 지시문을
      조립하는 일은 원문을 가진 Runner가 한다. P2-03이 정한 경계를 그대로 따른다
  (자) **진입 조건의 새 사유 코드는 `AdmissionRefusal` 에만 더한다.** 동의 거절
      (`AgreementRefusal`)·인수 거절(`AcceptanceRefusal`)과 합치지 않는다.
      네 번째 목록을 만들지도 않는다 — 이것은 "실행을 배정해도 되는가"의 같은 질문이다
  (차) `PREREQUISITE_NOT_IMPLEMENTED` 값은 **지우지 않고 남긴다.** P2-03·P2-04가 남긴
      진입 검사 기록이 그 코드를 갖고 있고, 값을 지우면 과거 기록을 읽을 수 없다.
      이제 새로 발급하지 않는다는 사실을 주석으로 적는다

## 성공 기준 (AC)

| ID | 기준 | 검증 방법 |
|---|---|---|
| AC-1 | **기본값은 두 단계 모두 사람 검토다.** `stage_review_setting` 행이 없는 Case도 설계·계획이 `human_review` 로 읽히고, 행 없음을 자동 진행으로 해석하지 않는다 | 자동 시험: 새 Case·기존(v4) Case 모두 두 단계 `human_review` |
| AC-2 | AI가 일곱 축의 `판단 / 미확인 / 영향`과 함께 수준을 제안하고, 그것이 **의도 버전에 묶인다.** 축을 점수로 합산하지 않으며, 축 정보가 없는 v1·v2 문서는 0건으로 남고 수준은 미결정이다 | 자동 시험: 축 7행 기록, 새 의도 버전에서 이전 제안 `superseded`, v1 문서 → `sizing_not_decided` |
| AC-3 | **AI가 수준을 조용히 낮추지 못한다.** 축에서 도출한 수준보다 낮은 제안이 오면 효과 수준은 도출한 쪽이고 두 값이 모두 기록에 남는다 | 자동 시험: `deep` 축 + `simple` 제안 → 효과 수준 `deep`, `recommended_level`·`derived_level` 둘 다 보존 |

| AC-5 | **설계와 개발계획을 각각 조회할 수 있다.** 단계별 목록·버전·검토 상태가 따로 있고, 간소 수준에서도 두 산출물이 모두 존재한다 | 자동 시험: `?stage=design`·`?stage=plan` 각각 반환, 간소 Case에서 두 단계 모두 필요 |
| AC-6 | **자동 진행에서도 원문 산출물이 보존된다.** 상태는 `auto_conditions_met` 이며 `human_reviewed` 로 적히지 않고 `decision` 표에 사람 검토 행을 만들지 않는다 | 자동 시험: 자동 진행 후 산출물 참조·원문 해시 유지, `decision` 에 `design_review` 행 0건, `actor` 가 정책 식별자 |
| AC-7 | **산출물이 없거나 수준이 요구하는 항목이 미정이면 기능 구현이 배정되지 않는다.** 사유가 코드로 구별된다 | 자동 시험 4건: `design_missing`·`design_incomplete_for_level`·`plan_missing`·`plan_incomplete_for_level` |
| AC-8 | **사람 검토가 남아 있으면 배정되지 않는다.** 검토 모드에 따라 사유가 구별된다 | 자동 시험 2건: `design_review_missing`·`plan_review_missing`, 자동 진행 모드에서는 해당 사유가 사라짐 |
| AC-9 | **오래된 승인은 재사용되지 않는다.** 설계·계획 검토 뒤 새 의도 버전이 생기면 두 산출물이 `stale` 이 되고, 계획이 대체된 설계 위에 있으면 거부된다 | 자동 시험 3건: `design_stale`·`plan_stale`·`plan_not_for_current_design` |
| AC-10 | **이월한 사람 질문이 남아 있으면 배정되지 않는다.** 의도 단계 질문과 설계·계획으로 이월한 질문을 구별해 거부한다 | 자동 시험 2건: `open_intent_questions`(기존)·`deferred_questions_unresolved`(신규) |
| AC-11 | **조건을 모두 갖추면 `feature_implementation` 이 허용된다.** 다만 `workspace_write` 는 계속 거부된다 — 검토·인수가 쓰기 권한을 만들지 않는다 | 자동 시험: 읽기 권한 허용 1건 + 같은 상태에서 `workspace_write` 거부 1건 |
| AC-12 | **작성 실행이 이전 버전을 본다.** 재작성 요청에 이전 의도 버전·미해결 피드백 참조가 고정돼 배정에 실리고 그 목록이 기록에 남는다. 참조 원문이 Runner에 없으면 "읽지 못함"으로 남고 지어내지 않는다 | 자동 시험: `run_context_ref` 행과 배정 payload 확인, 원문 없는 참조의 처리 + 라이브 1건 |
| AC-13 | 데이터 경계 유지: 설계·계획 본문, 축별 근거 서술, 조정 이유 원문이 제어부 DB·WAL·SHM·로그 **바이트에 없고** Runner 저장소에는 있다 | 자동 시험 확장 + 라이브 바이트 검사 |
| AC-14 | **재시작 복원.** 제어부·Runner 강제 종료 후에도 수준·조정 이력·설계·계획·검토 모드·검토 기록이 그대로다. v4 DB에 v5를 적용해도 기존 행이 보존된다 | 자동 시험(마이그레이션·재연결) + 라이브 강제 종료 대조 |
| AC-15 | **화면으로 한 바퀴.** 실제 CLI가 설계·계획 초안을 쓰고, 사람이 원문을 열람해 수준을 조정하고 두 단계를 검토한 뒤, 기능 구현 배정이 허용되는 것까지 브라우저로 재현한다 | 라이브: 브라우저 캡처·조작 기록, README 절차 |

## 고정 컨텍스트 참조 (RunContextRef)

목적별로 제어부가 고정하는 참조다. **본문은 실리지 않는다** — Runner가 이 참조로 자기
저장소에서 원문을 읽는다. 읽지 못한 참조는 지시문에 "읽지 못함"으로 표시되고 산출물이
그 사실을 갖는다.

| 목적 | 고정하는 참조 |
|---|---|
| `intent_authoring` | 직전 의도 버전 원문(`previous_intent`), 미해결 피드백 원문(`feedback`) |
| `intent_gate_review` | 검토 대상은 지시 원문이므로 추가 고정 없음(P2-03 그대로) |
| `design_authoring` | 동의된 의도 원문(`agreed_intent`), 직전 설계(`previous_design`), 미해결 피드백 |
| `plan_authoring` | 동의된 의도 원문, 현재 설계(`current_design`), 직전 계획(`previous_plan`) |

이것이 P2-04가 남긴 위험 1의 해소다. 이번 단계에서 다루는 이유는 설계·계획 작성이
**같은 작성 경로를 쓰기 때문**이다 — 고치지 않으면 설계 재작성도 같은 방식으로
퇴화하고, 그 퇴화가 기능 구현의 선행 조건을 망가뜨린다.

## 완료 기록 (2026-09-21)

성공 기준 **AC-1~15를 모두 통과**했다. 근거는 [P3-01 결과](../p3/evidence/P3-01-results.md)
8절에 기준별로 있다. 자동 시험 pytest 169건 + P1 계약 unittest 18건이 통과하고,
실제 codex·claude 7회 실행과 브라우저 확인으로 라이브 검증을 했다.

**계획이 예상하지 못한 일이 둘 있었다.** 둘 다 라이브에서 드러났고 고쳤다.

(가) **배정이 처음 허용된 순간 Runner 에 실행 경로가 없어 루프가 죽었다.** 진입 조건과
실행 경로는 서로 다른 것이어서 한쪽만 먼저 열릴 수 있는데, 그 경우를 계획에 적지 않았다.
지금은 실행 경로가 없는 목적을 **CLI를 부르지 않고 `failed` 로 보고**한다.

(나) **수준을 올려도 이미 있는 산출물이 부족해지지 않았다.** 필수 항목을 산출물 작성
시점의 수준으로 판단하고 있었다. 계획의 "수준별 필수 항목" 표는 어느 수준을 기준으로
판단하는지를 적지 않았고, 그 빈틈이 조정을 겉치레로 만들었다. 지금은 **Case 의 현재
수준**으로 판단하고 항목 표에 `지금 필수`와 `보고 시점 필수`를 따로 보인다.

그 밖에 라이브·검토에서 찾아 고친 것 셋이 더 있다(결과 문서 10절).
**기준을 완화하거나 새 수용 제한을 만들지 않았다.**
