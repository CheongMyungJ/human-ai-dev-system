## 2. 만든 것

**"무엇을 어떤 순서로 만들고, 그중 무엇이 왜 지금 막혀 있는가"가 보인다.**
P3-01에서 이월 질문 하나는 Case 전체를 막았다. 이제 그 결정에 의존하는 Task 만 막는다.

| 조각 | 무엇을 하는가 |
|---|---|
| `controller/work_graph.py` | 순환 검사·Task 상태 도출·차단 사유 계산. **DB 접근이 없다** — 진입 검사·화면·시험이 같은 함수를 본다 |
| `work_graph_revision` | 지금 유효한 계획은 무엇이고 왜 바뀌었는가. **리비전 단위로 통째로 바뀐다** |
| `task` | 무엇을 만들고 확인하는가. 종류·순서·짧은 요약만 있고 **본문 컬럼이 없다** |
| `task_dependency` | 무엇이 무엇보다 먼저인가. 순환·미지의 의존은 거부된다 |
| `task_criterion` | 어떤 Task 가 어떤 성공 기준을 **구현**하고 **검증**하는가 |
| `task_question_block` / `task_block_unresolved` | 어떤 사람 결정이 어떤 Task 를 막는가. **해석되지 않은 참조도 버리지 않는다** |
| `question_block_ref` | 산출물 원문이 적은 `blocks` 를 해석 전에 보관한다 — 설계 질문이 계획의 Task 를 가리킬 수 있어야 하기 때문 |
| 계획 문서 v2 (`domain/prep_doc.py`) | 개발계획이 `tasks` 를 갖는다. **v1 문서는 계속 읽는다** |
| `controller/admission.py` | `deferred_questions_unresolved` 의 범위가 Case 에서 Task 로 좁아졌다. 새 사유 4개 |
| `web/src/WorkGraphPanel.tsx` | Task·의존·차단 사유·기준 대응·사람의 재계획 |

### Task 의 완료 상태는 컬럼이 아니다

그 `task_key` 의 실행 결과에서 도출한다. 사람이 "끝났다"고 적는 경로를 만들지 않았다 —
그것은 실행 증거 없이 의존을 푸는 문이 되기 때문이다(FR-09 "미실행을 실행·통과로
표시하지 않는다"). `failed`·`cancelled`·`unknown` 으로 끝난 실행은 완료가 아니며,
특히 `unknown` 은 "아마 됐을 것"이 아니라 **모른다**이다.

### 좁히기가 느슨해지지 않게 하는 세 규칙

| 상황 | 결과 |
|---|---|
| 그래프가 없다 (계획이 Task 를 정의하지 않았다) | `work_graph_missing` — 전부 막는다 |
| 그래프에 Task 가 0건이다 | `work_graph_missing` — 전부 막는다 |
| 열린 이월 질문에 연결된 Task 가 하나도 없다 | `deferred_questions_unresolved` — **전부 막는다** |

셋째가 핵심이다. 연결이 없다는 것은 "아무 것도 막지 않는다"가 아니라 **무엇을 막는지
모른다**는 뜻이고, 모르는 것을 안전한 쪽으로 읽으면 질문 하나를 연결하지 않는 것만으로
모든 차단이 사라진다.

## 4. 라이브 검증 — 실제 CLI로 작업 그래프

프로세스로** 띄우고 실제 CLI를 불렀다. 전 구간 기록은
[P3-02-live.log](P3-02-live.log) 에 있다.

| Run | 목적 | 도구 | 결과 |

### 4.2 AI가 제안한 수준을 시스템이 올렸다 (P3-01의 규칙, 라이브 재확인)

```

```

codex 가 `standard` 를 제안했지만 축에서 도출한 `deep` 이 적용됐다. **낮은 쪽을 쓰지
않는다**는 P3-01의 규칙이 이번 라이브에서도 그대로 작동했다.

### 4.3 개발계획이 작업 그래프를 낳았다 (AC-1·AC-3·AC-4·AC-5)

codex 가 쓴 개발계획에서 **Task 9개**가 올라왔다. 전체는
[P3-02-work-graph.json](P3-02-work-graph.json) 에 있다.

| Task | 종류 | 선행 | 기준 연결 |
|---|---|---|---|
| T1 | 조사 | — | C-01·C-02 구현 |
| T2 | 실험 | T1 | C-01 검증 |
| T3 | 구현 | T2 | C-01 구현 |
| T4 | 구현 | T3 | C-01·C-02 구현 |
| T5 | 구현 | T1 | C-01·C-02 검증 |
| T6 | 검증 | T3, T5 | C-01 검증 |
| T7 | 검증 | T4, T5 | C-01·C-02 검증 |
| T8 | 검증 | T4, T5 | C-02 검증 |
| T9 | 통합 | T6, T7, T8 | C-01·C-02 검증 |

**요구하지 않은 것이 저절로 되지는 않았다** — 지시문이 검증 작업을 별도 Task 로
두라고 적었고, AI가 그대로 따랐다. 구현과 검증이 값으로 나뉘어 있으므로 "만들기는
하는데 확인하지 않는 기준"이 있으면 그것이 표에 드러난다(4.7절).

이월 질문은 **11건**(설계 5 + 계획 6)이었고, 그중 **6건이 원문의 자유 문자열
`blocks` 에서 Task 키로 해석됐다.**

```
질문→Task 연결={q-11fa…: ['T1'], q-3c95…: ['T1'], q-4e8f…: ['T1'],
                q-f500…: ['T1'], q-1a97…: ['T3','T5'], q-6d68…: ['T5']}
해석 실패 참조=[]
```

### 4.4 좁히기가 느슨해지지 않았다 (AC-6·AC-7)

**질문 11건 중 5건에는 기다리는 작업이 적혀 있지 않았다.** 그 상태에서 Task 9개가
**전부** 막혔다 — 연결된 질문이 없는 T2·T4·T6~T9 도 막혔다.

```
T1: 배정가능=False 사유=['deferred_questions_unresolved', 'deferred_questions_unresolved']
T2: 배정가능=False 사유=['deferred_questions_unresolved', 'task_dependencies_unmet']
...
구현 배정 T1: status=409 사유=['deferred_questions_unresolved']
```

T1 에 사유가 **두 번** 나오는 것이 이 설계의 모습이다 — "연결 없는 질문이 전부
막는다"와 "이 Task 를 막는 결정이 있다"는 다른 사실이고, 둘 다 보인다.

11건에 모두 답하자 **좁혀졌다.**

```
T1: 배정가능=True  사유=[]
T2~T9: 배정가능=False 사유=['task_dependencies_unmet']
```

질문이 풀리자 남은 이유가 **의존 하나**로 정확해졌다. 이것이 P3-01과 다른 점이다 —
그때는 질문 하나가 Case 전체를 `deferred_questions_unresolved` 로 막았고, 무엇이
왜 막혔는지 구별되지 않았다.

그래프에 없는 키로는 배정되지 않는다.

```
그래프 밖 task_id: status=409 사유=['task_not_in_work_graph']
```

### 4.5 선행 Task 가 실제로 끝나자 차단이 풀렸다 (AC-8)

**이것이 이번 단계에서 가장 중요한 라이브 결과다.**

```
실행 전 후속 사유=['task_dependencies_unmet']
T1 실행 status=201 outcome=completed          ← 실제 Claude Code 실행
실행 후 T1 상태=done
실행 후 후속 배정가능=True 사유=[]
후속 구현 배정: status=201 사유=[]
```

**사람이 "끝났다"고 적은 것이 아니다.** T1 의 상태는 그 `task_key` 의 실행 결과에서
도출됐고, 실행이 `completed` 로 끝났기 때문에 `done` 이 됐다. 그 문을 사람이 누를
수 있게 만들지 않은 것이 설계 선택이며(FR-09), 라이브가 그 경로를 실제로 탔다.

### 4.6 그래프를 갖춰도 쓰기 권한은 생기지 않는다 (AC-14)

같은 상태에서 권한만 바꾸면:

```
쓰기 권한 요청: status=409 사유=['permission_not_allowed_in_stage']
```

**진입 조건을 다 갖춘 것과 코드를 바꿀 권한은 다른 문제다.** P3-01이 정한 경계가
그대로다.

### 4.7 성공 기준 대응 — 판정하지 않고 보이기만 한다 (AC-4)

```
C-01: 구현=['T1','T3','T4'] 검증=['T2','T5','T6','T7','T9'] 확인작업있음=True
C-02: 구현=['T1','T4']      검증=['T5','T7','T8','T9']      확인작업있음=True
```

두 기준 모두 확인할 작업이 있다. **없었더라도 배정을 막지는 않는다** — 시스템은
산출물의 내용이 충분한지 판정하지 않는다는 P3-01의 경계를 그대로 유지하고, 보이는
것으로 사람 검토와 (P4의) QG-03에 넘긴다.

### 4.8 사람의 재계획 (AC-13)

```
추가 status=201
리비전 2건: r2(human_replanning: 검증 작업이 계획에 없었다),
            r1(plan_artifact: 개발계획 v1 이 정의한 작업)
재계획 뒤에도 T1 실행 이력 1건 — 상태=done
이유 없는 재계획: status=422
```

**재분할이 실행 이력을 초기화하지 않았다.** `run.task_id` 가 행 id 가 아니라
`task_key` 이기 때문이며, 리비전이 늘어도 T1 의 완료가 유지된다. 이유 없는 재계획은
거부된다.

## 9. 라이브로 하지 않은 것

**다음 넷은 자동 시험으로만 확인했다.** 미검증이 아니라 실제 CLI 실행으로 재현하지
않았다는 뜻이다.

| 항목 | 이유 |
|---|---|
| 의존 관계의 **순환**과 없는 Task 를 가리키는 의존 | 실제 AI가 그런 계획을 쓰게 유도해야 하는데, 유도한 결과는 실증이 아니다 |
| **자동 진행 모드에서 질문이 그대로 막는 것**(AC-9) | 설계·계획 둘 다 자동 진행으로 돌리는 한 바퀴를 따로 돌려야 한다 |
| **새 의도 버전이 그래프를 `stale` 로 만드는 것**(AC-12) | 라이브에서 의도를 다시 쓰면 그 뒤 설계·계획을 전부 다시 만들어야 한다 |
| **취소된 Task 의 거부**와 `limited_analysis` 의 그래프 검사 | 자동 시험으로 충분히 결정적이다 |

그리고 **구현 Task 는 라이브에서 끝나지 않았다.** 실행 경로가 P3-03이기 때문이며,
그것이 지금의 정확한 상태다 — 배정만 열리고 실행하면 `failed` 다.

## 10. 검토·시험 중 발견해 고친 것

| # | 무엇 | 어떻게 드러났나 |
|---|---|---|
| 1 | **Task 요약을 본문에서 만들고 있었다.** 산출물 서술이 200자 이내면 그대로 제어부에 올라갔다 | 새로 쓴 데이터 경계 시험이 잡았다. 작성자가 따로 쓴 요약만 쓰고, 없으면 자리표시 문구를 쓰도록 고쳤다. **짧은 본문만 새는 경계는 경계가 아니다** |
| 2 | **질문의 `blocks` 참조가 리비전을 넘어 쌓였다.** 계획을 다시 쓰면 없어진 Task 를 가리키는 옛 참조가 살아남아 그 질문이 영원히 전부 막는다 | 스스로 검토하다 찾았다. 같은 질문을 다시 보고하면 **더하지 않고 바꾸도록** 고치고 시험을 더했다 |
| 3 | **오래된(`stale`) 그래프에 Task 를 더할 수 있었다.** 의도가 바뀌어 계획이 이미 대체됐는데 거기에 작업을 더하면 옛 의도의 계획이 되살아난다 | 스스로 검토하다 찾았다. 거부하도록 고쳤다 — 고칠 것은 계획이지 그래프가 아니다 |

**검증 스크립트의 결함 셋**도 라이브에서 드러났다. 제품 결함이 아니므로 위 표와
나누어 적는다. (가) QG-01 검토에 의도 원문 대신 일반 문장을 지시로 줬다 — 이때
claude 가 "검토할 초안이 첨부되지 않았다. **빈 findings 는 '문제 없음'이 아니라
'입력 없음'이다**"라고 정확히 보고했고, 그 보고가 스크립트의 오류를 알려 줬다.
(나) 원문 열람 응답 형식을 잘못 읽었다. (다) **의도 단계 질문에 답하기 전에 동의를
시도해 거절됐고**(`open_intent_questions`), 그 뒤의 모든 거부가 이 하나에서 파생된
것인데 각각의 검사 결과처럼 보였다. 지금은 파생 거부를 진짜 검사 결과로 적지 않도록
그 지점에서 멈춘다.

## 11. 남은 위험

1. **구현 실행 경로가 없다.** 배정은 열리지만 실행하면 `failed` 다. 작업공간·브랜치·
   기준 커밋과 쓰기 권한은 P3-03이다. 그래서 **구현 Task 는 아직 끝날 수 없고**,
   그 뒤의 Task 도 의존으로 계속 막힌다 — 이것이 정확한 현재 상태다
2. **AI가 낳는 질문이 더 많아졌다.** 라이브에서 설계 5 + 계획 6 = **11건**이 됐다
   (P3-01은 8건). 좁히기는 "질문 하나가 무관한 Task 까지 막는 것"을 줄였을 뿐
   **질문의 개수를 줄이지 않는다.** 그리고 이번 라이브에서 11건 중 5건에 기다리는
   작업이 적혀 있지 않아 **결국 전부 막혔다** — 좁히기의 효과는 AI가 `blocks` 를
   얼마나 성실히 적는지에 달려 있다. 질문의 중요도 구분은 P4다
3. **`blocks` 는 여전히 자유 문자열이다.** 해석되지 않으면 버리지 않고 남기며 그
   질문은 모든 Task 를 막는다. 사람이 화면에서 고칠 수 있지만, **AI가 정확한 키를
   쓰도록 강제할 수단은 없다**
4. **Task·기준 연결이 적절한지는 판정하지 않는다.** 검증 Task 가 없는 기준을 보이기만
   하고 배정을 막지 않는다. 연결이 형식적으로 붙어 있는 것과 실제로 그 기준을
   확인하는 것은 다르며, 그 판단은 사람 검토와 P4의 QG-03의 몫이다
5. **한 Case 의 Task 가 9개가 됐다.** 작은 기능인데도 그렇다. 화면이 세로로 길어지고
   사람이 훑기 어려워질 수 있다 — 접기·묶기 같은 화면 정리는 이번 범위에 없다
6. P1·P2·P3-01에서 넘어온 위험(`residual_activity` unknown, 안전 중지 미연결, 열람
   요청의 만료·크기 한도 없음, 산출물 내용 판정 안 함, 수준 도출 규칙은 구현 제안)은
   그대로다
